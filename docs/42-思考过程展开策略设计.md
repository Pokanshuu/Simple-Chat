## 52.1 结论

先给结论，后文逐条给出依据、数值与验收方式。

| # | 议题 | 结论 |
|---|---|---|
| 1 | 设置模型 | 一个总开关「展开思考过程」+ 两个阶段选项：「生成中」= 全部展开 / 显示部分；「生成结束」= 保持展开 / 自动折叠。总开关**关闭时子项隐藏且不生效**，固定等于现状 |
| 2 | 默认值 | 总开关**默认关闭**。关闭态 = 生成中只显示部分（96 dp 尾巴）+ 生成结束自动折叠 —— 与当前线上行为逐帧一致 |
| 3 | 打开后的默认组合 | 生成中**全部展开** + 生成结束**保持展开**（即"全展开"）。理由：用户主动打开开关后必须立刻看到差异，否则开关像没生效 |
| 4 | 「生成结束」的定义 | 指**思维链收口**：首条正文到达（`reasoningDone = true`）或流结束 / 中断。**不是**整条回复 `DONE` |
| 5 | 阶段判定 | 生成中 = `UiMessage.reasoningStreaming`（`ui/chat/ChatModels.kt:332`）或时间线通道的 `running`（`ui/chat/TimelinePanel.kt:79`）；其余一律算生成结束 |
| 6 | 手动优先级 | **手动操作优先**：逐条展开 / 折叠一旦发生，本轮（该条回复的生命周期内）不再被策略改动；重新生成产生新消息 id 自然重置，重试（同 id）在进入新一轮流式时清除 |
| 7 | 逐条状态存哪 | **只存内存**（ViewModel 内的 `Map<messageId, Boolean>`），不落库、不进备份。进程重建后回到全局策略；旋转 / 字号变化不重建 Activity（`app/src/main/AndroidManifest.xml:49`），状态保留 |
| 8 | 会话维度 | **不做每会话覆盖**。唯一持久化来源是全局设置；"重进会话"看到的是全局策略 + 本进程内该条的手动状态 |
| 9 | 「显示部分」定义 | 保留现有实现：底部对齐、高度上限 **96 dp**、只渲染末尾约 **1200 字符**、顶部 **22 dp** 渐隐；默认字号下约 **4 行** |
| 10 | 溢出提示 | 总开关打开且「生成中 = 显示部分」时，溢出后在尾巴顶部右侧出现 **「展开全部」胶囊**（点按 = 本条本轮强制展开）。总开关关闭时不出现，保证默认行为零变化 |
| 11 | 流式中能否点标题 | **不能**（沿用现状 `enabled = !running`，`ui/chat/ThinkingHeader.kt:54`、`ui/chat/ProcessPanel.kt:110`）。流式中唯一的逐条入口就是第 10 条的胶囊 |
| 12 | 生成后自动折叠时机 | **0 ms 延迟**，在思维链收口的那一帧开始，动画 **220 ms**（`FoldAnimMs`，`ui/common/Motion.kt:37`）。不做"延迟 X ms"，否则与正文增长叠成两次跳动 |
| 13 | 生成后自动展开 | 与折叠同一判定点。**高度差小于一屏**走 220 ms 动画；**大于一屏或思考超过 4000 字**瞬时切换（0 ms），避免长文本逐帧重排 |
| 14 | 竖线 | `2 dp / 3 dp` → **统一 1.5 dp**（圆角随线宽 = 0.75 dp）；圆点 7 dp、槽位 16 dp、正文左缘**全部不动** |
| 15 | 竖线颜色 | 圆点通道沿用 `processBar × 0.45`；OpenAI 通道由 `processBar` 原值改为 `processBar.alpha × 2`（≈ 浅色 0.32 / 深色 0.42），做"等墨量换算"补偿线宽减半 |
| 16 | 设置持久化 | 新增 JSON blob `ThinkingDisplaySettings`（仿 `ShareImageSettings`、`TypographySettings`）。旧键 `auto_collapse_thinking` **只读迁移**，并继续写镜像值供回滚 |
| 17 | 超长保护 | 生成中「全部展开」遇到 `reasoning.length > LARGE_MESSAGE_CHARS`（128 000，`ui/chat/MessagePage.kt:4`）时**降级为显示部分**并记诊断日志；生成后展开沿用现有 `LargeMessageBody` 分流 |
| 18 | 性能手段 | 全文分段渲染（复用 `textChunks`，块 ≤ 2000 字）+ 仅末块随流变化 + 流式中禁用 `animateContentSize` + `derivedStateOf` 收敛溢出判定 |
| 19 | 搜索命中 | 命中思考内容时**自动展开并记为手动展开**（否则会被"生成结束自动折叠"当场收回）。现有自动展开见 `ui/chat/MessageList.kt:1004-1006` |
| 20 | 非目标 | 不改思考强度语义、不把思考内容同步服务端、不做复制思考正文、不做分享截图里思考块的竖线、不新增数据库表 |

一句话：**总开关决定"要不要展开"，两个阶段选项决定"什么时候展开多少"，手动点过的那一条永远听用户的。**

## 52.2 现状：代码里现在到底怎么做的

### 52.2.1 两条渲染通道

思考内容有两条互不相同的渲染链路，任何策略都必须同时覆盖：

| | OpenAI 兼容通道 | 扩展通道（DeepSeek 官方 / Anthropic 兼容） |
|---|---|---|
| 组件 | `ProcessPanel`（`ui/chat/ProcessPanel.kt:80`） | `TimelinePanel`（`ui/chat/TimelinePanel.kt:68`） |
| 内容结构 | 思考一段 + 正文一段 | 思考 / 搜索 / 浏览 / 正文**交错** |
| 流式中 | `TailContent`：96 dp 底部对齐尾巴、顶部渐隐（`ProcessPanel.kt:117`、`138-211`） | 当前激活的思考段走同一个 `TailContent(gutter = true)`（`TimelinePanel.kt:188-192`）；**已收口的段本来就全文显示** |
| 生成结束 | 等价 `expanded` 为真才显示全文（`ProcessPanel.kt:116-121`） | `running || expanded || !showHeader` 才显示步骤（`TimelinePanel.kt:104-105`） |
| 入口 | `ui/chat/MessageList.kt:1110` | `ui/chat/MessageList.kt:1089` |

> 一个容易被忽略的现状：扩展通道里**已完成的思考段与工具行一直是全文**，只有"还在流的那一段"被 96 dp 窗口裁掉。所以「显示部分」在这条通道上只作用于活跃段，不是整块时间线（§52.6.3 会明确写死这个边界）。

1. 标题点击确实能在"生成结束"后手动展开，但**一旦滑出屏幕再滑回来就复位**，更不用说重进会话 —— 用户看到的是"我刚才明明点开过"。

## 52.3 目标与非目标

### 52.3.1 目标

1. **可表达**：用户能分别决定"生成中看多少"和"生成结束后是否保留全文"。
2. **不打扰**：不关心这一项的用户（绝大多数）在默认设置下**看不到任何变化**，包括视觉与交互。
3. **手动优先**：任何一次用户点按都能压过全局策略，且在同一次浏览期间不再被策略改写。
4. **两通道一致**：OpenAI 通道与扩展通道对同一设置的响应一致；差异只保留在"有没有工具行"这一层。
5. **可施工、可验收**：每一项都有明确数值、判定函数、单测与设备验收步骤。
6. **视觉降噪**：思考块竖线变细，且不因变细而消失。

### 52.3.2 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 改「思考强度 / 思考档位」语义 | 那是**发给模型的参数**（`ui/chat/ChatModels.kt:114-127`、`docs/25-首次启动引导与思考强度.md:13-15`）；本文只改展示 |
| 把思考内容发给服务端 / 参与上下文 | 既有硬约定：思维链只本地展示，构造请求不回传（`docs/07-功能设计.md:966`） |
| 每会话独立设置 | 会话级设置已有 `ConversationSettings`（`ui/chat/ChatModels.kt:108-138`），但它是"这一轮怎么生成"；展开策略属于显示偏好，混进去会让两个面板的语义互相污染 |
| 思考正文的复制 / 分享 / 朗读 | 复制入口当前只复制 `message.content`（`ui/chat/ChatScreen.kt:1327`），朗读也只读正文（`:1356`）；思考不是交付物，v1 不开新入口 |
| 分享截图里的思考块竖线 / 展开策略 | 分享图思考段目前无竖线（`ui/chat/MessageShareImages.kt:114-121`），且已有独立的「隐藏思考」选项（`ui/chat/MessageShareControls.kt:220`） |
| 新增数据库表 / 字段存"这条是否展开" | 纯 UI 瞬态，不值得背迁移与备份语义（§52.9.2） |
| 自动检测"用户正在读思考"并暂停折叠 | 没有可靠信号，误判比不做更烦人 |
| 思考块的富文本 / Markdown 渲染 | 现在是纯 `Text`（`ProcessTextStyle`），换渲染器会把流式成本抬一个数量级 |

## 52.4 设置模型：一个总开关 + 两个阶段策略

### 52.4.1 控件结构与位置

设置在 **设置 > 对话行为**（`ui/settings/SettingsScreen.kt:1725` `ChatBehaviorPage`），落在现有「显示」分组卡内，替换当前的「自动折叠思考内容」开关行：

```
显示
┌──────────────────────────────────────────────┐
│ ✦  展开思考过程                        [ 关 ] │  ← SettingsSwitchRow，替换现「自动折叠思考内容」
└──────────────────────────────────────────────┘
  关闭时：生成中只显示最后几行，生成结束后自动收起。   ← 说明文字（仅关闭时可见）

（总开关打开后，以下两组才出现）

生成中
┌──────────────────────────────────────────────┐
│        全部展开                            ✓ │  ← SettingsChoiceRow
│        显示部分（最后约 4 行）                 │
└──────────────────────────────────────────────┘

生成结束
┌──────────────────────────────────────────────┐
│        保持展开                            ✓ │
│        自动折叠                               │
└──────────────────────────────────────────────┘
```

- 行组件沿用仓库现成的三件套：`SettingsSwitchRow`（`ui/settings/SettingsScreen.kt:3460`）、
  `SettingsChoiceRow`（`:1957`，图标 + 标题 + 选中对勾，`selectable(role = RadioButton)`）、
  `SettingsSectionLabel` / `SettingsCard` / `RowDivider`（`:3166` / `:3178` / `:3191`）。
- **总开关关闭时整组子项隐藏**（不是置灰），与「跨对话记忆」关闭后隐藏「参考会话数」行同一模式
  （`ui/settings/SettingsScreen.kt:1810-1822` 一带）。隐藏而非置灰：置灰会让用户以为"这里还有东西没打开"。
- 子选项行**不配图标**：同页的搜索设置两组开关行本来就不带图标（`SettingsScreen.kt:1772-1783`），
  且行宽在窄屏 + 大字号下要留给选项文案。
- 说明文字用 `Modifier.settingsSectionGrid()` 的 `bodySmall` + `placeholder` 色，与「记忆」页顶部说明同款
  （参照 `ui/settings/SettingsScreen.kt:1794-1800`）。
- 不新增一级入口、不新增二级页面。

### 52.4.2 数据 schema（建议）

```kotlin
// data/ThinkingDisplaySettings.kt（新文件，仿 data/ShareImageSettings.kt）
@Serializable
enum class ThinkingDuring { FULL, PARTIAL }

@Serializable
enum class ThinkingAfter { EXPAND, COLLAPSE }

/**
 * 思考过程展开策略。只影响展示，不参与请求构造。
 *
 * 默认值刻意取 "expand = false"：老用户升级后什么都不变。
 * during / after 的默认值只在用户主动打开总开关时才被用户看到，
 * 取 FULL + EXPAND 是为了"一开就看到全部"。
 */
@Serializable
data class ThinkingDisplaySettings(
    val expand: Boolean = false,
    val during: ThinkingDuring = ThinkingDuring.FULL,
    val after: ThinkingAfter = ThinkingAfter.EXPAND,
) {
    /** 实际生效的生成中策略：总开关关闭时不看子项。 */
    fun effectiveDuring(): ThinkingDuring = if (expand) during else ThinkingDuring.PARTIAL

    /** 实际生效的生成结束策略：总开关关闭时不看子项。 */
    fun effectiveAfter(): ThinkingAfter = if (expand) after else ThinkingAfter.COLLAPSE
}
```

写入 `StoredSettings`（`data/SettingsStore.kt:149` 起）：

| 项 | 值 |
|---|---|
| 字段 | `val thinkingDisplay: ThinkingDisplaySettings = ThinkingDisplaySettings()` |
| key | `val THINKING_DISPLAY = stringPreferencesKey("thinking_display")`（`Keys` 内，`:1025` 一带） |
| 读取 | `prefs[Keys.THINKING_DISPLAY]?.let { runCatching { json.decodeFromString<ThinkingDisplaySettings>(it) }.getOrNull() } ?: 迁移值` |
| 写入 | `suspend fun setThinkingDisplay(settings: ThinkingDisplaySettings)`，`json.encodeToString` |
| 坏数据兜底 | 解码失败（`runCatching.getOrNull()` 返回 null）→ 走迁移值 → 再不行用默认。与 `ShareImageSettings`、`TypographySettings` 的兜底写法一致（`data/SettingsStore.kt:386-391`） |

### 52.4.3 迁移：老用户默认行为必须与当前一致

| 升级前的存储状态 | 迁移后的生效值 | 与当前行为 |
|---|---|---|
| 无 `auto_collapse_thinking`（新装 / 从未改过） | `expand = false` → 部分 + 折叠 | 完全一致 |
| `auto_collapse_thinking = true`（默认值） | 同上 | 完全一致 |
| `auto_collapse_thinking = false`（用户手动关过自动折叠） | `expand = true, during = PARTIAL, after = EXPAND` → 部分 + 保持展开 | 完全一致（当前代码里"关掉自动折叠"只在生成结束后生效，生成中仍是尾巴） |
| `thinking_display` 已存在且可解码 | 直接用新值 | 新行为 |
| `thinking_display` 存在但解码失败 | 走上面三行的迁移逻辑 + 记一条诊断日志 | 可回退到一致行为 |

实现要点：

- 读取顺序：**新键优先**，新键缺失才读旧键。迁移逻辑放在 `SettingsStore.flow` 的映射里
  （`data/SettingsStore.kt:346-435`），不要放在设置页 —— 首帧就要是对的。
- 写入时**镜像旧键**：`AUTO_COLLAPSE_THINKING = (effectiveAfter() == COLLAPSE)`。这样用户降级回旧版本时，
  "生成结束后是否折叠"这一半行为仍然合理；镜像只是一行赋值，不增加维护成本。
- 旧字符串 `settings_auto_collapse` 保留一版（不再被 UI 引用），下个版本再删。

### 52.4.4 默认值取舍

| 组合 | 是否默认 | 理由 |
|---|---|---|
| 关闭 = 部分 + 折叠 | ✅ 默认 | 与现状逐帧一致；这是"零打扰"的前提 |
| 打开 = 全部展开 + 保持展开 | ✅ 打开后的默认 | 开关打开必须立刻可见差异；"全展开"是最容易理解的一档 |
| 打开 = 全部展开 + 自动折叠 | 可选 | 想看过程但不想让思考占着版面的人 |
| 打开 = 显示部分 + 保持展开 | 可选 | 等价于老用户 `autoCollapseThinking = false`，迁移会落到这一档 |
| 打开 = 显示部分 + 自动折叠 | 可选（与关闭等价） | 不禁止。用户可能只是想"先打开总开关、细项以后再说"，此时行为与关闭相同是可接受的 |

## 52.5 行为矩阵（核心）

### 52.5.1 两个阶段怎么判定

| 阶段 | 判定 | 证据 |
|---|---|---|
| 生成中（思考仍在流） | `message.reasoningStreaming == true`（= 有思考 + 整条在流 + 思考没写完） | `ui/chat/ChatModels.kt:332` |
| 生成中（时间线通道） | `streaming && !hasAnswer` → `running` | `ui/chat/TimelinePanel.kt:78-79` |
| 生成结束 | 其余全部情况：首条正文已到 / `DONE` / `STOPPED` / `ERROR` | `ui/chat/ChatViewModel.kt:2505-2515`（`noteBody()` 置 `reasoningDone = true`） |
| 思考内容迟到（正文写完后才来摘要） | 按生成结束策略处理，不重新进入生成中 | `ui/chat/TimelinePanel.kt:142-151` 的分支前提 |

> **「生成结束」= 思维链收口，不是整条回复写完。** 理由：正文一开始，思考块就应该让出空间；
> 若等整条 `DONE` 再展开/折叠，用户已经读到一半的回答会被往上顶一屏 —— 那是"读一半换版式"。
> 这一点与现有实现一致（现有动画在 `reasoningStreaming` 变 false 时就开始）。

### 52.5.2 五种组合的完整矩阵

“可见”列写的是**用户实际看到的思考区**（不含正文）。行号引用同 §52.2。

| 组合 | 生成中 · OpenAI 通道 | 生成中 · 扩展通道 | 生成结束（首条正文 / 中断 / 失败） | 默认 | 备注 |
|---|---|---|---|---|---|
| **A. 关闭**（= 部分 + 折叠） | 96 dp 尾巴（最后约 4 行，顶部渐隐），标题不可点 | 活跃段尾巴；已收口段与工具行照旧全文 | 收成标题行「已思考（用时 N 秒）⌄」 | ✅ | 与当前线上行为一致 |
| **B. 打开 + 部分 + 折叠** | 同 A，但溢出时多一枚「展开全部」胶囊 | 同 A + 胶囊 | 折叠；若用户点过胶囊则保持展开（手动优先） | | 与 A 的唯一差别是"流式中可一键看全文" |
| **C. 打开 + 部分 + 保持展开** | 同 B | 同 B | **自动展开全文**（220 ms；长文本瞬时，见 §52.7） | | 老用户 `autoCollapseThinking = false` 迁移到此 |
| **D. 打开 + 全部 + 折叠** | 全文可见、随流增长；标题不可点 | 活跃段也全文；工具行照旧 | **自动折叠**为标题行（220 ms），用户之后可点开 | | "边看边想，写完就收" |
| **E. 打开 + 全部 + 保持展开** | 同 D | 同 D | 保持全文 | ✅（打开后的默认） | "全展开" |

补充约定：

1. **生成中标题一律不可点**（五档相同）。理由：流式期间展开/收起会把正在跟底的内容结构性地顶走
   （`ui/chat/ChatScreen.kt:1307-1323` 的注释就是这条经验），而这份策略已经交给设置；流式中的逐条入口只有
   B/C 的「展开全部」胶囊。
2. **生成结束后标题一律可点**（五档相同），点按 = 手动覆盖，见 §52.5.3。
3. 没有思考内容（`hasReasoning == false`）时**整块不渲染**，与任何策略无关（`ChatModels.kt:323`、
   `test/.../ReasoningPhaseTest.kt:69-77`）。
4. 时间线通道没有思考、只有搜索/工具行时：`showHeader == false`，步骤始终展示，不参与本策略
   （`TimelinePanel.kt:81-82`、`:104-105`）。

### 52.5.3 手动覆盖的优先级与状态机

优先级（从高到低）：

1. **按条手动状态**（用户点标题 / 点胶囊 / 搜索命中跳转）
2. **全局策略**（§52.5.2 的 A–E）
3. **兜底默认**（若设置读取失败：部分 + 折叠）

逐条状态取值只有三种：

| 值 | 含义 | 产生方式 |
|---|---|---|
| `null`（缺省） | 跟随全局策略 | 初始；新一轮流式开始时重置 |
| `EXPAND` | 本条强制展开 | 生成结束后点标题展开；点「展开全部」胶囊；搜索命中思考 |
| `COLLAPSE` | 本条强制折叠 | 生成结束后点标题折叠（策略本为展开时） |

状态机（单条消息）：

```
                    ┌──────────── 新一轮流式开始（重试 / 重新生成产生新 id）→ 清除 override
                    ▼
 [null：跟随策略] ──点标题──▶ [EXPAND] ──点标题──▶ [COLLAPSE] ──点标题──▶ [EXPAND]
       │                                                        │
       └──策略为 EXPAND 时，用户点标题 = 切到 COLLAPSE ◀──────────┘
```

关键规则：

- **手动优先不设"有效期限"到本轮结束**：这一条回复只要还在（不被重新生成/重试替换），用户点过的状态就一直有效，
  包括跨过"生成结束"那一刻、跨过会话切换（同进程内）。
- 自动折叠 / 自动展开**只作用于 `override == null` 的消息**。因此"手动展开后又被自动折叠"在实现上不可能发生，
  不需要额外的"本轮不再折叠"标记。
- **重试**是同 id 重来（`ui/chat/ChatViewModel.kt:1828-1830`），必须在消息重新进入 `STREAMING` 时清掉该 id 的 override，
  否则新的一轮会继承上一轮的展开态。**重新生成**产生新消息 id（`:1873-1883`），天然无 override。
- **续写**不新增思考（`ui/chat/ChatViewModel.kt:1905-1913`），不清 override。
- override 表上限 1000 条，超出按写入顺序淘汰最旧（正常使用到不了；只是防长会话无限增长）。

### 52.5.4 逐条状态的生命周期总表

| 事件 | override 是否保留 | 用户看到 |
|---|---|---|
| 生成中（策略生效） | 无 override | 按 A–E |
| 首条正文到达（自动折叠/展开） | 不改 | 策略或手动状态 |
| 用户点标题 | 写入 | 立即切换，220 ms 动画 |
| 用户点「展开全部」胶囊 | 写入 `EXPAND` | 立即全文，本轮不再自动折叠 |
| 滑出屏幕再滑回 | **保留**（存在 ViewModel，不在 Composable 里） | 与离开前一致 |
| 切换会话再切回（同进程） | **保留** | 与离开前一致 |
| 旋转 / 字体缩放 / 深浅色切换 | 保留（Activity 不重建，`AndroidManifest.xml:49`） | 一致 |
| 切版本 / 切分支 | 按消息 id 保留（各版本各存各的） | 一致 |
| 进程被杀后重进 | **丢失** | 回到全局策略（`reasoningDone` 本来也不落库，见 §52.9.3） |
| 重试同一条 | 新一轮流式时清除 | 回到策略 |
| 重新生成 | 旧 id 的 override 变孤儿（无害，随淘汰清理） | 新消息按策略 |

### 52.5.5 与搜索、多选、复制的关系（摘要，细节见 §52.11）

| 场景 | 行为 |
|---|---|
| 搜索命中的是思考内容 | 自动展开 + 写入 `EXPAND`（视为手动），高亮走现有 `LocalSearchHighlight`（`MessageList.kt:1085-1086`） |
| 搜索命中的是正文 | 不改思考状态 |
| 分享多选 / 选择文本态 | 思考标题**不可点**（见 §52.11 的修复项） |
| 复制 | 只复制正文，不含思考（维持现状，Non-goal） |
| 朗读 | 只读正文（维持现状） |

## 52.6 「显示部分」的精确定义

### 52.6.1 显示什么

| 维度 | 规定 | 依据 |
|---|---|---|
| 显示哪一段 | **末尾**（最后约 4 行），底部对齐；内容向上溢出被裁掉 | 现状实现 `ProcessPanel.kt:176-193`；理由：思考的价值在"最新在想什么"，与尾巴模式一致 |
| 高度上限 | **96 dp**（`TailHeight`） | `ProcessPanel.kt:243`；`docs/02-UI设计.md:161` 的 4 行口径 |
| 行数换算 | 默认字号下每行约 22.2 dp（15 sp × 0.925 × 行高 24），96 dp ≈ **4.3 行** | `ui/theme/Type.kt:57`、`:113` |
| 字符窗口 | 只渲染末尾 **1200** 字符（约为可视量的十几倍，目的是把"整段重排"压成常数） | `ProcessPanel.kt:251`、`:263-271` |
| 溢出遮罩 | 顶部 **22 dp** 垂直渐变（`Color.Transparent → Black`，`DstIn`） | `ProcessPanel.kt:166-174` |
| 是否滚动 | **不可滚动**。这是一个"日志尾巴"，不是可读区域 | `ProcessPanel.kt:126-135` 的设计说明 |
| 是否跟底 | 尾巴内部不滚（内容自动从下方推入）；外部聊天列表的跟底由 `ChatScreen.kt:884-899` 负责 | 同上 |

### 52.6.2 为什么是 96 dp / 约 4 行

| 候选 | 取舍 |
|---|---|
| 72 dp（约 3 行） | 太窄，思考的"最近一段话"经常被切成半句，读不出信息 |
| **96 dp（约 4 行）** ✅ | 够看清最近一段；在 6.1–6.7 英寸屏上占屏高约 12%，不挤压正文；与现有实现零差值 |
| 120 dp（约 5 行） | 再高就开始像"可读区域"，但又不给滚动，用户会忍不住去拖它 |
| 前 N 行（从开头截） | ❌ 生成中用户关心的是"最新在想什么"；前 N 行在长思考里永远是同一段，等于不更新 |
| 随屏幕高度百分比（如 15%） | 小屏过大、大屏过小；且高度一变会带动所有历史消息重新测量，得不偿失 |

### 52.6.3 两条通道的边界

- **OpenAI 通道**：整段思考就是一段流，96 dp 窗口作用于全段。
- **扩展通道**：96 dp 只作用于**当前仍在流的那个思考段**；已经收口的思考段、搜索行、浏览行保持原样全文
  （`TimelinePanel.kt:187-212` 的现状）。即"显示部分"不是把整块时间线折叠成 4 行 —— 那会把工具行的可点性一起吞掉。
- 时间线通道里 `running == false` 之后（首条正文到达），整块按"生成结束"策略处理（折叠 / 展开），不再有 96 dp 窗口。

### 52.6.4 溢出提示：「展开全部」胶囊

| 项 | 规定 |
|---|---|
| 出现条件 | 总开关打开 **且** 生成中策略 = 显示部分 **且** 内容溢出（测量高度 > 96 dp + 1 px，复用 `ProcessPanel.kt:155-156` 的 `overflowing`） |
| 位置 | 尾巴顶部右侧（盖在 22 dp 渐隐带之上），右对齐，距右缘 0 dp |
| 尺寸 | 视觉高 24 dp、横向内边距 8 dp、`labelSmall`；**点击热区 48 dp**（无障碍最小触控） |
| 样式 | `PillShape` + `card × 72%` 底色（与 §31.5 的展开箭头同一处理，`docs/07-功能设计.md:1170-1173`）、文字色 `processText` |
| 文案 | 中文「展开全部」/ 英文 "Show all"（复用 `msg_expand_all` 或新增 `thinking_expand_all`，见 §52.12） |
| 点击行为 | 本条写入 `override = EXPAND` → 切换为全文渲染；**本轮不再自动折叠**（手动优先） |
| 总开关关闭时 | **不出现**（保证默认行为与现状零差异） |
| 是否可再次收起 | v1 不做。流式中再收起会让正在跟底的视口跳一次，收益低 |

### 52.6.5 与首字加载、滚动锚定的关系

| 关注点 | 结论 | 依据 |
|---|---|---|
| 首字加载（WaitingIndicator） | 不受影响。等待态在思考块之前独立显示，思考块出现用淡入 | `MessageList.kt:1069-1078`、`:1104-1108` |
| 滚动锚定 | 显示部分高度**固定 96 dp**，不随 token 增长 → 不产生每帧高度变化，锚点无扰动 | `ProcessPanel.kt:158-163` |
| 自动跟底 | 96 dp 盒子内部不增长，所以尾巴本身不需要跟底；正文的增长由列表跟底循环负责 | `ChatScreen.kt:884-899`、`ui/chat/ScrollToBottom.kt:128-132` |
| 用户上翻后 | `detached = true` 期间完全不跟（`ChatScreen.kt:815`、`:885-886`），内容增长发生在视口下方，不拽人 | `docs/07-功能设计.md:1213-1217` |

### 52.6.6 字体缩放下的表现（边界，不额外适配）

| 系统字体缩放 | 行高（约） | 96 dp 内可见行数 | 处理 |
|---|---|---|---|
| 1.0× | 22.2 dp | 4.3 行 | 基准 |
| 1.3× | 28.9 dp | 3.3 行 | 可接受 |
| 1.5× | 33.3 dp | 2.9 行 | 可接受，仍能看到最近两句 |
| 2.0× | 44.4 dp | 2.2 行 | 可接受（"显示部分"语义仍成立） |

**不改 96 dp**：高度阈值一旦跟随字号，就会让"同一屏里不同字号用户看到的行数不同、块高也不同"，
而块高参与列表测量与锚点；字号适配属于全局排版规则（`docs/02-UI设计.md` §15），这里不单独处理。

## 52.7 「生成后自动折叠 / 自动展开」的时机与动画

### 52.7.1 时机

| 事件 | 时间点 | 依据 |
|---|---|---|
| 思维链收口（正常） | 首条正文 token 写入时 `noteBody()` 置 `reasoningDone = true` | `ui/chat/ChatViewModel.kt:2505-2515` |
| 思维链收口（无正文直接结束） | `status` 变 `DONE` / `STOPPED` / `ERROR` 时，`reasoningStreaming` 随之变 false | `ChatModels.kt:332` |
| 折叠开始 | **同一帧**，0 ms 延迟 | 见下方取舍 |
| 动画时长 | **220 ms**（`FoldAnimMs`） | `ui/common/Motion.kt:32-37`（与用户气泡、思考面板共用同一节奏） |
| 缓动 | `MotionEasing`（`FastOutSlowInEasing`） | `ui/common/Motion.kt:40` |

### 52.7.2 为什么是"立即"而不是"延迟 X ms"

| 方案 | 结论 |
|---|---|
| 延迟 300–500 ms | ❌ 与正文首字增长叠加：先收思考、再长正文，中间隔一段空白，观感是"跳两次" |
| 等整条回复 `DONE` | ❌ 用户已经读了一半回答，此刻收起思考会把下方内容整体上移一屏 |
| **收口当帧开始** ✅ | 与现有动画节奏一致；"正文出现 = 思考结束"本来就是同一条产品语义 |

### 52.7.3 展开的动画例外

| 场景 | 动画 | 理由 |
|---|---|---|
| 手动折叠（全文 → 标题行） | 220 ms | 高度变小，成本低 |
| 手动展开（标题行 → 全文）且内容 < 一屏 | 220 ms | 与折叠对称 |
| 手动展开且内容 ≥ 一屏 / 超过 4000 字 | **瞬时（0 ms）** | `animateContentSize` 会在 220 ms 内逐帧重排长文本，长思考上必然掉帧；用户真正想看的是"打开后立刻能读" |
| 策略自动展开（组合 C/E 的收口时刻） | 同上一行的规则 | 同上 |
| 策略自动折叠 | 220 ms | 与手动折叠一致 |

判定"是否长文本"用纯函数：`shouldAnimateExpand(charCount: Int, heightPx: Int, viewportPx: Int): Boolean`，
`charCount < 4000 && heightPx < viewportPx`。可 JVM 单测。

### 52.7.4 动画期间的滚动

- 自动折叠 / 自动展开**不设置 `detached`**：用户没有主动"停下来读"的意图，跟底逻辑继续工作
  （`ChatScreen.kt:1324` 的 `onFoldToggle` 只在手动点击时调用）。
- 手动点击仍然 `detached = true`（现状不变）：让被点的那一行留在原处，内容向下方展开。

## 52.8 视觉规范：思考块竖线变细

### 52.8.1 数值

| 组件 | 现在 | 改为 | 依据 |
|---|---|---|---|
| 扩展通道引导列竖线（`ThinkingGutter.kt:42`） | 2 dp | **1.5 dp** | 1.5 dp 在 3x（xxhdpi）下是 4.5 px、2x 下 3 px、1.5x(hdpi) 下 2.25 px，仍是一条清晰细线；1 dp 在 mdpi 只有 1 px，低 DPI 设备会时隐时现，因此 **1 dp 不取** |
| OpenAI 通道流式竖线（`ProcessPanel.kt:185`） | 3 dp | **1.5 dp** | 两条通道必须同宽，否则"细一点"只改了一半 |
| OpenAI 通道展开态竖线（`ProcessPanel.kt:226-228`） | 3 dp | **1.5 dp** | 同上；圆角由 `RoundedCornerShape(2.dp)` 改为线宽 / 2（0.75 dp），实际等价于全圆头 |
| 圆点 | 7 dp | 7 dp（不变） | 圆点是"正在思考"的锚点，直径不动；线细之后点线比由 3.5:1 变成 4.7:1，更像"点 + 引导线" |
| 圆点到线间距 | 4 dp | 4 dp（不变） | 高度节奏不变，避免整块上下位移 |
| 引导列槽宽 | 16 dp / 间距 10 dp / 正文缩进 26 dp | **全部不动** | 只缩线宽、不缩槽位 ⇒ 正文左缘零位移，`Text` 换行结果与现在完全一致 |
| 标题行 | 图标 15 dp、文字 15 sp、箭头 16 dp、内边距 8×4、左补偿 −8 dp | **全部不动**（RTL 补偿方向另修，见 §52.8.5） | 用户只提了竖线 |

### 52.8.2 颜色：等墨量换算

线条的"感知重量"近似 ∝ 宽度 × alpha。宽度减半时若 alpha 不变，OpenAI 通道的线会淡到几乎看不见
（现在本来就只是 0.16 / 0.21 的极淡色）。因此：

| 通道 | 现在 | 改为 | 说明 |
|---|---|---|---|

### 52.8.3 内边距与圆角联动

| 位置 | 处理 |
|---|---|
| OpenAI 流式尾巴 | 竖线用 `drawBehind` 画在 `x = 0`，`padding(start = 15.dp)` **不动** ⇒ 线变细后线与文字的间距由 12 dp 变 13.5 dp（多 1.5 dp，不可见级），正文左缘不动 |
| OpenAI 展开态 | `Box(width = 3.dp)` → `Box(width = 1.5.dp)`，紧随的 `Spacer(12.dp)` → **`Spacer(13.5.dp)`**，两者合计恒为 15 dp ⇒ 正文左缘不动 |
| 引导列 | 线仍居中于 16 dp 槽位（`centerX = 8 dp`），宽度变化只影响自身，槽位与文字位置全不动 |
| 圆角 | 线宽 / 2（`ThinkingGutter.kt:77` 的写法本来就是这样）；OpenAI 展开态的 2 dp 固定圆角改为 0.75 dp 或直接用同款 `drawRoundRect` |

**总原则：只缩线宽，不缩槽位、不动正文左缘。** 任一正文位置变化都会带来"整段重新换行"，对历史消息是纯风险。

### 52.8.4 深色模式与对比度

| 项 | 数值（估算） | 结论 |
|---|---|---|
| 浅色：`#1A1A1A × 0.32` 叠在 `#FFFFFF` | 约 `#B4B4B4`，对比度 ≈ **2.1:1** | 细线属于装饰性分隔，不承担"必须可辨识"的功能信息（文字本身在）；2.1:1 与 Material 的 `outlineVariant` 同级，可接受 |
| 深色：`#E8EAED × 0.42` 叠在 `#121212` | 约 `#64666A`，对比度 ≈ **2.9:1** | 深色下细线更容易"糊"，所以暗色 alpha 更高（自动由公式得出） |
| 引用块竖线 | 2 dp，颜色独立（`markdownQuoteBar`） | 思考线（1.5 dp）**比引用块更细**：思考是次要信息，引用是内容结构，粗细差异正好表达层级 |
| 代码块 | 只有底色、无竖线 | 无冲突 |

设备验收时必须**同屏对照两个通道**（发一条带搜索的扩展通道消息 + 一条普通 OpenAI 通道消息），
确认"看起来是同一种线"。若深色下 0.42 偏抢眼，把 0.6 的上限压到 0.36（深色线随之降到 0.36，只改一个常量）。

### 52.8.5 RTL 与其它方向性

| 项 | 处理 |
|---|---|
| 引导列位置 | `Row` 自动镜像 ⇒ 引导列到右侧；`Canvas` 内坐标不镜像但线本身居中，无需处理 |
| OpenAI 流式尾巴的竖线 | `drawBehind` 的 `x = 0` 是物理左缘；RTL 下需改为 `x = size.width - barWidth` ⇒ 与文字（`padding(start)` 已镜像到右侧）对齐 |

| 渐变遮罩 | 垂直渐变，与方向无关 |

## 52.10 与流式渲染的耦合

### 52.10.1 「生成中全部展开」为什么有风险

- UI 层的提交节拍是 **16 ms**（一帧一次）：`STREAM_THROTTLE_MS = 16L`（`ChatViewModel.kt:3869`，注释说明这是对齐官方 rAF 的刻意选择）。
- 现在的尾巴模式用 `visibleTailOf` 把每次排版压成"末尾 ≤ 1200 字符"的常数（`ProcessPanel.kt:251`、`:263-271`）。
- 「全部展开」意味着**整段文本参与排版**。1–2 万字的思考在 16 ms 节拍下逐帧重排，主线程必然掉帧；
  长文本还会触发单 `Text` 的命中测试上限（约 5 屏，`ui/chat/TextChunks.kt:8-14` 记录了实测）。
- 另外，列表锚点是 `(下标, 偏移)`（`docs/07-功能设计.md:1240-1242`），内容高度大幅跳动会放大锚点误差。

因此「全部展开」不是"把 `heightIn(max)` 去掉"这么简单，必须配套下面四条。

### 52.10.2 分段渲染（建议实现）

复用现有切块器：`textChunks(text, maxChars = 2000)`（`ui/chat/TextChunks.kt:28-45`，块数上限内很便宜）。
把全文渲染成**零间距的 `Column`**，每块一个 `Text`（同一个 `ProcessTextStyle` / `processText` 色）：

```
Column(verticalArrangement = Arrangement.spacedBy(0.dp)) {
    chunks.forEachIndexed { i, chunk -> Text(chunk, ...) }   // 前面块文本不变 ⇒ Compose 跳过重排
}
```

- **只有最后一块随流变化**，前面块的字符串一旦稳定就不再参与排版。
- 新增纯函数 `appendThinkingChunks(previous, text, maxChars)`：若 `text` 以 `previous` 拼接结果为前缀，
  只重切最后一块并追加，避免每帧对 2 万字做 `substring`。
- 末块的"打字机"平滑仍用 `rememberSmoothReveal`（`ui/markdown/SmoothReveal.kt:44-89`，按帧耗时自适应冷却，
  `MaxCooldownMs = 96`）；**只对末块做**，不对全文做。
- 逐帧预算已经由渲染层兜住：`adaptiveCooldownMs`（`SmoothReveal.kt:22-24`）会在慢帧时主动降速，
  `MarkdownText` 的设计说明见 `ui/markdown/MarkdownText.kt:113`。

### 52.10.3 重组 / 布局预算

| 做法 | 效果 |
|---|---|
| 流式中**禁用** `animateContentSize`（现状已如此：`ProcessPanel.kt:97-103`、`TimelinePanel.kt:87-91`） | 避免"动画追不上增量"把最新内容裁掉 |
| 溢出判定用 `derivedStateOf { contentPx > maxPx + 1 }` | 高度变化不必让整个 `ProcessPanel` 重组（现有实现是普通 `val`，`ProcessPanel.kt:155-156`；建议收进 `derivedStateOf`） |
| 折叠时**不建正文节点** | `when` 的 `else -> Unit`（`ProcessPanel.kt:116-121`），不创建 `Text`、不持有文字布局缓存 ⇒ 长会话里折叠态的内存与测量成本都是常数 |
| 不可见的流式条目 | LazyColumn 只会组合可见条目；用户上翻到读取历史时，末尾流式条目离开视口即停止组合（`MessageList.kt:281-295` 顶部原点 + 标准懒加载） |
| 超长降级 | `reasoning.length > 128_000` 时强制走「显示部分」并记诊断日志；生成后展开仍走 `LargeMessageBody`（`ProcessPanel.kt:118`、`TimelinePanel.kt:194-196`） |

### 52.10.4 与「流式锚点 / 跟底」的交互

| 情形 | 行为 |
|---|---|
| 全部展开 + 贴底 | 内容长在视口下方，锚点钉顶边 ⇒ 已显示内容不动；跟底循环把新内容带进视口（`ChatScreen.kt:884-899`） |
| 全部展开 + 用户上翻 | `detached = true`，不跟底；新内容继续在视口下方增长，不拽人 |
| 收口时自动折叠 | 高度变小、发生在正文上方；跟底会在一两帧内把视口带到位。**不置 `detached`**（自动行为不是"用户在读"） |
| 收口时自动展开 | 同上；长文本瞬时切换，避免 220 ms 内逐帧重排 |
| 手动点击 | `onFoldToggle()` ⇒ `detached = true`（`ChatScreen.kt:1324`），被点的标题行留在原处 |
| 搜索跳转 | 由搜索通道自己处理定位（搜索视口 `MessageList.kt:250-269`；停跟/复位 `ChatScreen.kt:815-823`）；展开思考是前置动作，必须在滚动定位**之前**完成，否则命中位置会算在旧高度上 |

### 52.10.5 「折叠时停止渲染」是否省电省内存

- **省布局/测量**：折叠态不建 `Text`，等于每帧省下一次长文本测量。
- **不省字符串内存**：思考文本在 `UiMessage.reasoning` 里，随会话加载常驻（`db/Entities.kt:149-150`、
  `data/Mappers.kt:48-49`），要省只能做分页/懒读，那是另一个工程（与 `LARGE_MESSAGE_CHARS` 分流同级）。
- **省绘制**：折叠态只画标题行 + 箭头，无渐变遮罩（遮罩只在溢出时创建离屏图层，`ProcessPanel.kt:166-174`）。

## 52.11 交互细节

| 场景 | 规定 |
|---|---|
| 点击标题展开 / 折叠 | 生成中不可点（五档一致）；生成结束后可点，写入手动 override，触发 `onFoldToggle` ⇒ 停止跟底，220 ms 动画 |

| 续写 | 不新增思考，不重置 override |
| 复制思考内容 | **不做**（Non-goal）。长按菜单复制正文（`ChatScreen.kt:1327`），思考正文当前也不可选中 |
| 搜索命中折叠内容 | 命中思考 ⇒ 自动展开 + 写入 `EXPAND`（升级现有 `MessageList.kt:1004-1006`），并保证展开发生在定位滚动之前 |
| 分享多选（`shareSelection.active`） | 思考标题**不可点**：需要把 `interactive` 之外再加"是否允许面板内点击"传进 `ProcessPanel` / `TimelinePanel`。现状只关了外层 `combinedClickable`（`MessageList.kt:654`），内层 `ThinkingHeader.clickable` 仍生效 |
| 选择文本态（`textSelection.isActive`） | 同上，不可点 |
| 朗读 | 只读正文，与本功能无关 |
| 图片生成轮 / 无思考轮 | 没有思考块，不显示任何展开控件 |
| 迟到思考 | 按生成结束策略；若策略为折叠，则显示标题行（与 `TimelinePanel.kt:142-151` 的"摘要后到"分支一致） |

### 52.14.3 验收步骤（建议按序执行）

1. **默认零变化**：升级安装（不清数据）→ 打开旧会话 → 生成中仍是 4 行尾巴，结束后仍折叠；与上一版录屏逐帧对比无差异。
2. **迁移**：把旧键 `auto_collapse_thinking` 置 `false`（数据层调试入口或临时改默认）→ 启动后生成结束为展开；生成中仍是尾巴。
3. **打开总开关**：设置 > 对话行为 → 打开「展开思考过程」→ 返回会话，见「生成中 / 生成结束」两组选项，当前值 = 全部展开 + 保持展开。
4. **组合 E**：生成一条长思考 → 生成中可见全文且随流增长；正文开始后仍保持全文；手动点标题折叠 → 220 ms 收起。
5. **组合 D**：改为「全部展开 + 自动折叠」→ 重发 → 正文出现瞬间思考收起（约 220 ms），点标题可再展开且不再自动收回。
6. **组合 C**：改为「显示部分 + 保持展开」→ 生成中 4 行窗口 + 溢出显示「展开全部」胶囊；首条正文时自动展开全文。
7. **手动优先**：在组合 D 下，正文出现后点开思考 → 继续生成到 `DONE` → 思考**保持展开**。
8. **逐条记忆**：展开某条旧消息的思考 → 滑出屏幕再滑回 → 仍展开；切会话再切回 → 仍展开。
9. **搜索**：搜索一个只出现在思考里的词 → 跳转后该条思考已展开且命中高亮，且不会被自动折叠。
10. **多选 / 选择文本**：进入分享多选 → 点思考标题 → 不展开（只响应勾选）。
11. **竖线**：两条通道各截一张 100% 放大图 → 竖线宽 1.5 dp，圆点 7 dp，正文左缘与上一版一致（叠加对比无位移）。
12. **RTL**：强制 RTL → 引导列在右侧、标题图标与正文左缘对齐、无横线错位。
13. **性能**：1.5 万字思考 + 全部展开 → `gfxinfo` / 帧耗时面板无持续掉帧（目标：掉帧率不高于同类正文流式）；折叠态无长文本测量。
14. **进程重建**：流式中强杀 → 重进 → 消息为中断态、按策略显示、正文与思考内容不丢（依赖既有 checkpoint）。

### 52.16.2 开放问题（评审时确认）

| # | 问题 | 本文建议 |
|---|---|---|
| 1 | 总开关关闭时，是否仍允许点标题展开思考？ | **允许**。关闭的语义是"默认不展开/自动折叠"，不是"禁止查看"；禁止查看等于把内容藏起来，用户无法自查模型想了什么 |
