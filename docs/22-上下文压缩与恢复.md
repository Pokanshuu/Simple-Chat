# 22 · 上下文压缩与恢复

适用于 SimpleChat v1.2.0（构建号 32）。已安装构建号 31 的用户可从同一发布页下载新版 APK 覆盖升级。

压缩只替换供后续请求使用的摘要，不删除或改写本地消息。通常保留最近约 6 条消息；
近期内容超过模型窗口一半时，按完整用户轮次缩小保留范围，至少保留最新一轮。
这些轮次不参与压缩，仍以完整内容发送。没有可纳入摘要的较早消息时，不发起摘要请求。

## 整段优先策略

1. 确定待压缩范围，包括原有摘要、较早的消息和可读的文本附件，不包含保留的近期轮次。
2. 找到与原文和请求配置匹配的检查点后，从上次完成的位置继续。已完成的批次直接参与最终摘要。
3. 按当前窗口和输出预算选择输入长度。待压缩原文能放进一次请求时就整段发送，否则按同一预算分批。
4. 整段输入被拒绝时，显示接口报告的上限（如有），手动继续后才分批。已在分批时，单批输入超限会自动缩小。超时、断流、空响应或截断都会停止本轮，用户可手动继续。

本地 token 估算不等同于服务端计数。服务端的输入限制只影响当前压缩，不改变模型的窗口配置。

## 摘要指导

只根据待压缩范围内的用户消息和原有摘要选择指导类型，不使用保留的近期轮次或助手消息进行分类。
对应的提示词参与检查点指纹，避免复用不匹配的进度。

- 创作：优先保留角色关系和情绪变化、视角、场景、时间线、未回收伏笔和写作约定。
- 技术：优先保留环境、复现条件、验证结果和后续步骤。
- 通用：类型线索不足时使用。侧重当前目标、约束、事实、进度和未决事项。

各类型都要求保留关键名称、数值和用户约束。历史指令只作为资料，不执行；压缩请求不配置搜索和网页读取工具。

## 分层压缩与恢复

先独立总结各批原文。各批完整摘要按时间顺序拼接后，若在 4,096 token、当前请求窗口的八分之一和 64,000 字符以内，直接使用拼接结果；超过预算时才请求模型合并。单条超长消息可拆分，但不会切断 Unicode 代理对。
只有完整响应通过校验后才推进源偏移并保存检查点。压缩时显示进度和停止入口，不显示部分摘要。
成功后检查会话、路径修订号和原摘要是否仍匹配，再替换正式摘要并清理检查点。

| 项目 | 行为 |
|---|---|
| 输入预算 | 预留请求窗口的 5%、系统提示、256 token 开销和输出预算。每批最多 1,500,000 个 UTF-16 字符 |
| 输出预算 | DeepSeek 官方已知大窗口型号参考 Harness 的 compaction-basic，为摘要请求预留 65,536 个输出 token，并在历史之后要求生成精简摘要。其他接口初始最多 4,096 token。输出截断后手动继续，该批可使用最多 8,192 token。小窗口最多使用窗口的八分之一 |
| 输入超限或 HTTP 413 | 将当前批次至少减半，并采用服务端报告的较小上限。同一位置最多自动尝试两次更小的输入 |
| 网络中断、429、临时服务故障、空输出、输出截断 | 停止并提示，已保存的进度可用于手动继续 |
| 请求等待 | 输入不超过 4,000 字符时单次最多等 45 秒，其他请求最多等 90 秒。使用 65,536 输出预算的请求共享整次压缩的 3 分钟时限。超时即停止 |
| 每次手动启动 | 最多 8 次请求、3 分钟。原文、缩批重试及合并共享上限。达到上限时若还有工作则暂停 |
| 鉴权、额度、模型或通道配置错误 | 直接提示，不反复缩批 |
| 无法收敛 | 摘要总长度未减少或超过 12 次合并层级时停止，保留原摘要 |

这些限制控制单次压缩的工作量，不修改模型列表、输入栏的 1M 窗口或正常聊天请求的配置。
请求长度的本地估算不等同于服务端分词结果；服务端拒绝仍需自适应恢复。

## 进度与数据保护

- 进度位于应用私有、排除系统备份的目录。文件只保存指纹、源偏移、已完成摘要及批次预算，不保存 API Key 或整份源对话。
- 每个会话最多保留一份进度。先同步临时文件，再原子替换，避免中断留下半份 JSON。
- 源内容、模型、接口、协议、认证配置或提示词变化后，旧指纹不匹配，重新开始。
- 损坏或过大的进度文件不复用。存储失败不使已完成的模型响应失效，但该部分工作可能需要重做。
- 成功完成、放弃正式摘要或删除会话时清理相应进度；删除全部会话时清理全部进度。
- 取消或关闭应用后不会自动发起新请求。用户再次选择压缩时恢复匹配的已保存进度。
- 整段发送时明确显示一次请求。分批时显示已完成的原文比例和实际请求次数。合并时单独提示原文已处理完毕。日志记录请求序号、输入长度、处理位置及失败类型。

## 文件 API 衔接

文件引用减少重复上传和请求体组装，文件内容被模型读取后仍会占用上下文。
压缩读取本地消息正文及文本附件，不重新上传已保留的长文本。

仅有远程 `file_id`、没有可读取文本的附件不能视为空文件。若这种附件位于待压缩范围内，
压缩会在发起摘要请求前提示补充正文，并保留原摘要和所有消息。
文件 API 需保留可供压缩读取的文本，或提供文本提取能力，才能压缩这部分内容。

## 验证边界

使用 912,000 个拉丁字符生成本地估算为 228k token 的样本。在构建号 31 模拟第一次整段请求超时，客户端共发起 21 次请求，包括 19 批原文和 1 次摘要合并。在修复版中，同样的超时只触发 1 次请求。模拟接口正常响应时，256k 窗口可以用 1 次请求完成该样本。单独使用 228,000 个中文字符的测试也只需 1 次请求。

在 Android 手机上，此前因摘要输出截断而失败的约 228k 长对话已成功压缩，并通过使用者的多次复测。该记录未采集服务端计费明细。

Android 模拟器分别验证了 OpenAI 和 Anthropic 两种协议的长度拒绝、取消、断点恢复和原文保留。测试使用本地响应，没有使用真实账户额度。真实服务的耗时、计费和摘要质量需要结合服务端记录判断。

构建号 28 的验收见[v1.1.6 预发布验收](24-v1.1.6预发布验收.md)。下方专项记录来自更早的独立快照，
不能用来验证整段优先策略或摘要指导。自动测试可以验证客户端请求和回退行为，
不能证明摘要语义无损。真实服务上的摘要质量和耗时尚未验证。

## 实机检查

1. 打开此前无法压缩的长对话，开始压缩。确认仅显示加载状态，界面仍可响应操作。
2. 中途停止后重新压缩，确认能继续完成；原消息数量和附件不变。
3. 完成后检查摘要中的关键人物、关系、限制、决定及未完成事项。
4. 继续发送一条消息，确认新回复可利用摘要及最近完整对话。
5. 修改待压缩原文或切换模型后重试，确认使用当前内容和配置。
