## 51.1 结论

先给结论，后文逐条展开依据。

| # | 议题 | 结论 |
|---|---|---|
| 1 | 现状 | 已有**只读的细滚动条**（`ScrollToBottom.kt:158-253`）：宽 3 dp、最小 28 dp、停手 700 ms 后淡出、完全不接触摸。**目前没有任何拖拽 / 胶囊实现**（对话页的滚动条只有这一处；仓库其余 `scrollbar` 字样是 Mermaid 关闭系统滚动条与变更记录） |
| 2 | 交互形态 | 在现有细条上叠加一档「可拖拽态」：滚动持续 ≥ 150 ms 后条带变粗到 6 dp，右侧 32 dp 成为命中带；手指竖向拖动即接管 |
| 3 | 定位方式 | **全列表比例映射**（滑块位置 → 行号），不是逐条步进、不是按住加速。跳转用 `scrollToItem` 的 O(1) 定位（`ScrollToBottom.kt:52-79` 的既有教训） |
| 4 | 胶囊 | 拖动开始 120 ms 后出现，显示**目标消息第一条非空文本行的前 13 个码点**；单行、最大 200 dp、跟随滑块、松手 120 ms 消失 |
| 5 | 跟手 | 滑块中心与手指位移 1:1；位置→行用冻结的快照映射，避免拖动中视口高度变化导致抖动 |
| 6 | 惯性 | **不做**。绝对映射已经给出精确落点，再加惯性会与「手指按着」的直觉打架 |
| 7 | 松手吸附 | **不吸附到行**（保留精确子行位置）；松手后 100 ms 内由拖拽绘制的滑块交叉淡回布局推导的滑块，消除亚像素差 |
| 8 | 点击轨道 | Ready 窗口内**点按轨道 = 跳转**（无动画）；静止且条带已淡出时不响应，避免吞掉右缘点击 |
| 9 | 长按 | **不做长按进入拖拽**（会与消息长按菜单抢同一个手势）；直接按在滑块上即可拖 |
| 10 | 触发 | 滚动 ≥ 150 ms → Ready；Ready 内触摸右侧条带 → 可抓；按在滑块上始终可抓（选择 / 搜索 / 文本选择 / 面板展开等禁用态除外，见 51.4.4）；不做「快速 fling」的速度判定（`LazyListState` 不暴露 fling 速度，见 51.5.3） |
| 11 | 淡出 | 细条沿用 700 ms；Ready 停手后给 900 ms 抓取窗口，再 200 ms 淡出；胶囊只在拖动期间存在 |
| 12 | 选择模式 | **禁用交互**（只留细条）。与既有消息索引一致：选择模式下索引手势本身就被禁用（`ChatScreen.kt:1974`） |
| 13 | 搜索 / 文本选择 / 输入面板 | 全部禁用交互，只留视觉。理由见 51.4.4 冲突矩阵 |
| 14 | 无障碍 | 滑块与胶囊是**装饰层**，不进 TalkBack 焦点；替代操作是列表自带滚动动作、消息索引（§34）、回到底部按钮（`ChatScreen.kt:2139-2195`） |
| 15 | 胶囊文本 | 复用消息索引的占位文案（`MessageIndexModel.kt:26-31`）；代码块显示「代码 · 语言」、表格显示「表格」，不渲染 Markdown |
| 16 | 数据/状态 | MVP **不改数据库、不改 ViewModel**：胶囊文本从 `messageRows`（`ChatScreen.kt:760-761`）现场取，加一个 64 条的小 LRU 缓存；仅在需要给 TalkBack 暴露动作时才加 ViewModel 辅助 |
| 17 | 设置开关 | **默认不加**。若评审要求：设置 > 对话 > 对话行为 > 显示，`scroll_bar_preview`，默认 `true`，DataStore 持久化（51.5.8） |
| 18 | 交付 | P0 拖拽定位（无胶囊）→ P1 胶囊 → P2 无障碍动作 / 设置开关 / RTL 矩阵；全文缩略图与「拖动惯性」明确不做 |

一句话：**把现有的 3 dp 细条升级成「拖动时变成可抓的胖滑块 + 一条只显示一行摘要的胶囊」，位置用整表比例映射一次到位，不引入惯性，也不碰其它导航手势。**

### 51.2.2 现有滚动体验的缺口

| 场景 | 现在怎么做 | 代价 |
|---|---|---|
| 几百条的长会话回看 3 小时前那句话 | 一路往上滑，或左滑开消息索引（§34，只列用户消息） | 索引只列**用户消息**，且是 36% 宽的面板（`MessageIndex.kt:86`）；想找 AI 回复里的一段仍要滑 |
| 1 万条消息定位到中间 | 只能滑或翻 | 细条只是指示器，看到位置也去不了 |
| 流式生成中上翻 | 手指一动就停跟随（`ChatScreen.kt:851-863`） | 停是停了，但没有「快速回到某处」的手段 |
| 多选 / 删除跨长会话勾选 | 现有设计禁用索引手势（`ChatScreen.kt:1974`），只能滑 | 本轮不改变该结论（见 51.4.4） |

### 51.2.3 平台与竞品惯例（只作方向参考）

- **长列表的「位置提示」模式**在 Android 生态里很常见：联系人列表的字母索引条、Material 组件库之外各类 fast scroller，都在拖动时给一个随手指移动的浮层，浮层内容是「当前位置的标签」而不是整段正文。本设计沿用这个模式，但**不引用任何具体产品的实现细节或数值**。
- 聊天类应用的拖动预览通常只显示一行摘要或时间，**不显示整条消息**：浮层会遮住正文，越大越难用。
- 触控目标上，Android 的通用建议是主要操作 ≥ 48 dp；滚动条属于「辅助定位控件」，命中带取 32 dp、拇指最小取 48 dp，是「可达」与「不占正文」的折中。

### 51.2.4 可直接复用的既有资产

| 资产 | 位置 | 复用方式 |
|---|---|---|

| 「跳转只量目标条目」的 O(1) 做法 | `ScrollToBottom.kt:52-79` | 拖拽定位只 `scrollToItem`，绝不 `scrollBy(超大值)` 去逐条测量 |

## 51.3 目标与 Non-Goals

### 51.3.1 目标

1. 任意长度的会话里，**一次拖动**从当前位置到目标位置；1 万条消息的会话目标耗时 < 1.5 s。
2. 拖动过程中能看到「这是哪条消息」：胶囊显示该位置消息第一条非空文本行的前 13 个码点。
3. 不破坏任何既有手势：列表滚动、长按菜单、双击选字、消息索引左滑、会话抽屉、系统侧滑返回、多选/删除、搜索、文本选择全部回归。
4. 零额外重组：拖动期间每帧成本与现有细条同量级；不出现新的掉帧。
5. 可被单独关闭 / 降级：无胶囊的 P0 版本本身可用。
6. 视觉全部取既有 token；深色、壁纸、主题色、字体缩放、平板宽屏都不出现"另一套语言"。

### 51.3.2 Non-Goals

| 不做 | 原因 |
|---|---|
| 全文缩略图 / 整条消息预览卡 | 会遮住正文、每帧要渲染 Markdown，成本与收益不成比例；一行摘要足够回答"这是哪条" |
| 逐像素的全列表高度映射 | `LazyColumn` 条目高度按需测量，拿到全表高度就必须逐条组合（`ScrollToBottom.kt:52-69` 的 ANR 根因），不可接受 |
| 拖动惯性 / 甩动 | 绝对映射已精确；惯性会让"松手后继续跑"，与滑块跟手矛盾 |
| 长按进入拖拽 | 与消息长按菜单、消息索引的既有手势冲突；Ready 窗口和直接按滑块已经够用 |
| 替换系统滚动条 / 全局开关到所有列表 | 只服务对话页；其它列表没有"找某一条"的语义 |
| 把消息索引面板与滚动条合并 | 索引是"按用户消息跳"，滚动条是"按任意位置跳"；面板是点击式，滚动条是连续式，交互模型不同 |
| 在选择 / 搜索 / 文本选择模式下启用 | 见 51.4.4，会吃掉这些模式里的点击与选区手势 |
| 胶囊显示消息序号 / token 数 / 时间 | 快速拖动时读数变化太快，读不出来；消息索引与操作栏已经承担这些信息 |

## 51.4 交互设计

### 51.4.1 状态与出现时机

四个可见状态（`Hidden` / `Thin` / `Ready` / `Dragging` 加一个 `Fading` 收尾）：

| 状态 | 进入条件 | 视觉 | 命中带 | 退出 |
|---|---|---|---|---|
| `Hidden` | 无滚动；或淡出结束 | 无 | 无 | 滚动开始 |
| `Thin` | `listState.isScrollInProgress` 为真且滚动不足 150 ms | 宽 3 dp、alpha 0.38、最小高 28 dp（= 现状） | **仅滑块**（32 dp 宽、竖向 ±12 dp） | 满 150 ms → `Ready`；停手 → 700 ms 后 `Fading` |
| `Ready` | 滚动持续 ≥ 150 ms；或刚从 `Ready` / `Dragging` 停手、尚在 900 ms 抓取窗口内 | 宽 6 dp、alpha 0.55、最小高 48 dp（120 ms 过渡） | 右侧 32 dp | 停手 900 ms → `Fading`；手指按住 → `Dragging` |
| `Dragging` | 在 `Ready` 命中带内**竖向**拖动越过 touch slop；或按在 `Thin` 滑块上拖动 | 同 `Ready`，滑块跟手；胶囊 120 ms 后出现 | 同上 | 松手 → `Ready`（停滚后计时）；指针取消 → `Ready` |
| `Fading` | `Thin` 停手 700 ms / `Ready` 停手 900 ms | alpha → 0（200 ms） | 无 | 结束 → `Hidden` |

关键数值与理由：

| 参数 | 值 | 理由 |
|---|---|---|
| 滚动持续多久进入 `Ready` | **150 ms** | 轻点列表或 1–2 帧的小滚动不弹交互态；150 ms 在 60 Hz 下约 9 帧，真正的滑动一定能跨过。`LazyListState` 不暴露 fling 速度（见 51.5.3），用"持续时长"代替速度判定，不引入逐帧采样开销 |
| `Thin` 停手淡出 | **700 ms** | 沿用现状（`ScrollToBottom.kt:152`），不改变既有观感 |
| `Ready` 停手抓取窗口 | **900 ms** | 比 `Thin` 多 200 ms：这是可抓的状态，多给一点时间让手指够到；再长会挡右缘点击 |
| `Ready` 出现 / 退出的形态过渡 | **120 ms / 150 ms** | 与 `MotionEasing`（`Motion.kt:39-40`）一致；短到不拖沓，长到能看出"变粗了" |
| 淡出 | **200 ms** | 沿用现状（`ScrollToBottom.kt:191`） |
| 胶囊延迟 | **120 ms** | 点轨道跳转时手指可能只停留几十毫秒，延迟避免胶囊闪一下；真正拖动一定超过 120 ms |
| 胶囊消失 | **120 ms** | 松手后立刻给"操作结束"的反馈 |
| 不遮内容边距 | 轨道上下各 **12 dp** | 与消息列表 `contentPadding` 的 12 dp 对齐（`ChatScreen.kt:744-749`），且避开顶栏与底部渐变带 |
| 不进入输入栏 | 轨道下界 = 布局高 − `inputAreaHeight` − 12 dp | 输入栏浮在列表上（`docs/02-UI设计.md:464-471` 的 §24.12）；滑块跑到输入栏后面就抓不到 |

### 51.4.2 命中区域与拖拽

| 项 | 值 | 说明 |
|---|---|---|
| 命中带宽度 | **32 dp** | 从内容列右缘向左 32 dp。≥ 24 dp 的经验下限；32 dp 在 360 dp 宽的屏上占 9%，不至于把正文点击抢走 |
| 竖向上、下界 | 轨道上下各内缩 12 dp | 见上表 |
| 滑块视觉宽 | 3 dp（`Thin`）/ 6 dp（`Ready`、`Dragging`） | 6 dp 仍在 16 dp 页边距内，不压正文 |
| 滑块最小高 | 28 dp（`Thin`）/ 48 dp（`Ready`、`Dragging`） | 48 dp 是"能按住"的最小高度；`Thin` 只接受"按在滑块上"这一种抓取，沿用 28 dp 视觉 |
| 滑块形状 | 全圆头（`CornerRadius(width/2)`） | 现状即如此（`ScrollToBottom.kt:203`） |
| 手指按在滑块上的判定 | 命中带内、且 `\|downY − thumbCenterY\| ≤ thumbHeight/2 + 12 dp` | 上下各放 12 dp 的容差，抓 28 dp 的小滑块不必像素级精确 |
| 跟手比例 | 滑块中心与手指位移 **1:1** | 拖动是绝对定位，不做加速曲线；1:1 最可预期 |
| 拖动方向判定 | 竖向位移 ≥ touch slop 且 `\|dy\| > \|dx\|` 才接管 | 右缘起手的**横向**左滑留给系统返回与消息索引（见 51.4.4） |
| 端点阻尼 | 超过首/尾后再拖最多 12 dp，位移乘 0.35 | 有"到边了"的反馈但不死硬；12 dp 约为一个字的行高 |
| 端点触觉 | 首次到达第 0 行 / 最后一行各一次 `HapticFeedbackType.TextHandleMove` | 项目内已有同款用法（`ChatScreen.kt:1729`、`Controls.kt:249`） |
| 拖动惯性 | **无** | 见 51.3.2 |
| 松手吸附 | **无** | 保留精确位置；不额外动画，胶囊淡出即可 |
| 点击轨道 | **Ready** 窗口内、按下后未移动即抬起 → 跳到该点（无动画） | "点哪去哪"；`Hidden` 不响应，`Thin` 只响应按在滑块上，避免吞右缘普通点击 |
| 按在滑块上 | `Thin` / `Ready` / `Dragging` 任意时刻 | 直接抓取：滑块中心与手指保持按下时的相对偏移，不跳位；这是"想拖时一定能拖"的确定入口 |
| 长按 | 无操作（不进入拖拽、不弹菜单） | 与消息长按菜单、索引手势不抢同一次长按 |

位置 → 行号的映射（**全列表比例映射**）：

```text
给定（拖动开始时冻结）：
  total         = 当前 LazyColumn 行数（messageRows.size）
  visibleSpan   = 拖动开始时视口在"行单位"下的跨度（沿用 ScrollToBottom.kt:238-239 的算法）
  scrollable    = max(0, total - visibleSpan)
  track         = 轨道像素高
  thumbH        = 当前滑块像素高（已按最小高钳制）
  travel        = max(0, track - thumbH)

滑块顶 → 行单位：
  unit  = scrollable * ((thumbTop - trackTop) / travel)      // 0 .. scrollable
  row   = floor(unit).coerceIn(0, total - 1)
  frac  = unit - row

行单位 → 滑块顶（现有绘制公式，ScrollToBottom.kt:255-258）：
  thumbTop = trackTop + travel * (unit / scrollable)
```

- `unit` 是"视口顶部所在的行单位"，所以胶囊显示的是 **`rows[row]` 对应的消息**，跳转后该行也正好落在视口顶部。
- `frac` 用于**行内二次修正**：目标行已测量出高度时，`scrollToItem(row, (frac * rowHeight).roundToInt())`，这样 20 万字一条的超高消息内部也能连续拖动，而不是一跳跳到它的顶部。
- 映射在按下时**冻结**（`total`、`visibleSpan`、`thumbH`、`track` 全部取快照）。拖动中流式结束可能新增 footer 行（`MessageListEntry.kt:18-24`），若不冻结就会边拖边改比例、滑块从手指下面跑掉。

### 51.4.3 胶囊（消息预览）

**内容规则**：`rows[row]` 取到 `UiMessage` 后，按"屏幕上看到的那条是什么"取文本。

| 消息情形 | 取文本 | 示例 |
|---|---|---|
| 用户消息有正文 | `content` 的第一个非空行，轻量去 Markdown | `# 你好` → `你好` |
| 用户消息纯图片 | 复用 `MessageIndexLabels.image` | `（图片）` |
| 用户消息多附件 | 复用 `MessageIndexLabels.attachments` | `（附件 3）` |

### 51.4.4 与既有手势的冲突矩阵

| 机制 | 触发条件 / 位置 | 判定 | 理由与实现约束 |
|---|---|---|---|
| 列表纵向滚动 | 任意位置 | **`Ready` 命中带内**归滚动条；**`Thin` 只接按在滑块上**；其余归列表 | `Hidden` 完全不消费 down；普通右缘起手滑动照常滚列表，只有先落到 3 dp 滑块上才会被接管 |
| 系统侧滑返回 | 屏幕左/右缘横向滑 | **让给系统** | 我们的接管条件是「竖向位移 ≥ slop 且 \|dy\| > \|dx\|」；横向位移先越阈值就放弃、一个事件都不消费 |
| 消息索引左滑（§34） | 任意位置左滑 | 方向不同，互不抢 | 索引手势在父节点 `Main` 遍只认左滑（`MessageIndex.kt:183-201`）；滚动条只在 `Initial` 遍、竖向后消费。横向时两者都不接管，保持现状 |
| 长按消息菜单 | 任意位置长按 | **不冲突** | 滚动条不在按下时消费事件；超过长按阈值仍未移动就放弃，长按菜单照常（51.5.3） |
| 双击 AI 回复选字 | 正文双击 | **不冲突** | 双击不产生竖向位移；`Ready` 窗口内双击若第二下落在条带内，也只是"点轨道跳转"，不会进入选字（该点在条带内，本来就不在正文上） |
| 单击空白收文本选择 | 选区激活时点空白 | **不冲突** | `dismissMessageSelectionOnTap` 只在 `Initial` 遍消费"短按抬起"（`MessageTextSelection.kt:50-75`）；滚动条不接短按，只有 `Ready` 轨道点按才消费 |
| 多选 / 删除模式 | `shareSelection.active` | **禁用交互**（只留细条） | 与消息索引一致：选择模式下索引手势整个不挂（`ChatScreen.kt:1974`）；条带内点击若跳转，会吞掉一次勾选。长列表勾选仍靠普通滚动，这是既有取舍 |
| 文本选择态 | `textSelection.isActive` | **禁用交互** | 选区手柄是独立窗口（`MessageTextSelection.kt:44-48`），列表滚动由系统选择逻辑接管；此时再叠一层拖拽只会抢手势。点空白退出后恢复 |
| 搜索态 | `vm.searchTarget != null` | **禁用交互** | 搜索会改 `contentPadding` 并把命中项居中（`MessageList.kt:250-283`），跳转定位是搜索的主导航；两类定位同时存在会互相改写视口 |
| 输入面板展开 | `panel != InputPanelState.NONE` | **禁用交互** | 面板展开时消息区盖了一层吃点击的透明遮罩（`ChatScreen.kt:1443-1455`），此时拖动滑块没有意义 |
| 会话抽屉 | 屏幕左缘右滑 | **不重叠** | 条带在右侧；宽屏常驻侧栏时条带贴的是内容列右缘（`RootScreen.kt:562` 的 `constrainContentWidth`），也不在窗口左缘 |
| 顶栏双击回顶 | 顶栏区域 | **不重叠** | 顶栏在消息区上方（`ChatScreen.kt:1225-1228`），条带只覆盖消息区 |
| 输入栏发送按钮 | 右下角 | **不重叠** | 轨道下界在 `inputAreaHeight` 之上（见 51.4.1） |
| 通知/返回键等 | 不涉及 | — | 拖动没有独立返回栈层，不拦截返回键 |

### 51.4.5 无障碍

| 项 | 结论 |
|---|---|
| 滑块与胶囊的语义 | **装饰层**：`Modifier.clearAndSetSemantics {}`，不进 TalkBack 焦点、不朗读；否则会与 `LazyColumn` 自带的滚动语义重复，TalkBack 会把"滚动条"当成一个额外可操作节点 |
| 触摸探索（TalkBack 开启） | 不启用条带命中：`AccessibilityManager.isTouchExplorationEnabled` 为真时只画视觉，不挂拖拽逻辑。理由：触摸探索下右缘条带会盖住内容节点，且用户用焦点遍历而不是直接摸位置 |
| 替代操作 | ① 列表自带的滚动动作（`LazyColumn` 默认提供）；② 消息索引面板（§34，`MessageIndex.kt:303-416`）可点击跳转；③ 「回到底部」按钮（`ChatScreen.kt:2139-2195`）；④ 顶栏双击回到顶部（`ChatScreen.kt:1225-1228`） |
| 与系统「无障碍滚动」的兼容 | 不修改列表的 `SemanticsProperties`，不在拖动时切 `userScrollEnabled`，系统的滚动动作始终有效；胶囊文本不 `liveRegion` 播报（拖动中连续播报无法听清），如评审要求 P2 再加"松手后播报一次当前位置" |
| 触控目标 | 拇指 48 dp、命中带 32 dp × 轨道高；虽然小于 48 dp 宽度，但它是**辅助**定位控件，主操作仍是全宽列表滚动，且只在 `Ready` 窗口内生效 |

### 51.5.2 状态机与动画参数

```text
滚动开始:  Hidden ──▶ Thin ──(滚动 ≥ 150 ms)──▶ Ready ──(按住 + 竖向拖)──▶ Dragging
                      │                          │  ▲                          │
                      │ 停手 700 ms               │  └─────── 松手 / 取消 ───────┘
                      ▼                          │ 停手 900 ms
                    Fading ◀─────────────────────┘
                      │ 200 ms
                      ▼
                    Hidden
```

| 过渡 | 属性 | 时长 | 曲线 | 实现 |
|---|---|---|---|---|
| `Thin → Ready` | 宽 3→6 dp、alpha 0.38→0.55、最小高 28→48 dp | 120 ms | `MotionEasing`（`Motion.kt:39-40`） | `animateFloatAsState` / `animateDpAsState` |
| `Ready → Dragging` | 胶囊 alpha 0→1 | 100 ms（延迟 120 ms 后开始） | `MotionEasing` | `AnimatedVisibility(fadeIn)` 或 `animateFloatAsState` |
| `Dragging → Ready` | 胶囊 alpha 1→0；宽高不变 | 120 ms | `MotionEasing` | 同上 |
| `Ready → Fading`（停手 900 ms） | alpha 1→0 | 200 ms | `MotionEasing` | 沿用现状淡出时长 |
| `Thin → Fading`（停手 700 ms） | alpha 1→0 | 200 ms | `MotionEasing` | 现状（`ScrollToBottom.kt:178-193`） |
| `Dragging` 内滑块位置 | 每帧 | 即时 | 无动画 | `graphicsLayer { translationY = … }`，不触发重组 |
| 松手后滑块重同步 | 100 ms 内从"拖拽位置"过渡到"布局推导位置" | 100 ms | 线性 | 两个 alpha 交叉或对差值做一次 `Animatable` |

`Dragging` 期间**不做**任何隐式动画（`animateFloatAsState` 会给跟手加延迟）；只有视觉宽度/透明度在状态切换时做 120–200 ms 过渡。

### 51.5.3 手势实现要点

**挂在哪**：挂在 `ChatScreen.kt:1971-1975` 的 `Layout` 父节点上，与 `messageIndexDrag` 同一层，**不挂在浮层兄弟上**。依据是 §34.7 的实测结论：带 `pointerInput` 的节点会把它的**兄弟**挡在命中路径之外；挂在父节点则列表、输入栏都是它的后代，谁也不挡（`docs/07-功能设计.md:1388-1405`）。

**顺序**：`.scrollBarDrag(...)` 放在 `.messageIndexDrag(...)` **之前**（更外层）。`Initial` 遍从外到内，滚动条先看到并消费；`Main` 遍从内到外，`messageIndexDrag` 看到 `change.isConsumed` 会立即 `break`（`MessageIndex.kt:178`），不会误开索引。

**手势骨架**（伪代码，落实为 `awaitEachGesture`）：

```kotlin
Modifier.scrollBarDrag(state, listState, rows, layoutDirection, fontScale) = composed {
    val scope = rememberCoroutineScope()
    onGloballyPositioned { state.setLayoutWidth(it.size.width) }
    pointerInput(state, rows) {
        awaitEachGesture {
            val down = awaitFirstDown(requireUnconsumed = false, pass = PointerEventPass.Initial)
            val hit = state.hitTest(down.position, layoutDirection)   // 纯函数
            if (!hit.enabled) return@awaitEachGesture                  // 条带之外 / 非 Ready / 被禁用

            var accX = 0f; var accY = 0f
            var claimed = false
            val trackPress = hit.kind == Track
            val anchor = if (hit.kind == Thumb) hit.thumbCenterY - down.position.y else 0f
            val downTime = down.uptimeMillis

            while (true) {
                val event = awaitPointerEvent(PointerEventPass.Initial)
                val change = event.changes.firstOrNull { it.id == down.id } ?: break
                if (change.changedToUpIgnoreConsumed()) {
                    if (!claimed) {
                        // 条带内的一次"按了没动"不要漏给底下的消息点击
                        change.consume()
                        if (trackPress) state.jumpToTrack(down.position.y)   // 点轨道
                    }
                    break
                }
                if (!claimed &&
                    change.uptimeMillis - downTime >= viewConfiguration.longPressTimeoutMillis
                ) {
                    break   // 长按：让位给消息长按菜单，不跳、不拖
                }
                accX += change.positionChange().x
                accY += change.positionChange().y
                if (!claimed) {
                    val slop = viewConfiguration.touchSlop
                    if (abs(accX) >= slop && abs(accX) > abs(accY)) break           // 横向让位
                    if (abs(accY) >= slop && abs(accY) > abs(accX)) {
                        claimed = true
                        change.consume()
                        state.beginDrag(
                            pointerY = down.position.y + accY, anchor = anchor,
                            viaThumb = hit.kind == Thumb,
                            listState = listState,
                        )
                        // 拖动开始 = 用户主动离开底部，与 DragInteraction.Start 同义（ChatScreen.kt:851-863）
                        state.onDetach()
                    }
                } else {
                    change.consume()
                    state.dragTo(change.position.y, listState)
                }
            }
            if (claimed) state.endDrag(listState)   // 内部判断 isAtBottom() 后恢复跟随
        }
    }
}
```

要点：

| 点 | 做法 | 原因 |
|---|---|---|
| `hitTest` 的启用规则 | `Ready`：整条 32 dp 命中带可命中，`kind` 为 `Thumb` 或 `Track`；`Thin`：只有滑块中心 ±（半高 + 12 dp）算 `Thumb`，其余落点返回 `enabled = false`；`Hidden` 或任一禁用态直接 false | 让 `Thin` 保留"直接按滑块可拖"，同时不抢右缘普通滚动与点击 |
| 不消费 `down` | 只在判定为竖向并越过 slop 后消费 | 消费 down 会让横向系统返回 / 长按拿不到事件；也让 `dismissMessageSelectionOnTap`（`MessageTextSelection.kt:50-75`）正常工作 |
| 短按 / 长按的收尾 | "按了没动"抬起时**消费 UP** 再执行轨道跳转；超过 `longPressTimeoutMillis` 仍未移动则直接放弃（不跳、不拖） | 不消费 UP，轨道点击会同时触发底下消息的点击 / 编辑；超过长按阈值说明用户要的是消息菜单，不是跳转 |
| 消费发生在 `Initial` 遍 | 父节点先于列表看到 | 越过 slop 的同一个事件就吃掉，`LazyColumn` 永远不会开始这次滚动 |
| 停 fling | 依赖「按下即停」的 `Scrollable` 标准行为；若施工实测不停，在 `beginDrag` 里 `scope.launch { listState.scrollToItem(row, offset) }` 顶掉同优先级的 fling | `MutatorMutex` 语义；`scrollToBottom` 已证明 `scrollToItem` 是 O(1)（`ScrollToBottom.kt:52-79`） |
| 不用 `userScrollEnabled = false` | 不切；拖动期间由消费保证列表拿不到事件 | 避免每次拖动开始/结束都重组整个 `LazyColumn`；如回归发现嵌套滚动泄漏再评估 |
| 不逐帧重组 | 拖动状态只在绘制 / `graphicsLayer` 里读；胶囊文本 80 ms 防抖后才写组合状态 | 与现有细条"状态一律在绘制期读"一致（`docs/11-实现记录.md:149-159`） |
| 状态订阅与节流 | `isScrollInProgress` 用 `snapshotFlow` 驱动 `Thin`/`Ready` 计时；目标行用 `snapshotFlow { targetRow }.distinctUntilChanged().debounce(80)` 推给胶囊；能用绘制期读的状态不用 `derivedStateOf` 包 | 避免把逐帧变化的状态提升进组合；`derivedStateOf` 只在"当前行"这种多输入派生值上用 |
| 手指取消 | `awaitEachGesture` 的 `finally` 里调 `endDrag(cancelled = true)`，保留位置、胶囊淡出 | 来电、返回手势等打断不应把状态卡在 Dragging |
| 与索引手势的关系 | 竖向拖动时索引手势看到 `isConsumed` 直接 `break` | `MessageIndex.kt:174-201` 已有该判断 |

**为什么不做「快速 fling 速度」判定**：`LazyListState` 的公开 API 没有 fling 速度；`interactionSource` 的 `DragInteraction.Stop` 也不带速度（`ChatScreen.kt:855-859` 只拿它判停）。自己逐帧采样 `firstVisibleItemIndex/offset` 做差分需要额外状态与阈值调参，且每帧都有读取成本。滚动持续 ≥ 150 ms 已经能把"轻碰"与"在滑动"分开，足够触发交互态。

**拖动与自动跟随**：自定义手势不经过 `listState.interactionSource`，不会产生 `DragInteraction`，所以必须显式补两件事：

1. 拖动开始 → `detached = true`（等价于 `ChatScreen.kt:854`）。
2. 松手后当 `listState.isAtBottom()` 且 `vm.searchTarget == null` → `resumeFollowing()`（等价于 `:855-859`，`resumeFollowing` 定义在 `:817-822`）。

不补第 1 条：流式跟底会在拖动下一帧把视口拽回底部；不补第 2 条：拖到最底部后不再跟随新内容。

### 51.5.4 位置 → 行映射与 O(1) 定位

```kotlin
// 纯函数（internal，JVM 可测）
internal fun unitForThumbTop(thumbTop: Float, trackTop: Float, travel: Float, scrollable: Float): Float
internal fun thumbTopForUnit(unit: Float, trackTop: Float, travel: Float, scrollable: Float): Float
internal fun targetRowForUnit(unit: Float, total: Int): Pair<Int, Float>   // row, frac
internal fun thumbHeight(visibleFraction: Float, track: Float, minThumb: Float): Float
internal fun endDampedDelta(raw: Float, overshoot: Float, maxOvershoot: Float): Float
```

施加定位（**每帧最多一次**，`collectLatest` 取消旧任务）：

```kotlin
private suspend fun applyTarget(unit: Float, total: Int, listState: LazyListState) {
    val (row, frac) = targetRowForUnit(unit, total)
    val visible = listState.layoutInfo.visibleItemsInfo
    if (visible.none { it.index == row }) {
        listState.scrollToItem(row, 0)          // 第一段：O(1)，只量目标行
    }
    val height = listState.layoutInfo.visibleItemsInfo.firstOrNull { it.index == row }?.size
    if (height != null && frac > 0f) {
        listState.scrollToItem(row, (frac * height).roundToInt().coerceIn(0, height - 1))
    }
}
```

- **不逐条滚动**：`scrollBy(超大值)` 会按需逐条测量，几百条就是十几秒 ANR（`ScrollToBottom.kt:52-69` 的真实事故），绝对不能用。
- 目标行未测量时先 `scrollToItem(row, 0)`，下一帧读到真实高度后再补 `frac` 偏移；两段都是 O(1)。
- 拖到最底（`unit ≥ scrollable − 0.5`）时直接调 `scrollToBottom()`（`ScrollToBottom.kt:70-79`），不按 `frac` 定位：最后一条可能高过视口，按行内偏移会停在半路，或把底部内边距顶出来露出空白。
- 拖动过程中用户持续移动时用 `MutableSharedFlow(extraBufferCapacity = 1, onBufferOverflow = DROP_OLDEST)` + `collectLatest`：永远只处理最新目标，旧的 `scrollToItem` 被取消。
- `targetRow` 变化才更新胶囊文本（并 80 ms 防抖）；`frac` 变化只更新滑块位置，不触发文本计算。

### 51.5.5 胶囊文本提取与缓存

- `scrollBarPreview(message, labels)` 是纯函数：输入 `UiMessage` + `MessageIndexLabels`，输出 ≤ 13 码点的字符串。**不碰 Android Resources**（labels 由调用方注入，沿用 `MessageIndexLabels` 的 lambda 设计，`MessageIndexModel.kt:20-31`）。
- UI 侧 `remember { LruCache<String, Pair<String, String>>(64) }`：key 为消息 id，value 为 `(content 引用, 预览)`。命中条件：`cached.content === message.content`（字符串引用比较，O(1)）。不相等就重算。流式中的尾条内容每批 token 都变，引用不同 → 不缓存，直接算（只有这一条，成本可忽略）。
- 失效：会话切换 / `pathRevision` 变化（`ChatViewModel.kt:233`）/ `messageRows` 整体变化时 `clear()`；消息删除后 id 不再出现，LRU 自然淘汰。
- 单次成本：扫描 ≤ 240 码点 + 一次首行清洗，远小于 0.1 ms；80 ms 防抖下最多 12.5 次/秒。

### 51.5.6 性能预算（1 万条会话）

| 项 | 预算 | 依据 |
|---|---|---|
| 每帧绘制 | 1 个圆角矩形 + 1 次 `graphicsLayer` 平移（胶囊） | 现有细条已经是"只画一个圆角矩形"（`ScrollToBottom.kt:202-251`） |
| 每帧重组 | **0 次**（胶囊文本变化时才重组，≤ 12.5 次/秒） | 状态读在绘制/图层 lambda 内 |
| 每帧测量/布局 | 0 次（胶囊只在文本变化时量一次高度） | 不用 `BoxWithConstraints` / `offset(Dp)` —— 上一轮正是它们把滚动拖垮（`docs/11-实现记录.md:149-159`） |
| 拖动定位 | 每帧 ≤ 1 次 `scrollToItem`，O(1) | `ScrollToBottom.kt:52-79` |
| 摘要计算 | ≤ 0.1 ms/次，≤ 12.5 次/秒 | 240 码点预扫 + LRU 64 条（约十几 KB） |
| 目标 | 拖动时 Janky 不高于基线 2.4% 的 +1 个百分点；帧 P90 ≤ 16.6 ms | 基线见 `docs/10-CHANGELOG.md` 的 v0.9.0-beta.7 行（当前工作区约 :365） |
| 验证 | 400 条合成会话沿用 `HistoryScrollRegression.kt:26-37` 的构造；1 万条用 `LargeMessageUiRegression` 同款思路 | 设备回归命令见 51.7.2 |

### 51.5.7 数据结构改动建议

**MVP：零改动。**

- 目标行 → 消息已有现成映射：`messageRows[row].message`（`MessageListEntry.kt:4-11`、构造见 `:15-26`；`ChatScreen.kt:760-761` 已持有 `renderedMessages` 与 `messageRows`）。

**可选（P2，仅当要给 TalkBack 暴露"跳到最前/最后"时）**：

| 改动 | 位置 | 说明 |

### 51.8.2 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 自定义手势抢右缘普通滚动 | 中 | 用户觉得"右边缘滑不动" | 只在 `Ready` 窗口内接管整条命中带；`Thin` 只认按在 3 dp 滑块上；`Hidden` 完全不消费；#9 专项用例 |

| 每次拖动 `scrollToItem` 造成测量抖动 | 中 | 卡顿 / 跳位 | `collectLatest` 只保留最新目标；每帧最多一次；行内二次修正读实测高度；沿用 `HistoryScrollRegression` 做帧对比 |
| 超高单条消息内拖动比例过慢 | 中 | 用户以为失灵 | 行内 `frac` 二次修正；胶囊持续显示同一条摘要；20 万字专项用例 |

| 胶囊遮挡/闪烁 | 中 | 观感差 | 200 dp 上限、120 ms 延迟、80 ms 防抖、松手即消失；真机走查 #3/#4/#5 |
| 性能回退 | 低 | 违背项目底线 | 零重组设计 + 绘制期读状态；设备帧指标对照基线 |

## 51.9 待确认问题

1. **触发窗口是否够用**：`Ready` 只在"滚动持续 ≥ 150 ms"后出现，停手后保留 900 ms。若实际使用中用户更希望"条带一出现就能拖"（哪怕慢滚），把 150 ms 改为 0 即可，但会牺牲右缘普通滚动的容错。是否按 150 ms 起步？
2. **胶囊内容是否要带位置感**：当前只有一行摘要，没有"第 N/M 条"或百分比。快速扫过时摘要本身在变，是否需要一个固定不变的位置读数（会加宽胶囊）？
3. **多选模式是否真的不需要快速定位**：本轮沿用既有取舍（`ChatScreen.kt:1974` 在选择模式禁用索引手势），滚动条也一并禁用。若实际多选跨几百条很痛苦，可改成"多选下只禁用点按轨道、保留拖拽"，需要产品确认。
