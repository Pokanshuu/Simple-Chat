### ⚠️ 多语言验收踩到的坑：`Res` 不能用 Application 的 resources

**现象**：切到 English 后，新建对话的标题仍是「新对话」，AI 起的标题也还是中文。

**根因**：`Res.get` 取的是 **Application 的 resources** —— base context 在**进程启动**
时按当时语言包好一层就不再动，而设置里换语言只 `recreate()` Activity、不重建
Application。于是 `Res` 这条路（兜底标题、起名提示词、预设、导出模板、报错…）
**永远停在启动时的语言**；界面标签反而都对（它们走 Activity 的 `stringResource`，
随 recreate 重包）—— 症状因此很"半截"，只错非 composable 的那半边。

**修法**：`LocaleHelper.localizedContext()` 按**当前语言**从**未包装的**原始 base
现算 context（按档缓存、换语言自动失效）；`Res` 改走它。⚠️ 基底必须用未包装的
那份 —— 往已包装的 Application base 上再包，"跟随系统"的判定会读到启动时的 locale。

**教训**：换语言 = 只重建 Activity 时，**所有非 composable 取词路径**都得自己跟着走；
单测测不到（JVM 没有 Resources），只能靠真机验收 —— 这类"半截翻译"必须列入验收清单。

**同因的第二坑：`recreate()` 会把导航状态丢掉** —— 换语言的瞬间人被送回对话页。
`RootScreen` 的 `route`、`SettingsScreen` 的 `page` 都是普通 `remember`，重建即复位；
改 `rememberSaveable` 后跨重建存活，切语言就停在设置页原地（三种切换方向均真机验过）。

**同因的第三坑（真机：澎湃 OS3）：`recreate()` 后状态栏不沉浸**，退出重进又正常 ——
系统在重建 / resume 前后把窗口属性重设回它那套（`decorFitsSystemWindows`、
对比度兜底），落在最后一次 `SideEffect` 之后，而设置页是静止的、没有下一次重组
来纠正。解剖 activity-1.13.0 字节码确认 `enableEdgeToEdge` 各 API 档都做三件事：
`setDecorFitsSystemWindows(false)`、系统栏上色、`StatusBarContrastEnforced = false`；
修法是把施加抽成函数，在 **`ON_RESUME` 再施加一遍**（重建 / 切后台 / 返回都必然
经过它）+ 一帧 `decorView.post` 补刀，并显式补写 `isStatusBarContrastEnforced = false`。
⚠️ **真机实测该修法无效** —— 系统的重设比 resume 更晚；已降级为已知问题记在
`TODO.md`「🐛 已知问题」（含后续可试方向），冷启动兜底、影响小，用户接受。

**四、滚动条的性能**

滚动条原先**每帧重组一次**：`layoutInfo` / `firstVisibleItemIndex` 读在组合里，
滚动一帧变一次；再叠上 `BoxWithConstraints`（`SubcomposeLayout`，每次测量都要
子组合一次）与 `offset(Dp)`（每帧重新布局），这根 3dp 的小条把滚动拖到卡顿
不可用。改成整条滑块只是一段绘制 —— `drawWithCache` 里画一个圆角矩形，滚动
状态一律在**绘制期**读，不重组、不测量、不布局。

> **通用规则**：随滚动逐帧变的状态（`layoutInfo` / `firstVisibleItemIndex` /
> `isScrollInProgress`）一律别读在组合里 —— 放进 `drawBehind` / `graphicsLayer`
> / `layout` 的 lambda，才只让对应阶段失效。

### 本轮完成（v0.9.0-beta.6）—— 系统栏沉浸 + 主题色 + 三笔收尾

**设计细节写在 [`docs/02-UI设计.md`](02-UI设计.md) §33**，这里只留"做了什么 + 为什么"。

**一、系统栏改成跟 App，不跟系统**（§33.1）

- `enableEdgeToEdge()` 只管"布局伸到系统栏后面"，系统栏的**样式与明暗**它都按系统来。
  本 App 的主题模式是独立的 → "系统浅色 + App 深色"时状态栏图标与「小白条」会反色。
- 读 AndroidX 源码确认（不是猜）：targetSdk ≥ 35 走 `EdgeToEdgeApi35.setUp`，其中有
  `window.isNavigationBarContrastEnforced = (navigationBarStyle.nightMode == MODE_NIGHT_NO)`；
  而默认导航栏样式 `auto(浅遮罩, 深遮罩)` 的 `nightMode` 是 `MODE_NIGHT_AUTO`（= 0）
  → 这句被设成 **true**：**系统获准往导航栏后面加半透明遮罩**。手势导航下就是那条
  "底部跟界面对不上"的带子（金标联盟「导航条适配」说的割裂感）。
- 修法（`ui/theme/SystemBars.kt` 新增）：两个系统栏样式显式透明 + `detectDarkMode` 用
  **本 App** 的深浅 + `isNavigationBarContrastEnforced = false`（API 29+）+
  `navigationBarDividerColor = 透明`（API 28+，MIUI 还会画一条 1px）。
- **API 29 以下保留库自带遮罩**：那时的三键导航键画在导航栏底色上，全透明会让它消失。
- 新增 `LocalIsDarkTheme`，主题一改就重设。实测：系统浅色 + App 深色时窗口的 `vsysui`
  由 `LAYOUT_STABLE LIGHT_STATUS_BAR LIGHT_NAVIGATION_BAR` 变成 `LAYOUT_STABLE`。

**二、主题色**（§33.2）

- 设置 → 个性化 → **主题色**：七色（蓝/绿/红/粉/紫/棕/灰），点开弹一排色块，
  选中的那个外面套一圈描边（用 `onSurface`，深色下也看得见）。
- 浅 / 深各一档：深色那档不是"把浅色调亮"，是单独挑过的（同色相在近黑底上要够亮）。
- **浅底派生而不是手写**：选中态填充与用户气泡 = `lerp(页面底色, 主色, 0.16/0.22)`。
  7 色 × 2 档 = 28 个手调色值既难保证同色相、改一个还要改一片。比例照原蓝色反推，
  **默认观感不变**。
- 范围只限品牌色一族：页面底色、正文颜色、功能色（危险 / 警告）都不动 ——
  换主题色不该把"有错误"这类语义色也换掉。

**三、折叠块展开的锚点**

- 顶部为原点下，展开**本来就不动锚点**（锚钉条目顶边，展开是往下长）——
  真正把标题顶走的是**自动跟底**：展开让内容变高 → `canScrollForward` 变真 →
  跟底那一帧把整屏往上推。修法：展开/收起时复用 `detached`（"别跟底"）。
- 顺带清掉 `onFoldResize(Δpx)` 那套死代码（`UserBubble` / `ProcessPanel` 各一份
  `foldResizing` / `lastHeight` / `foldTouched` / `onSizeChanged` / `LaunchedEffect`）：
  它是"底部为原点"时代的开环补偿，换顶部为原点后调用方传的已经是 `{}`。

**四、流式滚动平滑**

- ① 思考尾巴**只排版看得见的那几行**：原来把整段思考 `unbounded` 交给 `Text` 排一遍
  再裁到 96dp（显示 4 行、每 50ms 排几千字）。现在只取末尾 1200 字，并优先从换行处切
  （换行是逐行推进的，从硬换行后开始切，每一行与整段渲染逐字一致）。
- ② 正文采样 80ms → **50ms**，跟数据层 `STREAM_THROTTLE_MS` 同频。这道闸从"降频"
  变成"不加频"，真正扛开销的是分块。
- ④ 跟底从"每帧 `scrollBy(1e9)` 一把跳到位"改成"**每帧吃掉剩余距离的 70%**"。
  代价：最新一行滞后不到一行（刻意接受）。
- ⚠️ ④ 连带必须改的判据：原来的"用户离开底部"是 `isScrollInProgress && !atBottom`，
  它成立的前提是跟底**每帧落到**底部。改成逼近后不再落底，一次误判就会**卡死**
  （新字全停在屏外）。现在改为**手指拖动**置位，解禁只留三条明确的路：
  手势停稳后落在底部 / 点「回到底部」/ 发消息·重新生成·重试·编辑重发·新对话。
  （中途一度写成"在底部就清"，而锚点与折叠**正是在贴底状态下**置位的、布局要下一帧
   才落定 → 刚设的标记被当场撤销 → "切中间那条的分支又跑到最底下"。已修。）

**五、回到底部按钮**

- 生成中在按钮**外圈**转一圈进度环（淡色轨道 + 约 90° 实色弧，1.1s/圈）。
- 环画在 32dp 节点**外面**（`DrawScope` 不裁剪）→ 节点尺寸不变，环出现/消失按钮不挪；
  且它必须是按钮的**后一个兄弟**才能压住按钮边缘（画在下面会被不透明的底与描边吃掉）。
- 显隐判据加上 `detached`：只看 `!atBottom` 会在跟底过程中以内容到达的节奏来回翻
  （每来一批字变真、被跟底吃掉又变假）→ 按钮**不停闪烁**。

**六、输入栏与三处"借错语义"**（§33.3）

- 输入栏第二行图标统一为**黑**（原为灰，和同一行的 `⊕` 不一致，看着像禁用）；
  激活态改为「淡底 + **同色描边** + 同色内容」。
- `Palette` 图标归给主题色，外观改用新加的 `Contrast`（半实心圆）。
- 「压缩上下文」去掉写死的 `selected = true` —— `selected` 的语义是"该选项当前是开着的"，

### 本轮完成（v0.9.0-beta.5）—— 方向推翻 + 流式渲染的两处根因

**设计细节写在 [`docs/07-功能设计.md`](07-功能设计.md) §32**，这里只留"做了什么 + 为什么"。

**一、推翻 beta.2 的「底部为原点」**（§32.1）

- 列表改回 `reverseLayout = false`（顶部为原点）：锚点钉条目**顶边**，流式消息长高
  发生在**视口下方** → 屏上内容纹丝不动、**零补偿**。
- beta.2 给的理由里两条是错的：① "流式追加不拽人" —— 底部为原点下锚点钉**底边**，
  流式消息在底边继续长高就把已显示内容整体往上顶，实测 **0.5s 滑走 861px 且手拦不住**
  （= 用户从第一轮起一直报的"文字自己往上走"）；② "贴底 = `index==0 && offset==0` 是
  结构性质" —— 只在"尾部恰好是下标 0"时成立，消息比屏高、用户滚到中段就不代表
  视口相对**内容**的位置。只有"打开就在最新"这条是真的，而它不需要方向来换。
- 落点：`LazyListState(firstVisibleItemIndex = Int.MAX_VALUE)` —— **布局参数**而非一次滚动，
  **首帧**就在底部。
- 代价说清：贴底跟随不再免费（新字长在视口下方），改为**逐帧循环** `scrollToBottom()`，
  让位给手指（`isScrollInProgress`）与路径重建（`pathRebuilding`）—— 与官方
  `StreamingAutoScrollEffect` 同构。

**二、「向上滑有概率飞到很上面」的根因：库的 `Markdown` 是异步解析**（§32.2）

- 字节码取证：`MarkdownKt → rememberMarkdownState`；`MarkdownStateImpl → Dispatchers,
  parseMarkdownFlow`；`State$Loading / State$Success`。
- 逐帧探针实测：同一条消息进视口时高度 **2946 → 13431 → 23355px**，第一次只有真实高度的
  约 **10%**（真实 ≈1.7px/字，第一次 ≈0.17px/字，都严格跟字数成正比）。
- 而 LazyList 锚点的偏移是**内容里的绝对像素位置** → 内容一长锚点就漂。
- 修法：库的**同步**入口 `parseMarkdown()` + `Markdown(state = …)` 重载
  （高度第一次测量就是真实的、`Loading` 那一帧根本不存在）+ **按块文本缓存**（上限 256，
  滚出滚回不重解析）+ 列表一变就**后台预热**（从最新一条往前 —— 那一头先被看到）。
- 副产品：`Markdown` 的异步解析协程不再随每次组合启动，流式期间少一条后台解析流。

**三、「切版本」锚点收敛成一条规则**（§32.3）

- 用户对"底部"的定义是**操作栏可见**，而操作栏在条目**末尾** → 锚**目标末尾在屏上的 y**。
- 分两段（新高度要等这一帧布局才知道）：① 第一帧 `requestScrollToItem(target, 0)`
  只求**不越界**（顶边贴视口顶边，因此目标必留在视口里）；② 下一帧拿**新高度**
  `scrollToItem(target, 新高度 - endY)` 精确归位；目标若不在可见条目里，先拉进来再算。
- 前面几版各错一次，反例全记在 §32.3：**有符号 offset**（负值把视口甩到 `fvi=0`）、
  **"列表末尾"**（兄弟版本可能自带下游 → 跳到对话末尾）、**"目标的下一条"**
  （下游被丢掉时那条不存在 → `coerceIn` 夹回目标自己 → 摆到目标顶边）、
  **旧高度估偏移**（新版本短得多时目标整个被推到视口之上）、
  **修正只在可见条目里找目标**（目标已不在视口 → `size=null` → 直接放弃）。
- **「重新生成 / 重试 / 编辑并重发」一律不锚**：把这条换成一条**空的**流式回复，
  高度先塌到十几像素（实测 18355 → 12），原来的阅读位置在新内容里根本不存在 ——
  硬锚只会往上跳；而且用户按它们就是想看新回复，跟到底部才对。
- `detached = true` 只在**切版本 / 删除**时置位（用户在看/对比某一条，不在等新内容）；
  回到 `atBottom` 自动恢复跟随 —— "切最后一条"和"切中间那条"因此各归其位。

**四、性能与清理**

- `MarkdownBlockView`：块的参数收窄成 `(String, Modifier)`、样式从主题读 —— 否则
  Compose 的**跳过判定**失效（样式对象每次重组都是新的、参数永不相等），
  每个块每帧都要重解析 + 重排版，分块渲染（只重解析尾块）就白做了。
- 移除全部临时埋点（`SCScroll` / `SCAnchor`）与 `MessageList` 里两个死 import。

**教训（值得单独记）**：位置类 bug **不要靠推理**。前面七轮每轮换一个假设、每轮都错；
按用户建议换成探针（记录"谁写了什么、写之前之后各是多少"）之后，**一次**就把两个根因
同时摆出来了。

## ✅ 架构升级：槽位模型 → **parentId 树**

**起因**：编辑重发要删掉下游。用户问「不应该有个新分支吗」—— 对，是我当初选错了模型。

**槽位模型（旧）做不到分支**：消息的身份是「第几位」，slot 2 不知道自己是基于
slot 1 的哪个版本生成的。上游一换版本，下游就无法判断该不该跟着变 ——
唯一自洽的处理就是删掉。**它不是"没做分支"，是模型里没有分支这个概念。**

**树模型（新）**：身份是 `parentId`。

```
        u1 ── a1 ── u2 ── a2
         │            │
         │            └── a2'   ← 在 u2 上「编辑并重发」
         └── a1'                  ← 在 u1 上「重新生成」
```

- 当前对话 = 从根沿 `active` 走到底的**路径**
- 编辑重发 = 挂一个新兄弟上去；**旧兄弟连同它整棵子树原样留着**
- 切版本 = 换一个兄弟 → **整段下游跟着换**

### 改动
- [x] `MessageEntity`：`slotIndex` → `parentId`（`""` 为根哨兵，让唯一索引生效）
- [x] `MessageTree`：`activePath` / `siblingCounts` / `subtreeIds` / `lastSibling`，
      纯函数 + **9 项单测**（含"编辑后旧子树仍可达"「坏数据不死循环」）
- [x] `MessageDao` / `ChatRepository` 全部重写；删除 = 删整棵子树
- [x] `CompactionEntity`：`fromSlotIndex/toSlotIndex` → **`throughMessageId`**
      （分支一切换"第几条"就变了，id 才稳定；不在路径上就说明是别的分支留下的，忽略）
- [x] **所有增删改完成后统一 `reloadPath()`** —— 不再在内存列表上原地修补，
      彻底消灭顺序 bug
- [x] 备份格式 v2（语义变了，v1 不兼容）
- [x] DB version 1 → 2
- [x] **「保存并发送」的二次确认删掉了** —— 树模型下它不再删任何东西
- [x] 顺带修：删掉当前正在看的会话后，界面不回到空态
      （`ensureConversation()` 兜底 + 删除时同步重置）

**真机验证**：发送 `ALPHA` → 编辑成 `BETA` 重发 → 用户消息 `2/2`、
回复 `BETA`；切回 `1/2` → `ALPHA` **和它的回复**整条回来。

## §41 · 对齐 deepseek-ai/chat-demo（v1.19）

### 一、为什么是「加一条通道」而不是「换协议」

官方 demo 的全部扩展能力（联网搜索、链接阅读、正文引用、服务端标题、时间地点提醒）
只长在 **Anthropic 兼容**的 `POST /anthropic/v1/messages` 上，OpenAI 兼容的
`/chat/completions` 拿不到。而本项目的主力覆盖面恰恰是后者（自建端点、OpenCode Go）。

于是双通道并存：

| 通道 | 端点 | 产出 |
|---|---|---|
| `OPENAI` | `/chat/completions` | 正文 + `reasoning_content` + 三档 `reasoning_effort` |
| `ANTHROPIC` | `/anthropic/v1/messages` | 块级回复（思考 / 工具 / 网页 / 带引用的正文） |

`AUTO` 的解析规则（`ApiStyle.resolve`）刻意**看端点、不看模型名**：

- `provider = DEEPSEEK` **且** Base URL 仍含 `api.deepseek.com` → 扩展通道
- 其余一律 OpenAI 兼容

理由：`provider` 只是个"预设"，用户可以把它改成自家网关。那种情况下扩展端点并不存在，
猜过去就是**每一次请求都 404**；而"没拿到搜索能力"只是少个功能。两害相权取轻。
需要扩展能力而端点不是官方域时，在设置里把通道显式设成 Anthropic。

### 二、块级回复怎么落库

`messages` 加两列（v7，显式迁移）：

- `timeline`：`List<ReplyBlock>` 的 JSON。空 = 没有结构（OpenAI 通道、老数据）
- `stopReason`：`end_turn` / `max_tokens` / `tool_use` / `refusal`

**为什么必须存结构而不是只存正文**：翻回三天前的对话，「已阅读 6 个网页」和正文里的
角标都得还在。只活在内存里等于每次重开都丢。

**为什么正文仍然单独存一份**：复制、导出、全文搜索、token 估算全都读 `content`。
它由累加器从全部 text 块拼出来（`ReplyAccumulator.answer`），不会与 `timeline` 分叉。

### 三、请求侧的三条硬规则（逐条对齐官方协议）

1. **历史里的思考不回传**，只有续写时保留**本轮**那一条（含签名）
2. **搜索调用与搜索结果不回传**；读链接的调用 + 结果**原样回传**，`signature` 一个字节都不能动
   （服务端靠它解密恢复网页正文）
3. **缺少签名的读链接整对丢弃** —— 传一半的结果块只会让服务端 400

外加 `tools`：`deepseek_read_url` 始终声明（用户贴了链接就该被读），
`deepseek_web_search` 受输入栏开关控制。

### 四、引用角标为什么不直接写 URL

正文里的角标先写成**页内锚点** `[ⁿ](#cite-N)`，渲染前才由 `resolveCitationLinks`
换成真实 URL。原因很实在：markdown 的链接目标遇到 `)`、空格、中文会被截断，
一次搜索结果就能把整段正文的排版搞乱。占位 + 替换是唯一稳的做法。

### 五、继续生成只做扩展通道

`ContinuePolicy` 五条否决：不是活跃路径最后一条 / 流式中 / 没有时间线（= 不是扩展通道）/
被安全拒绝 / 用过服务端工具。最后一条来自官方协议 —— 带工具块的轮次不能作为续写前缀。

OpenAI 兼容通道其实也能续，但要走 `/beta` 端点 + 给最后一条 assistant 打 `prefix: true`，
而 `/beta` 不在本项目配置的 Base URL 上。与其摆一个半能用的按钮，不如不摆（见 TODO）。

### 六、语音：为什么不用官方的 `/v1/tools/asr`

1. 那个端点只在官方域上提供，OpenCode Go / 自建端点没有
2. 系统识别不需要额外网络请求，也不额外计费

代价是**需要 `RECORD_AUDIO`** —— 本项目唯一的运行时权限（附件、拍照、相册、文件
全都走系统选择器，不要权限）。所以麦克风只在用户点它时才申请权限，
且设备没有识别服务时**根本不显示这个按钮**。

朗读用系统 TTS，同样零依赖。念之前先用 `prepareForSpeech` 把 code fence、表格行、
链接语法剥掉 —— 逐字符念 `fun main()` 毫无意义。

### 七、公式：为什么引 latex-renderer 而不是 WebView + KaTeX

每个公式一个 WebView 实例，长列表滚动会明显掉帧 —— 那正是本项目立项要解决的第一个问题。
`io.github.huarangmeng:latex-renderer` 是 Compose 原生 Canvas 渲染，代价是
**行内公式不能跟着文字走**（独占一行）。这个取舍写在 `MarkdownWithMath` 的注释里。

切分器 `splitMath` 的三条规则都是被真实坑出来的：

- 代码块 / 行内代码里的 `$` 不算公式（否则一段 shell 里的 `$PATH` 会吞掉后面整篇正文）
- 定界符内侧不能是空白（`$5 和 $10` 这类金额因此不会成对）
- 没闭合就按原文（流式期间先显示原文，闭合后才变公式 —— 宁可晚一拍，也不要闪一个红框）

### 八、Mermaid：3.4MB 的取舍

mermaid.js 随包发布（`assets/mermaid/`），不连 CDN：这是离线优先的客户端。
代价是 release 从 2.69MB 涨到 3.66MB（含 KaTeX 字体约 0.5MB）。

三条约束：只在真出现 ```mermaid 时才建 WebView；`securityLevel: 'strict'`（图形代码来自
模型输出，不可信）；渲染失败退回显示源码。JS 回调一律 `post` 回主线程再改 Compose 状态。

### 九、ZIP 归档为什么不拆图片

拆图要定义"图在包里叫什么、消息怎么引用它"的一套新契约，而现有 `BackupFile`
已经能无损往返。**同一份数据只留一种表示**，导入导出就不会因为"两条路各改一处"而对不上。
ZIP 的价值在于**一个文件好传**，不在于省那点体积。

`manifest.json` 是唯一的判定入口（`format = simplechat-archive`），
且必须排在 Chatbox 分支之前 —— 两种包的 manifest 同名，靠 format 区分。

- **列表 marker 右对齐**：浏览器 `::marker` 是右对齐贴着缩进量，左对齐会显得"符号飘在很左边"。
- **表格自己排**：库的表格是等宽列 + 卡片底 + `maxLines=1`，两列表格会被拉成两个大格子
  且长内容被省略号吃掉；改成按"该列最长单元格文字量"分配 `weight`，用
  `MarkdownTableBasicText` 保留单元格内的行内代码/图片渲染。
- **正文基准反推**：`bodyLarge` 由 17/29 改为 17.3/30.3，乘 0.925 正好回到官方 16/28。

仍未对齐（记录在案）：表格官方是 `width: max-content`（窄表格不铺满），我们为了让
`weight` 分列仍是铺满；`strong` 官方 600、库 annotator 固定 700；代码块保留行号与

## §44 · v1.1.3：长会话的导入 / 打开 / 二次打开，与错误文案收口

### 44.1 导入：从"整份读成 String"到"两遍流式"

**现象**：「最喜欢、最长的几个对话导入不了」；结果页只显示少了会话，说不清为什么。

**根因有两层，第二层是第一层留下的债**：

1. 旧实现把单条会话 JSON `readBounded(...).decodeToString()` 读成一个 `String`，
   再 `JsonCursor` 切片。40MB 的 UTF-8 会话读成 `String` 就是 80MB（UTF-16），
   再乘上逐条解析的临时对象，堆里放不下；
2. 于是给单会话加了 **24MB 上限**，超了整条跳过 —— 内存问题被转嫁成了**数据丢失**。

**解法**（`JsonStream` + `ImportSession`）：

- `JsonStream` 是**拉式**流式扫描器：直接吃 `Reader`，按 `hasNextField` /
  `hasNextArrayElement` / `captureValue` 逐段取，任何时候内存里只有"当前这一段原文"。
  ⚠️ 刻意不做成回调式：回调里无法 `suspend`，而写库是挂起操作 —— 那会把解决方案
  逼回"整条攒内存"或"多线程 + 队列"。
- 第一遍只扫标量 + 每条消息的 `id / parent_id / role`（外加 32 条以内的"提问开头"
  用于回退标题）→ 建树、算 `variantIndex`、算当前分支的选中版本；
- 第二遍重新流式读同一 ZIP 条目 → 逐条解析正文 → `sink` 写库。`ImportSession`
  的 `forEachMessage(sink)` 是挂起函数，仓储层在 `sink` 里批量 `upsertAll`（200 条一批）。
- 内存峰值 ≈ 一条消息 + 一批消息对象，与会话总大小无关；**上限整个删掉**。

**顺带的改动**：

- 写库由"50 个会话一个事务"改为**每个会话一个事务**（流式正文没法预攒 50 份）；
  单条会话失败只回滚自己，失败原因照旧进 `ImportReport`；
- 进度改为**按字节**并带会话内百分比：否则"1 个 60MB 会话 + 9 个小会话"的归档，
  进度条会在第一个会话上停 60% 不动，看起来就是卡死；
- `ExternalBackup` 里那份 DeepSeek 分支删掉了 —— 它返回的是整包建好的 `BackupFile`，
  在这里收下又会回到"整条攒内存"。

**验证**：单测造了一份 26MB 的会话（520 条 50KB）导入完整；模拟器上用真 ZIP 导入
一份 9.6M 字符（≈29MB JSON）的会话：802 条消息落地，`active` 801 条、被放弃的分支
1 条（界面显示 `‹ 1/2 ›`）。旧实现会在 24MB 上限处整条跳过。

### 44.2 打开长会话：先读骨架，再按 id 取正文

**现象**：几十万 token 的会话点进去转很久，上百万 token 直接闪退。

**根因**：`SELECT *` 把一个会话里**所有分支**的消息都读出来（正文 + `attachments` +
`timeline` 两段 JSON），再全部映射成 `UiMessage`。每「重新生成」一次，树上就多一条
被放弃的回复，而界面只显示其中一条 —— 分支越多，读的废数据越多。

**解法**（`MessageDao.getLightFor` + `MessageTree.activePathIds`）：

1. 只读骨架（`id / parentId / variantIndex / active / role / status / createdAt`），
   每行几十字节，几千条也是几百 KB；
2. 在内存里走出活跃路径的 id 列表；
3. 按 id 分批（400/批，避开 SQLite 绑定变量上限）只取这条路径的正文；
4. `toUi()` 映射仍在 `Dispatchers.Default`。

被放弃的分支**一次都不会被读出来**。`tailId`（每次追加消息都要调）同改。

### 44.3 「第一次打开顺畅、第二次打开卡死」（真机 ANR）

这条最终是**靠 ANR trace 定位**的，不是靠猜 —— 模拟器上稳定复现（同一会话连开两次
必 ANR），`/data/anr/` 里拿到的主线程堆栈显示：**Runnable、CPU 烧了 11~17 秒**，
栈顶在 `MessageList` → `MessageRow` → `MarkdownWithMath` → `normalizeHtml`/文本排版，
调用者却是 `ChatScreen` 的"首屏贴底"循环 → `scrollToBottom()`。

**真根因：`scrollToBottom()` 写成了 `scrollBy(1_000_000_000f)`。**

LazyList 的条目高度是**按需测量**的，它不知道"后面还有多高"，只能一条一条量着
吃掉这个超大 delta。于是：

- **第一次**打开：列表里还是空内容，`LazyListState(firstVisibleItemIndex = Int.MAX_VALUE)`
  那个"末尾之外"的请求**还没被消费**；等新内容发布，它自动夹到最后一条 ——
  根本不需要滚，所以"第一次很顺畅"；
- **第二次**打开：列表里还是上一个会话的内容，那个请求在首次布局时当场被消费掉；
  新内容一换，视口停在**旧下标**（实测 279/546）。这一步 `scrollToBottom()` 就真的
  要滚 266 条 —— 每条都要完整组合 + Markdown 渲染（单条 20~80ms），
  十几秒后 ANR。

修法：`scrollToItem(lastIndex)`（O(1) 跳转，不测量中间条目）+ 只补"最后一条比视口
高出来的那一点"（只需量最后一条）。修复后模拟器上连开 5 次（含 1030 条消息的会话）
不再 ANR。

**顺带修掉的三个隐患**（各自也会拖慢长会话，但不是这次 ANR 的直接原因）：

1. 解析缓存把 `parseMarkdown` 写在 `synchronized` 里 —— 后台预热持锁解析时，
   主线程取缓存要等锁；改成锁内只查/存、解析在锁外；
2. `MarkdownStateCache` 的淘汰策略是"条数 256 + 满了 `clear()`"，改**按字符预算 40 万
   的 LRU**（访问序）；
3. 预热 effect 的 key 是 `messages.size` 且"把整个会话每条都预热一遍"，改为
   只预热**末尾一条**且限长（>24000 字符不预热）。

### 44.4 上下文统计：从"每帧扫全文"到"防抖 + 后台"

`contextStats` 是 `derivedStateOf`，内部要 `TokenEstimate.ofAll` 扫全部正文。流式期间
`messages` 每 16ms 变一次 → 每帧把整条会话的字符数一遍。改为 `snapshotFlow` +
250ms 防抖 + `Dispatchers.Default`：输入栏上那行数字晚几百毫秒完全无所谓，主线程不再
为它做任何与正文长度相关的工作。

### 44.5 图片：把"魔数对就发"改成"三条件都合规才发"

真机仍有 `messages.N.content.0: You have uploaded an unsupported image`，且都出现在
长会话的历史图片上（每轮重发都失败）。旧 `prepare` 只校验"文件头魔数 + 体积"：
一张 9000×9000、1.2MB 的"合法 PNG"会被原样透传，而服务端视线上限是单边 8192px
（一次 ≥15 张图时 4096px）。现在：

- `BitmapFactory` 只读头拿真实宽高；单边 > 4096 或 > 3000 万像素 → 转码到 1600 长边；
- 原样透传必须同时满足"格式合法 + 体积 ≤1.5MB + 尺寸合规"；
- 头都解不出尺寸（损坏）→ 先试转码，仍失败则**丢弃并计数**（调用方已有提示通道）；
- 转码失败时只允许"格式与尺寸都合规"的图原样发 —— 尺寸超限的图绝不透传。

### 44.6 错误文案：所有出口收口

真机截图里还有两处英文原文：消息下方的 `Software caused connection abort`、
压缩失败的 `压缩失败：stream was reset: INTERNAL_ERROR`。

- `Throwable.userMessage()`：`IOException` 一族走 `networkFailureRes`（断网 / 超时 /
  连接中断 / 证书），不再把 OkHttp / socket 的英文原文透出；
- 新增 `serverErrorText()`：SSE **流内错误对象**（`No available channel for model …`、
  `Authentication Fails (governor)`）先按关键字翻成人话，原文收进括号；
- `MessageEntity.toUi()`：**历史消息里已落库的英文原文**读回来时翻译
  （`storedErrorText` + `isRawNetworkError`，只改显示、库里原文不动）；
- 压缩失败、模型刷新失败等路径全部经由 `userMessage()` / `serverErrorText`。

### 44.7 其它

- **大文本附件上限 10 万 → 40 万字符**：500KB 中文小说约 16 万字，原先被我们自己的
  门槛挡住；是否超模型窗口交给服务商判，错误提示已是人话（context length 映射）；

而早期测试样本是 `{"sessions":[…]}`。我们只认后者 —— 于是真实归档的**会话顺序**退化

## §45 · v1.1.3 验收期热修（真机）

### 45.1 启动即闪退：Android 15 `setVoice(null)`

真机 crash buffer（Android 15 / API 35）：

```text
java.lang.NullPointerException: Attempt to invoke virtual method
'java.lang.String android.speech.tts.Voice.getName()' on a null object reference
  at android.speech.tts.TextToSpeech.lambda$setVoice$13(TextToSpeech.java:1740)
  at android.speech.tts.TextToSpeech.setVoice(TextToSpeech.java:1739)
  at pu2.onInit(...)   ← SpeechOutputController 的引擎初始化回调（R8 混淆）
```

原因：为了"回到系统默认音色"写了 `engine.voice = null`，而 API 35 的
`TextToSpeech.setVoice` 缺少空值检查，引擎初始化回调又在主线程 —— 直接崩，
系统反复重启进程（看门狗又拉起、再崩）。

修法：**回默认只能设 `language`**，永远不设 `voice = null`；`setVoice` 本身也包
`runCatching`（个别引擎会因为音色数据被删而抛异常，不该让一个坏音色炸掉整个 App）。

### 45.2 官方朗读"炸麦雪花音"

用户反馈："试听好好的一读正文就炸麦""过一会儿又正常了"。两个独立根因：

1. **两条 `AudioTrack` 并发**：设置页的试听与对话页的朗读是两个
   `SpeechOutputController`；对话页在"正在念 A 时点 B"也只是 `speak`（`toggle` 只
   对**同一条**先 `stop`）。两路 PCM 同时进混音器 → 白噪声。修法：进程级
   `ActiveController` + 每次开口前 `stopPlayback()`（官方 PCM 与系统 TTS 都停）。
2. **PCM16 帧错位**：`InputStream.read` 返回的字节数不保证是偶数，直接
   `AudioTrack.write` 会让之后所有采样错位半个帧（听起来就是雪花音）；每个分块是
   独立 HTTP 流，下一块重新对齐 —— 所以是"间歇性"。新增 `PcmWriter`：
   - 跨回调保留半个采样，永远写**完整 16 bit 帧**；
   - 循环重试 `AudioTrack.write` 的部分写入（静默丢字节同样会杂音）；
   - 网关忽略 `format=pcm` 回了 `wav` 时，首个块跳过 44 字节头。
   纯逻辑可单测：任意奇数切分 → 输出字节顺序不变、每次写入都是偶数长度。

### 45.3 列表与行内代码排版

- **松列表续段被切出列表**：`1. 标题` + 空行 + `   正文` 这种写法，续段被分块器切成
  独立块、按普通段落渲染到列表外面（正文跑回最左边）。修：分块器把"列表块后面
  首行缩进 ≥1 格、≤8 格"的块并回列表块。
- **多余缩进进正文**：模型常把续段缩进得比内容列更多；CommonMark 只剥"内容缩进"，
  多出来的空格是**字面空格**，渲染成"莫名右移"。新增 `normalizeListIndent`：把列表项
  内正文行的缩进夹到内容缩进，嵌套列表标记行不动。
- **行内代码胶囊过大**：库的 `RoundedCornerSpanPainter` 用的是**整行行框**（行高
  30sp）画背景，而我们原先 margin=0 → 画出一个比字高一倍的灰色方块（真机截图里
  `1.0.0` 那个）。收紧为：上下各 5sp 负 margin 收进行框、水平 2sp、圆角 3sp。

- 单测 **541 全绿**（新增 `PcmWriterTest` 4、`ListIndentNormalizeTest` 8、分块器松列表 2）。
- 真机：安装 versionCode 14 后启动正常（此前无限闪退）；朗读音色页正常列出
  「系统音色 + DeepSeek 官方音色」，选 Stella 试听正常。

## §46 · 自定义端点的模型列表与能力（真机截图反馈）

### 46.1 现象

真机截图两张：设置 → API 配置，服务商「自定义」、Base URL `https://totokens.cc`、
「测试连接」下方显示 **「连接成功，可用模型 45 个」**；点开「模型」那一行，
弹窗只有一个标题和一个大白块，**一个选项都没有**。

### 46.2 根因：拉到的列表只用来报数

两处断链，叠在一起才成这个样子：

1. **测试连接把列表丢了**。`fetchModels` 返回 `List<String>`，而 `ApiPage` 的
   `onTest` 只拿它算了一句 `api_test_ok`，id 一个都没留下。
2. **弹窗的数据源是内置能力表**。`SettingsDialog.Model` 里写的是
   `ModelCatalog.knownModels(provider)`，而 `ProviderKind.CUSTOM` 的目录是
   `emptyList()` —— `ChoiceDialog` 又是"有几个选项就画几行"，于是画出了一个
   只有标题的白框（`Dialog` 用 wrap content，所以看着像"卡住了"）。

也就是说：**不是拉不到，是拉到了没人用**。

### 46.3 修法

- **落库**：`StoredSettings.modelIds`（`ModelIdList` 编解码，换行分隔、去重、
  上限 500）。存下来而不是只放内存，是因为"测试连接"在设置页、选模型也在设置页，
  但中间可能隔着一次重启；列表一丢，自定义端点就退回到空目录。
  **服务商 / Base URL 一换就清空**（`setProvider` / `setBaseUrl` 里比较旧值），
  旧端点的模型 id 在新端点上没有意义。
- **弹窗列两份**：`ModelCatalog.pickerModels(kind, remoteIds)` —— 远端 id 按
  服务端顺序排在**前**（中转站常把主力模型放前面），内置表里没被覆盖的补在**后**
  （网关的 `/models` 可能只回一部分）。远端为空时退回内置表，自定义端点于是
  真的是空 —— 所以界面必须处理空态。
- **空态与出口**：`ChoiceDialog` 加 `emptyHint`（空列表时说"先测试连接，也可以
  手动填写"）与 `extraAction`（「手动填写模型」→ 复用一个输入弹窗）。
  有的网关根本不实现 `/models`，没有这个出口，自定义端点就永远选不到模型。
- **弹窗可滚动**：45 个选项用 `Column` 铺开会有两个后果 —— 弹窗高过屏幕，
  以及**超出窗口的那部分点不到**（看起来又像"列表没显示"）。改用 `LazyColumn`
  + `heightIn(max = 420.dp)`。
- **对话页跟着走**：`ChatViewModel.applyStored` 原先只在**服务商枚举**变化时
  重置 `models = knownModels(kind)`，自定义端点下这一步恰好把拉到的列表抹掉。
  现在跟两个信号：端点变了（服务商或 Base URL）、或 `modelIds` 变了；
  并且 `refreshModels` 成功后也落库。

### 46.4 第三方模型的上下文与能力

真机反馈里那句「注意接入第三方的模型的上下文长度之类的」指的就是这里：中转站
常原样代理官方模型，id 与官方**一模一样**，但 `find` 原先只查"当前服务商"的
能力表 —— 自定义那张是空的，于是 `deepseek-flash` 被当成未知模型：
**上下文按 128K 算**（占用环虚高、压缩阈值提前触发）、**图片被
"模型不支持识图"摘掉**、思考档位直接置灰。

改为三级查找：**当前服务商表 → 全局表（两张内置表合并）→ 保守默认值**。

- 顺序不能反：同一个 id 在两表里能力可以不同（`deepseek-flash` 在 OpenCode Go
  那张里明确标了不支持识图，那是上游实测的路由结果），当前服务商的记录更可信。
- 全局表用 `putIfAbsent` 显式「先到先得」。⚠️ 第一版写的 `associateBy` 是
  **后写覆盖前写**，被新加的单测当场抓住（`deepseek-flash` 拿到了 OpenCode Go
  那条"不识图"）。
- 两表都没有的 id **保持保守默认值**（128K / 不识图 / 不思考），**不按 id 字面
  猜**：上下文猜大 → 压缩不触发 → 服务端 400（`maximum context length`）；
  猜小只是早点压缩。识图 / 思考猜错更糟 —— 会直接发出模型不接受的参数。

### 46.5 一处顺手的拦截

自定义服务商的 `defaultModel` 是空串，若用户没选模型就发消息，请求里的
`model` 是空的，服务端只会回一句看不懂的 400。`send()` 里加一道：`modelId`
为空 → 提示「还没有选择模型」并指出在哪儿选，不外发请求。

### 46.6 验证

- 单测 **563 全绿**（新增 `ProviderTest` 7 项：选择器顺序 / 补内置 / 去重 /
  跨服务商能力 / 当前表优先 / 未知 id 默认值；`ModelIdListTest` 6 项：
  往返、空行、去重、上限）。
- 待真机：自定义端点 → 测试连接 → 点「模型」应列出 45 个；选中后顶栏/面板显示
  对应模型；重启后列表仍在（`modelIds` 已落库）。

## §47 · v1.1.3：列表排版对齐官方客户端（v1.27）

### 47.1 现象与判定

真机反馈：「数字还是没对齐，间距还是有问题，和官方对比」。把官方客户端截图与
我们对同一条消息的渲染换算到 em 后逐项量：

| 指标 | 官方客户端 | 修正前 | 修正后 |
|---|---|---|---|
| 列表正文缩进 | ≈1.95em | 1.375em | 1.5em（顶层 24dp） |
| 符号右缘 → 正文 | 0.5em | 随位数变化（一位数 0.7em） | 0.375em（6dp） |
| 嵌套列表正文缩进 | ≈0.93em | 2.5em | 1em（16dp） |
| 条目间距 | ≈0.85em | 0.39em | 0.6em（10dp） |

### 47.2 根因一：右对齐从来没有生效

库的列表把符号渲染在 `Box(modifier = markerModifier())` 里，`Box` 默认
`propagateMinConstraints = false` —— 子 `Text` 拿到 `minWidth = 0`，按自身宽度测量，
`textAlign = TextAlign.End` 因此**完全无效**。符号永远贴列左缘：

- `1.`（13dp）与 `10.`（22dp）的点号不在同一条竖线上；
- 与正文的间隙随位数变化；
- `10.` 比"列宽 22dp − 间隙 5dp"还宽，直接溢出。

修法：自绘列表。符号列宽 = max(该层最小缩进, 用 `TextMeasurer` 量出的最宽序号 + 间隙)；
符号列用 `Box(contentAlignment = TopEnd)`，内部 `Text` 必须 `fillMaxWidth()` 才能让
`textAlign = End` 生效。

### 47.3 根因二：嵌套缩进被算了两遍

库对嵌套列表按 `padding-start = listIndent × depth` 缩进，而我们的符号列本身已经是
一层缩进，两者叠加后嵌套正文比父级正文多 40dp（官方约 1em）。自绘后每一层只由符号列
贡献缩进（顶层 24dp、每层 +16dp），与官方客户端的层进节奏一致。

### 47.4 根因三：序号与正文的基线差

两个 `Text` 在同一 `Row` 顶部对齐，但首行基线由**该行实际使用的字体**的 ascent 决定：

- 符号 `1.` 全为拉丁字符 → Roboto（ascent ≈ 0.927em）；
- 正文是汉字 → CJK 回退字体（Noto Sans CJK，ascent ≈ 1.16em）。

16sp 下正文基线比符号低约 3.7dp，视觉上就是"序号飘在文字上方"。官方 Web 端两者在
同一个行内盒里排，天然共基线。修法：用 `TextMeasurer` 以各自真实样式量出首行基线差再
下移符号；纯拉丁条目差值为 0，由 `containsCjk` 判定后跳过（不写死 3.7dp，换字体/字号仍成立）。

### 47.5 附带修复：未闭合块注释导致的会话闪退

发布前冒烟测试发现：打开含特定代码块的会话时闪退。

```
java.lang.IllegalArgumentException: Reversed range is not supported
  at AnnotatedString$Builder$MutableRange.toRange
  at IncrementalHighlight.of(CodeFence.kt)
```

把真实数据里的 **5162 段代码围栏**导出后用 JVM 单测逐段跑高亮器，定位到最小复现：
JS 代码里字符串包含 C 风格注释起始标记而其后没有结束标记，分词器把注释区间算成
`105..101`（`end < start`）。修法两层：换算区间时丢弃 `end <= start` 的非法结果；
写 `AnnotatedString` 前再按正文长度钳一次 —— 最坏情况只是少一段配色，不会中断渲染。
回归测试覆盖静态渲染与流式追加两条路径。

### 47.6 验证

- 单测 **572 全绿**（新增 `MarkdownListLayoutTest` 9 项、`CodeFenceTest` 2 项）。
- 模拟器：12 项有序列表（含 `10.`–`12.`）符号右对齐、两位数不溢出；嵌套列表缩进与
  间距与官方客户端截图一致；修复后重新安装 release 包启动正常、无 FATAL。

### 48. 发布前收尾：通知权限、行高网格、产物命名（v1.1.5）
