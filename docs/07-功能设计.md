## 12. Chatbox 数据导入

### 12.1 Chatbox 的两种导出

| 导出方式 | 路径 | 内容 | 可导入性 |
|---|---|---|---|
| **完整备份** | 设置 → 数据管理 → 导出数据 → **JSON/ZIP** | 全部会话 + 设置 + 附件资源 | ✅ **首选**，结构完整 |
| **单会话导出** | 会话菜单 → 导出 | Markdown / TXT / HTML | ⚠️ 降级方案，有损 |

Android 上 Chatbox 的导出文件位于 `Documents/chatbox_ai_exports`。

### 12.2 完整备份的格式（已从源码核实）

ZIP 压缩包，内含 `manifest.json` + 每个会话一个 JSON 条目 + resources 条目。

```jsonc
// manifest.json
{
  "format": "chatbox-backup",
  "formatVersion": 2,
  "exportedAt": "2026-09-21T12:00:00.000Z",
  "application": { "name": "Chatbox", "version": "1.23.1", "platform": "android" },
  "exportItems": ["setting", "key", "conversations", "copilot"],
  "data": { "settings": {...}, "copilots": {...}, "sessionSettings": {...} },
  "sessions": [
    { "path": "sessions/<id>.json", "size": 12345, "checksum": {...},
      "id": "<sessionId>", "meta": {...}, "resourceIds": [...] }
  ],
  "resources": [ { "id", "kind", "mimeType", "encoding", "filename", ... } ],
  "warnings": [...],
  "stats": { "sessionCount", "resourceCount", ... }
}
```

会话实体结构（取自 `src/shared/types/session.ts`）：

```ts
Session { id, name, threadName?, messages: Message[], threads?, messageForksHash? }

Message {
  id, role: 'system'|'user'|'assistant'|'tool',
  content: string,
  contentParts?: Array<
    | { type: 'text',      text }
    | { type: 'image',     storageKey }
    | { type: 'reasoning', text, duration? }
    | { type: 'info',      text }
    | { type: 'tool-call', toolName, args, result, state }
  >,
  files?, timestamp?, model?, ...
}
```

### 12.3 字段映射

| Chatbox | 本项目 | 说明 |
|---|---|---|
| `Session.name` | `conversations.title` | |
| `Message.role` | `messages.role` | `tool` 角色本期丢弃 |
| `Message.content` | `messages.content` | |
| `contentParts[type=reasoning].text` | `messages.reasoning` | 合并 |
| `contentParts[type=image].storageKey` | `attachments.localPath` | 需从备份 resources 中解出 |
| `contentParts[type=tool-call]` | — | 本期丢弃（按 Markdown 渲染工具调用为可折叠块也可，优先级低） |
| `Session.messageForksHash` | `messages.slotIndex / variantIndex` | 分支展开为多版本 |
| `Message.timestamp` | `messages.createdAt` | |
| `data.copilots` | `presets` | 映射为全局预设 |
| `slotIndex` | 按消息在 `messages` 数组中的**下标**顺序生成 | |

**分支处理**：Chatbox 的 `messageForksHash` 是 `{ [messageId]: { position, lists: [{messages}...] } }`，
表示「某条消息之后存在多个备选后续」。导入策略：

1. 沿主链（`list[position]`）生成 slot 序列
2. 遇到 fork 时，其余 `lists[i]` 的后续消息作为**额外版本**挂到对应 slot 上
3. `expandedMessageIds` 去重，避免共享前缀重复导入

### 12.4 降级方案：Markdown 导入

Chatbox 的 Markdown 导出格式为：

```markdown
# <会话名>

## 1. <thread 名>

<User 消息原文>

<Assistant 回复原文>
...
```

解析策略：按 `# ` 切会话、按 `## ` 切 thread，其余按空行分段并依「连续段交替归属
user / assistant」的启发式切分。**有损且不保证准确**，仅作为兜底，
UI 上明确标注「推荐使用 JSON 备份导入以获得完整数据」。

### 12.5 实现位置

```
data/import/ExternalBackup.kt   识别来源 + 把 Chatbox 备份**翻译成我们自己的 BackupFile**
data/import/ImageSize.kt        JPEG / PNG 头解析（取图片尺寸）
ChatRepository.importParsed()   落库（去重 / 事务 / 预设挂载 / 覆盖与合并）
ChatRepository.importExternal() 入口：认来源 → 翻译 → 交给 importParsed
```

**关键取舍：只写"怎么读"，不写第二遍"怎么写"。** 落库逻辑已经写好并有单测，
换一种备份来源变的只是读法；再写一遍写入路径，除了多一处要维护的分叉什么也换不来。
所以 `ExternalBackup` 的输出就是 `BackupFile`，写完直接复用现成的导入器。

### 12.6 ⚠️ 真实备份与本文档的四出入（已用真实文件核实）

§12.2 / §12.3 是**从 Chatbox 源码反推**的。拿到真实备份（Chatbox 1.23.3 /
formatVersion 2）跑第一遍就发现四处对不上 —— 而且**每一条都不会报错**，
只会安静地导入出"一堆残缺的会话"：

| 反推的写法 | 真实格式 | 只按反推写会怎样 |
|---|---|---|
| `sessions/<id>.json` | **`sessions/<id>/session.json`**（多一层子目录） | 一个会话都找不到 |
| 消息有 `content` 字段 | **只有 `contentParts`**（实测 `content` 出现 **0** 次） | 所有正文为空 |
| `session.systemPrompt` | **是 `role: "system"` 的消息** | **所有人设丢失** |
| 图片路径未知 | ZIP 里的 `resources/` 条目，靠 manifest 的 `originalStorageKeys` 与消息里的 `storageKey` 对接 | 附件丢失 |

**第三条最要命**：对本项目来说系统提示词就是人设与写作要求，丢掉等于把会话掏空
（各会话里全都有，有的写得很长）。所以 system 消息**不进对话流**，
而是合并成会话的 `systemPrompt`。

另外两个只有真数据才会暴露的坑：

1. **必须用 `ZipFile`，不能用 `ZipInputStream`。**
   Chatbox 是 JSZip 打的包，每个条目都带**数据描述符**（长度写在数据之后）。
   `ZipInputStream` 只允许 DEFLATED 条目这么做，而包里 `manifest.json` 与会话 JSON
   是 DEFLATED、**图片是 STORED** —— 撞上 STORED 直接抛
   `only DEFLATED entries can have EXT descriptor`。更糟的是 `manifest.json`
   恰好是**最后一个**条目，顺序流必须跳过前面所有图片才能读到它，于是必然失败。
   `ZipFile` 走**中央目录**（长度记在那里，与描述符无关），不受影响。
   代价是它要一个 `File`，所以落一个临时文件（用 `cacheDir`）。
2. **图片尺寸得自己解析。** `Attachment.width/height` 是布局用的占位比例，
   为 0 时 UI 退回 `ratio = 1f` —— **横图会被压成正方形**。
   所以按文件头解析 JPEG / PNG（`ImageSize.kt`，纯函数 + 单测）。
   JPEG 的 SOFn 段是**先高后宽**，且 EXIF 段里常内嵌一张缩略图，
   硬扫标记会读到缩略图的尺寸。

### 12.7 刻意不做的两件事

- **Markdown 导出降级**：那份格式是给人看的，要靠"空行交替归属 user / assistant"
  猜角色，猜错了用户**看不出来**。宁可明确拒绝，也不要悄悄导一份错的东西。
- **展开 `messageForksHash`**：Chatbox 的分支语义（按消息 id 挂备选后续）
  和我们的树不是一回事，而且用得很重（有的会话分支极多）。硬映射只会造出
  用户看不懂的版本。目前只取**当时正在看的那条**（也就是用户在 Chatbox 里
  看到的那个样子），并在导入结果里**明确告诉用户**丢了什么。

### 12.8 真机验证（2026-09-22，已通过）

用一份真实备份导入核对（备份是本机素材，不入库）：

| 核对项 | 结果 |
|---|---|
| 会话数 | 与源文件一致 ✓ |
| 消息数 | 与源消息数一致（差值 = 被提走作 systemPrompt 的 system 条数）✓ |
| 系统提示词 | **全部带上**，长度与源文件逐一吻合 ✓ |
| 图片附件 | base64 解开是合法 JPEG，宽高解析正确 ✓ |
| 头像不误入 | `kind=avatar` 的资源没有变成消息图片 ✓ |
| 断链 | 每条消息的 `parentId` 都在本会话内 ✓ |
| 打开渲染 | 最长的大会话能正常打开，Markdown 与思考栏正常 ✓ |

### 12.9 DeepSeek 官方导出导入（`deepseek_data-*.zip`）

**适用于**：SimpleChat 1.1.0 及更高版本 · `data/import/DeepSeekHistory.kt`

#### 概述

DeepSeek 官方聊天记录可一键导入为本地会话。格式来自官方开源前端
[`deepseek-ai/chat-demo`](https://github.com/deepseek-ai/chat-demo)（MIT）的
`src/services/chat/history/` 模块 —— 有 `README.md` 与 `format.ts` 逐字段定义，
**不是逆向推测**，因此不做"宽松兼容"：版本不符即拒绝，不猜。

#### 归档结构

导出文件名形如 `deepseek_data-2026-11-11.zip`，`manifest.json` 必须是首个条目。

| 条目 | 内容 | 说明 |
|---|---|---|
| `manifest.json` | `{ "export_format_version": 3 }` | 版本判定唯一依据 |
| `chat_sessions/{session_id}.json` | 会话与消息树 | 一条会话一个文件 |
| `chat_session_index.json` | 会话索引 | 决定会话顺序 |
| `chat_sessions/{session_id}_files/{file_id}_{name}` | 图片原件 | 按 `export_path` 匹配 |

#### 字段映射

| 归档字段 | 本地字段 | 说明 |
|---|---|---|
| `parent_id` / `current_message_id` | 完整消息树 | 同父多子 → 变体（`variantIndex`），当前分支那条标 `active`；断链的行整支丢弃 |
| `REQUEST` / `RESPONSE` | `content` | 提问 / 回答正文 |
| `TEMPLATE_RESPONSE` | `content` | 服务端模板正文，与回答同一处理 |
| `THINK` + `elapsed_secs` | `reasoning` + `thinkingMs` | 思考内容与用时 |
| `FILE`（`is_image`） | `attachments` | base64 + 宽高（宽高由字节现算） |
| `status` | `status` | `FINISHED`→完成、`INCOMPLETE`/`WIP`→停止、`FAILED`/`TIMEOUT`/超长→错误、`CONTENT_FILTER`→完成 |
| `inserted_at` / `updated_at` | `createdAt` / `updatedAt` | ISO 8601 → 毫秒 |

> [!NOTE]
> `CONTENT_FILTER` 映射为"完成"而不是"拒绝"：客户端只做透传，不替服务端执行内容裁量，
> 也不丢弃已经收到的正文。`stop_reason` 仅作记录。

#### 导入方式

导入入口为「设置 → 导入所有数据」，三种策略（对三种来源通用）：

| 策略 | 同名会话 | 数据影响 |
|---|---|---|
| 增量 | 跳过 | 只补本机没有的会话；本地改动不动 |
| 覆盖同名 | 删旧后导入 | 消息 / 预设挂载 / 摘要随外键级联删除，草稿单独清理 |
| 同名新命名 | 两条并存 | 新标题加「（副本 N）」后缀，并**换新 id**（消息 id 与 `parentId` 同步重映射） |

同名按**标题**判定：同一条会话换设备或隔一次导出，id 会变，标题才是用户认得出的那个对话。

#### 已知限制

| 项目 | 处理 |
|---|---|
| `TOOL_SEARCH` / `TOOL_IMAGE_SEARCH` / `TOOL_OPEN` / `TOOL_FIND` / `READ_LINK` | 导入搜索词、来源及工具步骤。归档读链签名可随历史重导出 |
| 分支 | **已保留**：同父的多个子消息导入为变体，界面可用 `‹ 1/2 ›` 切换 |
| `TIP` / `CONTENT_RISK` / `PARTIAL_FILE_READ` | 丢弃（纯展示提示，无信息量） |
| 非图片附件 | 丢弃（归档只有元数据，没有字节，**官方限制**） |
| 图片 | **无配额**：字节落盘到 ilesDir/attachments/，行里只留文件名（见 AttachmentFiles）。仅保留 64 MB 的单张防呆上限 |

#### 故障排除

| 现象 | 原因 | 处理 |
|---|---|---|
| 点「导入所有对话」长时间无反应 | 早期版本把整包读成 `ByteArray`（数百 MB 必 OOM） | 1.1.0 起改为流式落盘 + `ZipFile` 按中央目录读；进度分两阶段（读取中为循环条，导入中为百分比） |
| 导入失败并提示 allocation 失败 | 图片在**判断上限之前**就被整块读入 | 已改为有界读取：先看中央目录的 `entry.size`，再按 64 KB 分块，超限即放弃 |
| 某个会话打不开、闪退 | 单行超过 `CursorWindow`（2 MB） | 读取退到 `getAllForCapped`（截断附件列）；导入侧已限制单条消息的附件总量 |

### 14.3 分支（parentId 树的落地）

设计见 §4.1。实现要点（下表是**当前**语义，已随树模型更新）：

| 操作 | 语义 |
|---|---|
| 重新生成 | 同父新增版本并激活；旧版本连同子树原样留着 |
| 编辑 AI 回复 ·「保存」 | **原地**改这一条：不新增版本、分支不变、下游照旧 |
| 编辑 AI 回复 ·「保存并发送」 | 同父新增版本 + 在其下继续生成（旧分支可切回） |
| 编辑用户消息 | 同父新增版本 + 继续生成（旧回答留在旧分支） |
| 删除 | 删这条连同它的整棵子树 |
| 切版本 | 同一父节点下 `active` 转移，路径整段重建 |

**编辑刻意分两条路径**（不是"多一个按钮"，而是两种真实需求）：

- **用户消息**：复用输入栏（官方做法）。点气泡 → 输入栏顶部出现「修改输入」+ ✕，
  发送键即「保存并发送」。一个按钮，不做二次选择 —— 改了提问，旧回答本就无意义。
- **AI 回复**：吸底卡片，才需要区分「保存」与「保存并发送」。

⚠️ **「保存」曾经也走"新增版本"**，于是在树模型下有两个可见后果：只改一个错别字
也会冒出 `‹ 1/2 ›`，而且新版本没有子树 —— 会话下半段当场消失。现在「保存」是原地改，
分支数与下游都不变（见 `14-编辑保存与朗读收尾-2026-11-17.md`）。

**跨协议的一个坑**：「保存」不能只改 `UiMessage.content`。OpenAI 通道的界面与请求都读
`content`，而 Anthropic 通道两处都读 `timeline` 里的正文块 —— 只改 `content` 会变成
"OpenAI 那边生效、扩展通道那边没变"，所以 `rewriteTimelineText()` 必须同时改写时间线。

## 16. 上下文统计与压缩（M6 提前落地）

### 16.1 token 估算

**不引 tiktoken**：它是按目标模型精确编码的，换服务商就不准；体积与耗时也不小。
这里只要"够用的量级感"（12k 还是 120k）。

分 CJK / 非 CJK 加权：

```
tokens ≈ CJK字符数 / 1.5 + 其他字符数 / 4
```

中文与英文每 token 的字符数差 2.7 倍，用同一个常数会把纯中文或纯英文的场景
估偏一倍以上。**不用于计费**，只用于圆环、统计与阈值提醒。

> 单测锁住的是**单调性与量级**，不是绝对值：估偏一倍会让"该压缩了"的提示
> 变得毫无意义。

### 16.2 常驻占用指示

输入栏第二行（思考入口右侧）：`◯ 12k`。

- 环形进度 + 紧凑长度（`12k` / `1.2M`）
- 颜色三档：常规 / **≥70% 琥珀** / **≥90% 红** —— 不点开面板也看得见"该压缩了"
- 压缩生效时环尾加一个小蓝点，提示"发出去的和本地看到的不一样"

用 `derivedStateOf` 缓存：流式期间每 50ms 就会重组一次，
若每次都对全部消息重扫一遍，长会话里会白白吃掉帧预算。

### 16.3 压缩（Compact）

**核心约定：只改变发给 API 的内容，绝不删除或改写本地消息。**
被压缩掉的原文在界面上照常显示、照常可编辑、照常导出。

```
[system]  会话补充提示词 + 预设拼接
[system]  以下是此前对话的前情提要 ……（压缩摘要）
[user]    ↑ 只发送当前路径中 throughMessageId 之后的消息
…
```

三个刻意的设计：

| 决定 | 理由 |
|---|---|
| **通常保留最近 6 条完整消息** | 最近内容估算超过窗口一半时，按用户轮次缩减保留范围，至少保留最新一轮 |
| **摘要可读可改可重生** | 长篇创作里 AI 记错人名地名的代价极高，用户必须能直接修正 |
| **完成后显示摘要** | 压缩时只显示加载动画和停止入口，不展示中间结果 |

分层压缩会：先分别总结各批原文，再按原顺序合并摘要。服务端拒绝输入时，自动缩小当前批次。
已完成批次写入应用私有进度文件。重试时校验源内容和请求配置，只复用匹配的进度。

没有匹配的检查点，且待压缩原文和已有摘要满足字符上限与本地 token 预算时，
先用一次请求总结完整的待压缩内容。输入超限被拒、请求超时、结果为空或不完整，或摘要未缩短时，
使用原有的有界分层压缩。已有匹配的检查点时，直接恢复进度。近期保留的完整轮次不进入摘要输入。

摘要指导仅按待压缩范围内的用户消息和已有摘要选择创作、技术或通用类型。创作摘要关注角色关系、时间线和未回收线索；
技术摘要关注环境、验证结果和后续步骤；类型不明确时使用通用指导。历史指令只作为资料，不执行。

成功后一次替换正式摘要并清理进度文件。失败或取消时保留原摘要；修改消息、切换分支或发送新消息时停止压缩。
摘要可能遗漏细节，请核对关键事实。预算、检查点和验证范围见[上下文压缩与恢复](22-上下文压缩与恢复.md)。

## 21. 「从这里新建对话」（会话分叉）

### 21.1 为什么不是「新建分支」

原本设想的是长按菜单加「从这里新建分支」。**放弃这个说法与做法**：

分支在**会话内部**已经由「重新生成 / 编辑重发」完整覆盖了 —— 它们挂在同一个
父节点下成为兄弟，靠 `‹ n/m ›` 切换，下游整段跟着换（§18.2）。
在同一会话里再加一个"分支"入口，等于用两种方式做同一件事。

于是这个入口的语义收敛到**会话之间**：

> 取当前会话的一段，**复制**成一个**独立的新会话**，从那里接着写。原会话一个字节都不动。

一句话：**重新生成 = 会话内分支；从这里新建对话 = 会话间分叉。**

### 21.2 精确语义

| 维度 | 规则 |
|---|---|
| 复制范围 | 当前**活跃路径**上，从根**到被长按的那条为止**（含） |
| 分支与版本 | **只复制当前选中的那一版**，不搬兄弟版本。新会话里全是单版本 |
| 消息 id | **全部重新生成**，`parentId` 按新 id 重挂（沿用旧 id 会撞主键） |
| 新 id 链 | `parentId` 重新指向**新链上的前一条**；首条的 `parentId = ""`；`variantIndex = 0`、`active = true` |
| 会话级设置 | 模式 / Provider / 模型 / 系统提示词 / 挂载的预设 **一并复制** |
| 压缩摘要 | **不复制**。被摘要盖住的原文本来就在复制范围内，摘要是多余的 |
| 时间戳 | 消息**保留原始 `createdAt`** —— 它记录的是"这些话是什么时候写的"，重盖会让历史失真；树序本来也不依赖时间 |
| 标题 | `原标题（副本）`；已存在同名则 `（副本 2）`、`（副本 3）`… |
| 落点 | 新会话 `updatedAt = now`，因此排在列表最前 |
| 之后 | **自动打开新会话** —— 用户的意图就是"从这里接着写" |

### 21.3 与「重新生成」的分工

```
原会话                                  新会话（副本）
u1 ── a1 ── u2 ── a2                    u1 ── a1 ── u2 ── a2
              │                         （线性，无兄弟版本）
              └─ a2'  ← 重新生成：会话内多一个版本
                         u2 下出现 ‹ 1/2  2/2 ›

        └── 从这里新建对话（长按 u2）────────────┘
```

### 21.4 为什么不做成「连整棵树一起搬」

技术上做得到（把子树连同兄弟版本一起搬过去）。**不做**：

- 用户要的是"把这段单独拎出来继续写"，不是"把分支历史也搬过去"
- 新会话里冒出 `‹ 1/3 ›` 会让人以为这里也能切版本 —— 其实两边已经脱钩，
  切了也不会同步回原会话。那是个纯粹的认知负担
- 真想要旧分支，回原会话切一下就行，原会话一个字节都没动

### 21.5 失败与边界

| 情形 | 行为 |
|---|---|
| 流式进行中 | 与其它编辑操作一致，`isStreaming` 时早退 |
| 被长按的消息不在活跃路径上 | 理论上不可能（菜单只挂在当前列表上）；真发生就静默返回 |
| 活跃路径为空 | 静默返回 |
| 复制中途失败 | 整个操作在**一个 Room 事务**里，失败整体回滚，不会留下半个会话 |

### 21.6 实现位置

| 层 | 位置 |
|---|---|
| 纯逻辑 | `db/MessageTree.kt`：`pathTo(all, messageId)` 截到某条为止；`forkMessages(path, newConversationId, newId)` 重挂 id 与 `parentId` |
| 单测 | `MessageTreeTest` 增 7 项：截断位置、空路径、不在活跃路径上、id 链、变体扁平化、**复制出来的东西能被 `activePath` 走通**（错了就是"打开新会话一片空白"） |
| 数据 | `ChatRepository.forkConversation(fromMessageId): String?`，整个操作在**一个事务**里 |
| 标题 | `forkedTitle()`：`原标题（副本）`，同名递增；先把已有的副本后缀剥掉，免得"副本的副本"一路叠 |
| 状态 | `ChatViewModel.forkFrom(message)`：落库 → `openConversation(newId)` 自动打开 |
| 入口 | 长按菜单（`MessageList.kt`），用户消息与 AI 消息**都有** |

图标：`AppIcons.MessageSquarePlus`（Lucide message-square-plus，气泡里一个加号）。

**真机验证**：长按用户消息 → 副本只含那一条；长按 AI 回复 → 副本含两条且代码块完整；
标题依次为 `（副本）`、`（副本 2）`；原会话 token 数不变（一个字节没动）。

### 21.7 菜单最终形态

| 角色 | 菜单项 |
|---|---|
| 用户消息 | 复制 / **从这里新建对话** / 编辑 / ─── / 删除 |
| AI 消息 | 复制 / 重新生成 / **从这里新建对话** / 编辑 / ─── / 删除 |

位置在「编辑」之后、危险操作分隔线之前 —— 它是建设性操作，不该挨着删除。
菜单高度：5 项 × 44dp + 上下内边距 + 分隔线 ≈ 252dp，仍在一屏内。

## 22. 数据出口与检索

### 22.1 两种导出，服务两种人

| | JSON 备份 | **Markdown 文稿** |
|---|---|---|
| 给谁看 | 机器 | **人** |
| 内容 | 全部分支、全部版本、时间戳、性能数据 | **当前分支、当前选中版本的正文** |
| 用途 | 导入回来一模一样 | **贴进任何编辑器继续写** |
| 入口 | ⚙ 面板 → 导出 → JSON 备份 | ⚙ 面板 → 导出 → Markdown 文稿 |

Markdown 侧**刻意不做**三件事：不带分支版本、不带思考内容、不带性能数据 ——
对着一份稿子，那些都是噪音。

导出格式（`ChatRepository.exportConversationMarkdown`）：

```markdown
# 会话标题

> deepseek-flash · 共 12 条 · 导出于 2026-09-22 05:12
> 仅含当前分支、当前选中版本的正文，不含思考内容

---

**我**

提问原文

---

**AI**

回复正文（代码围栏原样保留）
```

用 `**我**` / `**AI**` 做角色标记而不是 `##` 标题 ——
正文里本来就可能出现 `##`，会串味。

文件名取会话标题，去掉文件系统不认的字符后 `.take(40)`，
**截断后还要把悬空的左括号和空白收掉** —— 否则 `（副本 2）` 会被切成
`…（副本 .md`。

### 22.2 全文搜索

搜索页从「只搜标题」扩到「**标题 + 消息正文**」。

```sql
SELECT c.*,
    (SELECT m.content FROM messages m
     WHERE m.conversationId = c.id AND m.content LIKE '%' || :query || '%'
     ORDER BY m.createdAt ASC LIMIT 1) AS snippet
FROM conversations c
WHERE c.title LIKE '%' || :query || '%'
   OR EXISTS (SELECT 1 FROM messages m
              WHERE m.conversationId = c.id AND m.content LIKE '%' || :query || '%')
```

**刻意不上 FTS**：这个量级（几百个会话）`LIKE` 完全够用，
而 FTS 要额外的虚表 + 分词器，中文还会被切坏。

结果行在标题下补一行**命中片段**：

- `snippet` 是**整条**正文，**不在 SQL 里截断** —— 中文按字节截会切出乱码
- 取窗口交给 `snippetAround()`（纯函数 + 10 项单测）：
  **以命中处为中心**取，两侧不够就补省略号

为什么不是"取开头 N 个字"：关键词在中后段时，结果行里根本看不见它，
用户会以为搜错了。

> 顺带修：抽屉列表原先也走带 `:query` 的同一个查询，现在拆成
> `observeAll()`（抽屉用，全量）+ `search(query)`（搜索页用），
> 抽屉的查询不再为搜索页的需求买单。

## 23. 附件（图片 / 纯文本文件）

### 23.1 支持范围

| 类型 | 支持 | 说明 |
|---|---|---|
| 图片 | ✅ | JPEG / PNG / GIF / WebP，导入时统一重编码 |
| 纯文本文件 | ✅ | md / txt / json / yaml…**按内容判定**，不按扩展名 |
| `.docx` / `.pdf` | ✅ | 见 **§27**（docx 抽文本、PDF 渲染成图） |
| 旧版 `.doc` / `.xls` | ❌ | OLE 复合文档，明确报错并提示另存为 docx |
| 其它二进制（压缩包…） | ❌ | 解码会得到一堆乱码，那种"垃圾进上下文"比报错更糟 |

选择器**不做 MIME 过滤**（传通配）。`.md` 在不同设备/提供者上被报成
`text/markdown`、`text/x-markdown` 甚至 `application/octet-stream`，
按 MIME 过滤会让用户在文件选择器里**根本看不到自己的 md 文件**。
真正的把关放在 `AttachmentImport.text`：严格按 UTF-8 解码，二进制直接报
"看起来不是纯文本文件"。

相册与文件入口**都支持一次选多个**：逐个读取、读到一个就进待发区；
单个失败不影响其余（成功的照常保留，失败个数与首个原因统一提示）；
读取期间切走会话，结果仍归**发起时**所在的那个会话。

上下限：文本 **10 万字**、原始文件 **24MB**、图片压缩后最长边 **1600px**。

### 23.2 图片处理（`data/AttachmentImport.kt`）

1. **按需采样解码**。先读 bounds，再按目标尺寸算 `inSampleSize` ——
   直接把 4000×3000 解进内存是 48MB，两次就 OOM。
2. **摆正方向**。API 28+ 用 `ImageDecoder`（自动应用 EXIF 方向）；
   API 26–27 回落 `BitmapFactory` + `android.media.ExifInterface` 手动旋转。
   不处理的话，手机竖着拍的照片会**躺着**进模型。
3. **压到白底**。JPEG 没有透明通道，带 alpha 的图直接压会让透明区域变成黑块。
   先画到白底 Canvas 上再压。
4. **重编码为 JPEG q88**。原因见下。

#### 为什么压到 1600px 就够了

官方 Vision 指南写得很清楚：图片在推理前会被统一缩到"总像素约等于 1300×1300"，
每张图 token 上限 **1024**。本地留更大的副本**不会**让模型看得更清，
只会让数据库和请求体白白变大。

#### 为什么存 base64 而不是文件路径

「一份 JSON = 一份完整备份」这个约定不能打破。路径方案要么在备份里丢图，
要么把备份改成 zip。压完之后单图通常 40–400KB，转 base64 再多三分之一，
是可接受的数量级。

**代价**：图片会随**每一轮**请求重发（接口无状态，历史里的图片每次都要带上），
token 账要按"每轮都算"来看 —— 上下文圆环里每张图按上限 1024 计入。

### 23.3 请求里怎么带（官方 Vision 格式）

官方只支持一种形态：`content` 是 **block 数组**，且**图片只能出现在 user 消息里**
（放进 system / assistant 直接 400）。

```json
{
  "role": "user",
  "content": [
    { "type": "text", "text": "看看这张图" },
    { "type": "image_url",
      "image_url": { "url": "data:image/jpeg;base64,...", "detail": "high" } }
  ]
}
```

组装规则（`ui/chat/RequestContent.kt`，纯函数 + 单测）：

| 附件 | content |
|---|---|
| 无 | 纯字符串（最省事） |
| 只有文本文件 | 纯字符串（附件内容按定界块拼进去） |
| 有图片 | block 数组 |

#### `detail` 为什么固定用 `high`

官方给了 `low / high / original / auto` 四档。`low` 会把图**缩到 512×512**，
而本项目最常见的图片用法就是"截图里有一段文字，帮我看看" ——
512×512 下小字直接糊成一团。`high` 的代价可控：每张图上限 1024 token，
且只有带图的会话才付这个成本。

#### 文本附件为什么要定界

```text
<<<附件开始：设定.md>>>
# 世界观
...
<<<附件结束：设定.md>>>
```

直接把内容粘进用户的话里，模型分不清"这是附件内容、那是我的要求"，
长文会把用户的指令淹没掉。定界之后模型能分清，用户事后也好核对。
压缩摘要时同样会把文本附件带上（否则"我上传的那份设定"会在压缩后凭空消失）。

### 23.4 「只挂附件不打字」是被允许的

用户消息允许**空正文 + 有附件**（"丢一张图进来说『你看看这个』"）。
这一条在 `orderedOutgoingMessages` 里有个坑：原先的过滤条件是
`content.isNotBlank()`，会把这种消息**整条丢掉** —— 请求里只剩一串 assistant，
服务端回 `Empty input messages`。现在判据是"有没有东西可发"
（正文非空 **或** 有附件）。

### 23.5 界面

- **入口**：输入栏的 `⊕`。菜单两项：图片 / 文件（md / txt 等纯文本）。
  模型不支持识图时，**提示挂在「图片」那一项上**（只有它受能力限制）。
- **待发送区**：输入栏**上方**一行可横滚的 chip。图片是缩略图，
  文件是"图标 + 文件名 + 字数"，右上角 ✕ 移除。
- **消息里**：附件排在正文**上面**（图片是"我给它看的东西"，文字是"我要说的话"）。
  颜色按场合分两套 —— 气泡内用**正文色低透明度**压蓝底，气泡外用浅灰底 + 描边。
  灰底灰框直接压在蓝气泡上像贴了张打了补丁的纸。
- **点图放大**：全屏查看器，显示文件名 / 尺寸 / 大小。
- **发送拦截**：模型不支持识图时在**客户端**拦住并提示换模型，
  而不是让请求打到服务端换回一个 400（`image_url is not supported` 对用户没有指导意义）。

### 23.6 编辑与导出

- **编辑消息**：附件**跟着进输入栏**，改错别字不会顺手把图弄丢
  （那是最容易让人骂街的一种丢失 —— 而且旧版本也翻不回来）。
- **JSON 备份**：附件原样进来、原样回去。图片**只有备份里那一份拷贝**。
- **Markdown 文稿**：文本附件按代码块导出；图片只留一行占位说明
  （内嵌 base64 会让文稿没法读）。需要连图一起带走就用 JSON 备份。

### 23.7 实现位置

| 文件 | 职责 |
|---|---|
| `data/Attachment.kt` | 数据类 + JSON 编解码 + 请求文本拼装 |
| `data/AttachmentImport.kt` | 图片解码/压缩/摆正、文本文件的 UTF-8 校验 |
| `ui/chat/RequestContent.kt` | 请求 content 组装 + token 估算（纯函数，有单测） |
| `ui/chat/Attachments.kt` | chip / 缩略图 / 全屏查看器（整屏、Fit、多图翻页） |
| `ui/chat/InputBar.kt` | `⊕` 入口与菜单 |
| `ui/chat/ChatScreen.kt` | 两个系统选择器、待发送状态 |

### 23.8 图片存储：内联与落盘并存

**适用于**：SimpleChat 1.1.2 及以上 · `data/AttachmentFiles.kt`

#### 为什么改

附件与正文在**同一行**。Android 的 `CursorWindow` 只有 2 MB，一行装不下一整张图，
那条会话就再也读不出来（`SQLiteBlobTooBigException`）—— 导入的历史里实测出现过
单行 7.4 MB，一点开就闪退。此前因此设了三道配额：单张 6 MB、单条消息 800 KB、
单次导入 24 MB。

#### 现在怎么存

| 形态 | `path` | `data` | 用在 |
|---|---|---|---|
| 内联 | `null` | base64 | 用户自己粘的图（已压到最长边 1600px）、旧数据 |
| 落盘 | 文件名 | 空串 | **导入的历史**、所有经 `writeConversation` 的写入 |

- 字节写在 `filesDir/attachments/<uuid>.<ext>`，行里只剩文件名；
- **三道配额全部取消** —— 行永远只有几百字节，与图片大小无关；
- JSON 列自描述，`path` 带默认值，**不需要改表**（v7 → v8 只加了引用表，见下）。

#### 三个边界

| 边界 | 做法 |
|---|---|
| 构造请求 | `outgoingAttachments()`：先把落盘读到内存（`toDataUrl()` 只认内联），再按模型能力过滤图片 |
| 导出备份 | `withInlineAttachments()`：读回 base64 内联，**备份格式不变** |
| 界面显示 | `rememberAttachmentImage()`：`path` 优先读文件，否则解 base64 |

#### 删除时的清理

`attachment_refs(path PRIMARY KEY, conversationId)` 登记落盘路径（每行几十字节）。
删除会话只查这张表 —— **不能**去读 `messages.attachments`，那是几兆的大 JSON，
读它正好撞上同一个 2 MB 限制（实测「删除所有历史对话」失败：
`Row too big to fit into CursorWindow requiredPos=954`）。

> [!NOTE]
> 数据库 v8 只新增引用表，老数据（内联 base64）原样保留、照旧可读。
> 文件缺失时按"原件缺失"处理：界面显示图标占位，不崩、也不影响发送。

#### 查看

点缩略图进**整屏**查看：深色底、`Fit` 铺满、点任意处关闭、多图左右翻页
（`HorizontalPager`，每页各解各的）。早先是居中卡片 + 固定高度盒子
（160–520dp），竖图两侧、横图上下会留出大片底色，看着像"图没加载完"。

## 26. 会话标题：AI 生成

### 26.1 行为

首轮回复落地之后，用一个 **flash 档模型**给会话起个标题（≤ 12 字）。

```
用户发出第一条消息
      ↓  （标题先用「首行截断」兜底，抽屉里立刻能看）
助手首轮回复完成
      ↓
用 flash 档模型生成标题 → 落库 → 顶栏与抽屉同步更新
```

放在**回复完成之后**而不是"发出去就生成"：拿到回复才知道这段在聊什么，
只根据提问猜出来的标题经常跑偏（"帮我写个开头" → 标题变成"写个开头"）。

### 26.2 三条护栏

任何一条不满足就**安静退出**，绝不给用户添麻烦：

1. **只在首轮**（会话里只有一条用户消息）—— 聊开了再改名字会让人莫名其妙；
2. **标题还没被人改过** —— 判据是"当前标题是否还等于 `derivedTitle(首条用户消息)`"。
   用户自己改的名字永远优先；
3. **每个会话只尝试一次**，且在**发请求之前**就打上标记 ——
   标题不值得为它反复烧 token，兜底标题本来就是能看的。

中途用户改了名怎么办？**落库前再确认一次**，变了就放弃。

### 26.3 为什么单独挑 flash 档

起标题是"短、快、便宜"的活：

- 用主力大模型**既慢又贵**，而且大模型更容易把标题写成一段小作文；
- 选择规则是"当前服务商目录里 **id 含 `flash`** 的那个"，目录里没有就退回当前模型。
  这样 DeepSeek 官方走 `deepseek-flash`、OpenCode Go 走 `deepseek-v4-flash`，
  不用把模型名写死。

同时还把 `thinking` 关掉（起标题不需要想）、`max_tokens` 压到 32。

### 26.4 清洗模型输出

模型非常爱加包装：`标题：xxx`、`"xxx"`、`《xxx》`、结尾还带个句号。
这些符号在抽屉里只占位置、不提供信息 —— `cleanGeneratedTitle()` 一律剥掉，
并且**只取第一行**（模型经常在第一行给标题、第二行开始解释）。

剥完为空（比如模型只回了一个 `。`）就返回 null，保留原名字。

### 26.5 一个必须成对维护的约定

`derivedTitle()` 既用来**兜底写库**，又用来**判断标题有没有被改过**。

规则一旦漂移（比如一边 take(20) 一边 take(24)），第 2 条护栏就永远不成立，
表现是"AI 生成的标题永远覆盖不上去" —— 从界面上完全看不出哪一环断了。
所以它被抽成纯函数并单测钉死。

### 26.6 标题的三个入口，和一个真相

标题一共有**三种**确定方式：

| 入口 | 什么时候用 |
|---|---|
| 抽屉里长按 → 重命名 | 在列表里顺手改 |
| AI 用 flash 档起名 | 首轮回复落地后自动 |
| **对话设置 → 对话名称**（本轮新增） | 正在写的时候改 |

前两条早就有了，但**它们互不同步**：顶栏停在旧标题上，抽屉却是新的。

#### 根因：同一件事有两处真相

`currentConversationTitle` 原先是个**只在切会话时同步一次的内存副本**：

```kotlin
// ❌ 只在 openConversation 里读一次库
currentConversationTitle = conversation.title
```

从抽屉改名只写库、不碰这个副本 → **顶栏停在旧标题上**。
而且只有顶栏看得出来（抽屉是 Room 的 Flow，天然是新的），
所以现象看着像"抽屉写错了"，其实是顶栏没跟上。

> 这和 §4.2 那两个死列是同一类问题：**同一件事有两处真相，而其中一处永远是陈旧的**。
> 区别只是死列无害，这个有害。

#### 修法：让库成为唯一的写入者

```kotlin
private fun observeTitle(conversationId: String) {
    titleObserverJob?.cancel()
    titleObserverJob = viewModelScope.launch {
        repository.observeConversation(conversationId).collect { entity ->
            if (currentConversationId == conversationId) {
                currentConversationTitle = entity?.title
            }
        }
    }
}
```

- 三种改名方式**都只写库**，界面侧一律由这条流回流，不可能各说各话；
- AI 起名那条路径也**不再自己同步顶栏**（原先有一句 `if (currentConversationId == …)`，
  现在删了）—— 少一处真相；
- 顺带把 §26.2 第 2 条护栏变准了：判据读的就是库里的值，**不会再被陈旧副本骗过**。

#### 名称框为什么要自己存一份草稿

不能直接把库里的标题当输入值：那个值是**异步观察**回来的，而流式期间会话行
还会被 checkpoint 反复更新 —— 直接绑库，打字打到一半就可能被旧值盖回去。

所以草稿留在本地、落库走 **400ms 防抖**（与「会话补充提示词」同一档；
逐字写库会让抽屉里的排序和标题一路乱跳）。外部改名时草稿会跟上，
但**正在输入时不打断**：

```kotlin
LaunchedEffect(title) {          // 刻意只把 title 当 key
    if (!focused) draft = title
}
```

不把 `focused` 一起放进 key 是有意的：失焦那一瞬间库里往往还是旧值
（防抖刚落库），那时重跑会把用户刚打的字盖回去。

### 26.7 真机验证（2026-09-22）

| 项 | 结果 |
|---|---|
| 抽屉改名 → 顶栏 | 立刻跟上（logcat 里能看到 Flow 的 emit）✓ |
| 名称框改名 → 顶栏 + 抽屉 | 两者同步 ✓ |
| 名称框在面板**最上面** | 排在「系统提示词」之前 ✓ |
| **改名不覆盖**（第 2 条护栏） | 首轮回复**流式期间**把标题改成 `GUARD-TEST`，回复 `DONE` 后标题**仍是 `GUARD-TEST`** ✓ |
| 只在首轮（第 1 条护栏） | 第二条消息后标题不变 ✓ |
| 每会话一次（第 3 条护栏） | 同上 ✓ |

至此**三条护栏全部真机验证过**（此前只有单测）。

## 27. 附件扩展：PDF 与 docx

在 §23 的基础上补两种最常见的文档。

| 格式 | 做法 | 需要识图模型 |
|---|---|---|
| `.docx` | 从 ZIP 里抽 `word/document.xml` 的文本 | ❌ 任何模型都能读 |
| `.pdf` | **把每页渲染成图**（系统 `PdfRenderer`） | ✅ 是当图片发出去的 |
| 旧版 `.doc` / `.xls` | 明确报错，提示另存为 docx | — |

### 27.1 为什么 PDF 是"渲染成图"而不是"抽文本"

**Android 自带的 PDF 库只能渲染、不能抽文本**（`PdfRenderer` 只给位图）。
要抽文本得引 PDFBox 之类的库，**+10MB** —— 对一个把"轻量"写在第一行的应用
不划算。而我们已经有了完整的图片链路（压缩、白底、base64、`image_url`），
把 PDF 页当图片发出去是**零新增机制**的做法。

代价要说清楚：**PDF 需要支持识图的模型**。所以：
- 面板上的提示写的是 `md / txt / docx / pdf`；
- 一次最多带 **12 页**（每页 ≈ 1024 token，再多会一口吃掉上下文），
  超出会明确告诉用户"共 N 页，只带了前 12 页"。

### 27.2 docx 的抽取为什么不用 XML 库

要的是**能读的正文**，不是还原排版。而 docx 的正文结构简单到可以直接
按几个标记替换：文字在 `<w:t>` 里、段落边界是 `</w:p>`。
为这一件事拉进一个 XML 库（以及它的安全配置、命名空间处理）不划算。

两个容易写错、且**不会报错**的地方（`DocxTextTest` 钉死）：

1. **段落标记要在剥标签之前处理** —— 先剥标签的话 `</w:p>` 自己就没了，
   整篇会挤成一坨；
2. **实体还原顺序** —— `&amp;` 必须**最后**。反过来时原文里的 `&amp;lt;`
   （也就是字面量 `&lt;`）会被先还原成 `&lt;`、再被当成实体还原成 `<`，
   凭空多出一个尖括号。

### 27.3 格式判定看文件头，不看扩展名

```
%PDF          → PDF
PK\x03\x04    → ZIP：再找 word/document.xml，找到就是 docx
D0 CF 11 E0   → OLE 复合文档（上古 .doc/.xls）→ 明确报错
其余          → 一律按纯文本试（严格 UTF-8 解码把关）
```

用户手里的文件叫什么名字都有可能。按扩展名 / MIME 判定，
只会制造"我的文件为什么打不开"这类无法解释的问题。

### 27.4 真机验证（2026-09-22，三份本机文件全部通过）

| 情形 | 结果 |
|---|---|
| 多页 PDF | 附件变成逐页缩略图，命名 `…pdf · 第 N 页`；**宽高比按页保留** ✓ |
| docx | 变成文本附件（显示字数）；**发给模型后答出**正文内容 ✓ |
| 旧版 `.doc`（OLE） | 明确报错 `不支持旧版 .doc / .xls 格式，请先另存为 .docx`，且**没有误加为附件** ✓ |

第三行是刻意的反例：用户手上这种"没有扩展名或扩展名混乱"的 `.doc` 很常见，
**必须给出可执行的下一步**，而不是"导入失败"。

### 27.5 两个只有真文件才暴露的坑

1. **PDF 页必须先铺白底再渲染。** 和图片附件同一个坑：PDF 页面本身是透明的，
   不铺白底直接压 JPEG 会得到黑块。
2. **docx 的段落标记要在剥标签之前处理。**
   `</w:p>` 如果留到剥标签那一步，会连同所有标签一起被抹掉，整篇挤成一坨。
   这两个都在 `DocxTextTest` 里钉死了（那类错误不会报异常，只会"读起来不对"）。

## 28. 消息元信息：模型与 token 数

### 28.1 行为

**碰一下 AI 回复**，操作按钮右边就出现 `deepseek-flash · 2 tokens`；
**手指一动（开始滚动）或碰别的消息就消失**，再点一下这条也能收起。

做成**瞬态**是刻意的：这两条信息属于"偶尔想看一眼"，常驻会在每条回复下面
挂一行没人读的小字 —— 而聊天界面里最贵的就是纵向空间。

范围只到 **AI 回复**：用户消息那行本来就刻意不放操作栏（§15.3 的"一个气泡下面
挂一排图标太吵"），而且它的点击已经是「编辑」，没有余量再挂一个手势。
`model` 本来也只有 AI 回复才有。

### 28.2 `messages.model`（DB v3 → v4）

```sql
ALTER TABLE messages ADD COLUMN model TEXT
```

只给**新生成的消息**写得进去。老数据是 NULL —— 界面上就**只显示 token 数，
不显示模型**，而不是拿当前模型猜一个填上去。老会话里可能混着好几个模型，
硬填一个就是**假信息**，比空着坏得多。

> 这一条在真机上验过：把某条的 `model` 清成 NULL（模拟 v3 数据），
> 界面就只有 `2 tokens`，没有模型名。

### 28.3 ⚠️ 一个手工构造的坑（`model` 在这里丢过一次）

`send()` 里那条流式占位的 `UiMessage` 是**手工 new 出来的**，不走
`MessageEntity.toUi()`：

```kotlin
messages += UiMessage(
    id = assistantId,
    role = MessageRole.ASSISTANT,
    content = "",
    reasoning = "",
    status = MessageStatus.STREAMING,
    parentId = user.id,
    model = settings.model.id,      // ← 漏掉过一次
)
```

**加了库字段之后，这里也要加一行** —— 症状很隐蔽：库里明明有，
界面上就是看不到，而且**只在"刚发出去那条"上看不到**（重新生成走
`reloadPath` 从库读回来，所以那条是好的）。

两处路径不一致，是这类字段漂移的温床。以后再往 `messages` 加列，
**先看这个手工构造点**。

### 28.4 token 数怎么算

```kotlin
TokenEstimate.of(message.content) + attachmentTokenEstimate(message.attachments)
```

算的是**它进上下文的那部分**：正文 + 附件（图片按每张上限 1024 记，§23.3）。

**思维链不计** —— 它只在本地展示，构造请求时不回传（§11.1）。算进去会让
这个数字与实际占用对不上，而"这条占多少上下文"才是看这个数的意义。

### 28.5 顺带发现的两个死列

`messages` 上还有 `tokens_in` / `tokens_out` 两列，**全项目没有任何读写** ——
和 `excluded`（§17.6）、`conversations.provider/model`（§4.2）一样是休眠列。
这次没有动它们（同一类"删了有风险、留着无害"的判断）。

真要用精确 token 数的话，它们本来就是位置 —— 但从 SSE 拿到的 usage 是
**整个请求**的量，拆不出"这一条多少"，所以即使填上也答不了本节的标题。

## 29. 启动行为 / 失败重试 / 拍照 / 两处对齐

### 29.1 启动一律停在「新对话」

原先启动会**恢复上次打开的会话**。代价是每次打开 App 都直接落进上一次那段
对话里，想开新的得先点「新建对话」。

放弃它的理由是这个 App 的日常用法 —— "想起来一句就写" —— 停在空白页
比落在半篇文章里更贴近它。

连带把 `lastConversationId` 这条偏好**整个删了**（字段 / DataStore key /
读写三处）。没人读的写就是死数据，同样的判断见 §4.2 与 §17.6。

### 29.2 失败的消息可以重试

失败的 AI 回复下面，错误文字**右边**多一个「重试」。

```
Unable to resolve host "api.deepseek.com": No address associated with hostname   [重试]
[复制] [重新生成] [编辑] [删除]
```

#### 为什么是「原地重试」而不是「重新生成」

`regenerate` 会**新增一个版本**（挂成兄弟，`‹ 1/2 ›`）。重试不该那样 ——
重试的是**同一次请求**，用户看到的还应该是那一格；冒出一个版本切换器
只会让人以为"换了个答案"。

```sql
UPDATE messages
SET content = '', reasoning = NULL, model = :model,
    status = 'STREAMING', errorMessage = NULL
WHERE id = :id
```

#### `model` 跟着一起写：用**当前**选的模型

用户很可能就是**换了模型才来点重试**的。所以不做"沿用当初失败那个模型"
的假设，重试即用当前模型，并把 `model` 一并更新 —— 否则界面会显示一个
根本没参与这次请求的模型名。

#### 为什么不做"可重试才显示按钮"

`StreamEvent.retryable` 判断的是**传输层**值不值得自动重试（429 / 5xx / 断网）。
而这里是人**手动**点：联网恢复了、API Key 改对了、换了个模型，任何一种
都可能让刚才的错误不再发生。按 `retryable` 藏起来反而会把路堵死。

> 真机验证：开飞行模式发消息 → 出现错误与「重试」→ 关掉飞行模式 →
> 点「重试」→ 消息转 `DONE` 并出回复，且**没有新增版本**。

### 29.3 附件面板补「拍照」

按官方那套补齐三个等宽入口：**拍照 / 相册 / 文件**。

| 入口 | 实现 | 需要权限 |
|---|---|---|
| 拍照 | `ACTION_IMAGE_CAPTURE` + **FileProvider** | ❌（相机权限归相机 App） |
| 相册 | `PickMultipleVisualMedia`（可多选） | ❌ |
| 文件 | `OpenMultipleDocuments`（可多选） | ❌ |

多选的一批按**选择器返回的顺序**逐个导入：读到一个就贴一个，不必等整批读完；
一个文件失败不会让其余选中的白读 —— 成功的照常留在待发区，
失败的攒到最后统一报一句（`attach_import_partial`）。
导入是异步的，期间用户可能切走会话，所以结果按**发起时的会话**归属：
还在原会话就写当前待发区，已经切走就写回那个会话自己的那一份，
不会把附件塞进新会话。

**必须走 FileProvider**：从 Android 7 起直接传 `file://` 会抛
`FileUriExposedException`。只开 `cacheDir/captures/` 一个子目录 ——
范围开到整个 cacheDir 是没必要的扩大面。

中转文件拍完立刻删：照片已经被解码、压到 1600px、转 base64 落库了，
它没有留下来的理由（`discardCapture`。失败也静默，删不掉最多占点缓存）。

`TakePicture` 的回调**只给一个 Boolean**，所以 URI 要在启动前建好、存下来 ——
否则回来时不知道去读哪个文件。

三个格子**等宽**而不是按内容自适应：三个入口地位平等，谁宽谁窄会让人
觉得有一个"更主要"。

### 29.4 关于页的"有的左对齐"是 `fill = false` 造成的

```kotlin
// ❌ 值这一列只按**自然宽度**排版，右边缘随文字长短飘
Text(value, textAlign = TextAlign.End, modifier = Modifier.weight(1.6f, fill = false))
```

`fill = false` 让它只取 `min(自身宽度, 分到的份额)` —— 短值的右边缘停在半路，
看起来就像"有的左对齐有的右对齐"，而且长值被挤到 61.5% 宽里折行。

修法是让值这一列**撑满剩余宽度**（`weight(1f)` 默认 `fill = true`），
`TextAlign.End` 才真的把每个值的右边缘对到同一条线上：

```kotlin
Text(label, ...)                       // 自然宽度
Spacer(Modifier.width(16.dp))
Text(value, ..., textAlign = TextAlign.End, modifier = Modifier.weight(1f))
```

顺带修掉一个副作用：值不再被压缩到 61.5%，长的许可名现在一行放得下。

> **规律**：`weight(..., fill = false)` 配 `TextAlign.End` 是自相矛盾的 ——
> `fill = false` 的语义是"按内容收窄"，而"右对齐到容器"要求它撑满。
> 两者只能取一个。

### 29.5 明确不做

**单条消息导出** —— 用户判断没有用，从待办里划掉。

## 31. 超长消息「下半部分点不动」

### 31.1 现象

用户消息超过约 **十万像素**（几十屏）后，气泡**下半部分点不动** ——
短按不进「修改输入」、长按也不弹菜单；**上半部分完全正常**。
短消息（几个字）从无问题。AI 回复也一直没问题。

### 31.2 怎么查的（先立测试台，再谈结论）

这个 bug 的第一版"根因"是**猜的**（"单个 `Text` 太高"），并且**猜错了** ——
按那个方向改成多 `Text` 分块渲染，**一点用都没有**。教训是：
先造一个**能自证位置**的现场。

1. **刻度消息**：直接往库里插一条 `L00001 … L010000` 的消息
   （每行 20 字符，1 万行 ≈ 21 万字 ≈ 70 万 px），滚到底能读到 `L01891` ——
   这就**证明了"确实停在几十万像素的深处"**，而不是"可能没滚到位"。
2. **每轮先跑正控**：先点一次顶部的 6 字消息（它必须点得动）。
   正控不过就**判定本轮作废** —— 否则检测方法本身失效时，会把假阴性当成结论。
   （第一轮跑就因为查错了弹窗标题而正控失败，及时发现、没让它污染结论。）
3. **嫌疑点做成运行时可切换**（读 app 私有目录一个 `diag.txt`，重启生效）：
   一次构建就能把假设逐个排除，而不是一版一版地重装手测。

同一深度、同一手势的结果对照：

| 气泡的写法 | 结果 |
|---|---|
| `clip(BubbleShapeOut)` + 水波纹（原状） | ❌ 点不动 |
| **只去掉 `clip`** | **✅ 点得动** |
| 只去掉水波纹 | ❌ 点不动 |

### 31.3 根因

**`Modifier.clip` 会给节点挂一层「带裁剪的图形层」。**
超长消息的气泡能有几十万像素高，**超过平台的图形层尺寸上限之后，这层就废了**：
内容照画，**命中测试却只认到某个高度为止** —— 表现正是"下半部分看得见、点不着"。

这也解释了**为什么官方客户端没这个毛病**：它自绘渲染，每条消息不走
Android 的图形层。**这是我们的实现踩的坑，不是"内容太长的必然代价"。**

⚠️ 与"单个 `Text` 太高"**无关**（已用分块渲染证伪）。也与水波纹无关。

### 31.4 修法

形状改由 `background(color, shape)` 画 —— 画一个圆角矩形，**不产生图形层**，
视觉与 `clip` 完全一致：

```kotlin
// ❌ 会挂图形层：.clip(BubbleShapeOut).background(colors.userBubble)
.background(colors.userBubble, BubbleShapeOut)
```

水波纹同理（它要靠 `clip` 才能裁成圆角）：换成**按下时垫一层同形状的浅色**，
形状天然正确、也不需要图形层，而且**垫在正文下面，正文颜色不受影响**：

```kotlin
val pressed by interaction.collectIsPressedAsState()
...
if (pressed) {
    Box(Modifier.matchParentSize().background(tint, BubbleShapeOut))
}
```

同类风险一并处理：**`AssistantBlock`**（AI 回复也可能很长）与
**Markdown 的代码块**（展开后可能很长）。

> **判据（值得记住）**：**永远不要给高度无界的节点挂 `clip` / `graphicsLayer`** ——
> 也就是消息正文这种"多长取决于用户粘了什么"的东西。
> 这是"长得对、跑起来坏、还只在大消息上坏"的那类坑。

### 31.5 超长消息自动折叠（体验，不是修法）

超过 **10 行**自动收起，正文往**右下角径向渐隐** + 圆形展开箭头（对齐官方）：

⚠️ **渐隐的绘制层级是个坑**：它必须画在**只包正文的那个 `Column`** 上 ——
它的下一个兄弟才是右下角那个箭头，于是箭头天然压在遮罩上方。
早先把它画到外面那层 `Column`（同时装着正文和箭头）上，箭头就被一起盖住了：
`drawWithContent` 在**该节点所有后代绘制完之后**才画。
**"兄弟先后顺序"只在同一层内作数，跨层不成立** —— 当时正是错拿它当理由。
箭头本身也要有**底色**：做成**半透明胶囊**（`card` 72% + `PillShape`）——
实心圆贴在气泡角上像一块硬片，太丑；但完全不带底色也不行，
只剩一根线会糊在淡出的文字里，仍像"被盖住"。
点一下展开、再点收起。**展开后照样整条都能点**（靠 31.4）。

「是否超行」用 `Text.onTextLayout` 的 `didOverflowHeight` 判定：

```kotlin
Text(
    text = message.content,
    maxLines = 10,
    overflow = TextOverflow.Clip,
    onTextLayout = { folded = it.didOverflowHeight },
)
```

⚠️ **那个负责测量的 `Text` 必须始终被组合。** 曾经把它放在 `if (folded)` 里，
而 `folded` 初始为 `false` —— 于是它永远不会被组合、`folded` 永远是 `false`，
**折叠从未生效过**（一个自锁的死循环，现象是"两个文本块原样铺着、没有箭头"）。

> 附注：折叠态把整条正文塞在**单个 `Text`** 里时，会超出无障碍树对长文本的上限，
> `uiautomator dump` 里**看不到这个节点**（展开态每块 2000 字，就看得见）。
> 以后调试长消息不要据此判定"没渲染出来"。

## 32. 流式渲染的方向与「切版本」的锚点

> beta.5。这一版**推翻了 beta.2 的一个方向性决定**，并把「切版本停在原处」从一个
> 反复出错的补丁收敛成一条规则。§13 的 beta.5 行是本节的摘要。

### 32.1 推翻 beta.2 的「底部为原点」

beta.2 把列表改成 `reverseLayout = true`（底部为原点），给的三条理由里**两条是错的**：

- ❌ **"流式追加不拽人"** —— 底部为原点下锚点钉在条目**底边**，而流式消息永远在
  底边继续长高，已显示内容被整体往上顶。实测 **0.5s 滑走 861px，且手拦不住**。
  这就是用户从第一轮起一直在报的"文字自己往上走"。
- ❌ **"是否贴底 = `index == 0 && offset == 0` 是布局的结构性质"** —— 只在
  "尾部恰好是下标 0"时成立；消息一旦比屏幕高、用户滚到中段，它就不代表
  "视口相对**内容**的位置"了。
- ✅ 只有"打开就在最新"这条是真的，而它不需要方向来换：见下。

改回**顶部为原点**（`reverseLayout = false`）：锚点钉条目**顶边**，流式消息长高是长在
自己**底边** = 视口**下方** → **屏上内容纹丝不动，零补偿代码**。
"点进去就在最新"改用 `LazyListState(firstVisibleItemIndex = Int.MAX_VALUE)`
（下标给到末尾之外，LazyList 自动夹到最后一条）—— 这是**布局参数**而不是一次滚动，
**首帧**就在底部。

**代价要说清**：贴底跟随不再免费 —— 新字长在视口下方，得主动滚。用逐帧循环
`scrollToBottom()`，并让位给手指（`isScrollInProgress`）与路径重建（`pathRebuilding`）。
与官方 `StreamingAutoScrollEffect` 同构（那套也是逐帧）。

### 32.2 根因：库的 `Markdown` 是**异步**解析的

**现象**：「向上滑有概率飞到很上面」「切版本闪一下 / 乱跑」，长文本才看得出来。

**机制**（字节码取证 + 逐帧探针实测）：

```
MarkdownKt         -> rememberMarkdownState        ← Markdown(content=…) 内部就是它
MarkdownStateImpl  -> Dispatchers, parseMarkdownFlow
State$Loading / State$Success
```

`Markdown(content = …)` 在 `Dispatchers` 上**异步**解析，状态先 `Loading` 再 `Success`。
于是**条目一进视口先按 `Loading` 的高度量一次，解析完才长到真实高度**——
实测同一条消息：**2946px → 13431px → 23355px**，第一次只有真实高度的约 **10%**
（真实 ≈ 1.7px/字，第一次 ≈ 0.17px/字，两者都严格跟字数成正比）。

而 LazyList 的锚点是 `(下标, 偏移)`，**偏移是内容里的绝对像素位置** ——
内容从 10% 长到 100% 时，同一个偏移落到完全不同的地方，**视口就跳**。
分块渲染（§6.3）把一次增长拆成了多次，所以是"分 2~3 步长起来"。

**修法**：用库的**同步**入口 `parseMarkdown(text)` 自己解析，再走 `Markdown(state = …)`
重载渲染 —— 高度**第一次测量就是真实的**，`Loading` 那一帧根本不存在；
再加一层**按块文本的缓存**（上限 256），滚出滚回不重解析。
同步解析的代价落在主线程，所以列表一变就在后台把各条的块**预热**进缓存
（从最新一条往前，那一头先被看到）。

**副产品**：`Markdown` 的异步解析协程不再随每次组合启动，流式期间少一条后台解析流。

### 32.3 「切版本」的锚点：用户对"底部"的定义是**操作栏可见**

操作栏（`‹ n/m › 📋 🔄 ✏️ 🗑`）在条目**末尾**。用户切版本时它必然在屏上，
而"停在原处"要保的就是**它没跑**。这一条我在前面几版里理解错了，
下面每一次都配着一个**实测过的反例**：

| 版本 | 锚成什么 | 反例（都是实测） |
|---|---|---|
| 1 | `(下标, LazyListItemInfo.offset)` | `offset` **有符号**，超长消息滚到中段是负值；直接喂给 `requestScrollToItem`（要无符号）→ 视口甩到 `fvi=0` |
| 2 | 取负修好 + `detached` 摘跟随 | 长消息"不在最底下"——偏移不动 ≠ 末尾不动 |
| 3 | **列表末尾** | 树模型下切到的兄弟版本**可能自带下游**（在那个分支继续聊过）→ 跳到**对话末尾** |
| 4 | **目标的下一条** | 下游被丢掉时那条**不存在**，`coerceIn` 夹回目标自己 → 视口被摆到目标的**顶边** |
| 5 | **目标的末尾在屏上的 y**（`endY`） | 两处：① 第一帧用**旧高度**估偏移，新版本短得多时目标**整个被推到视口之上**，LazyList 把它钳到后面的条目；② 修正只在**可见条目**里找目标 —— 目标已经不在视口里 → `size = null` → 直接放弃 |
| ✅ 6 | 同上，但分两段 | 见下 |

**最终形态（两段，因为新高度要等这一帧布局才知道）**：

1. **第一帧只求不越界**：`requestScrollToItem(target, 0)` —— 顶边贴视口顶边。
   它**永不越界**，所以目标一定留在视口里。
2. **下一帧拿新高度精确归位**：`scrollToItem(target, 新高度 - endY)`；
   目标若仍不在可见条目里，先 `scrollToItem(target, 0)` 把它拉进来再算。

`detached = true` 只在**切版本 / 删除**时置位（用户是在看/对比某一条，不是在等新内容）；
回到 `atBottom` 会自动恢复跟随 —— 所以"切最后一条"和"切中间那条"各归其位。
「重新生成 / 重试 / 编辑并重发」**一律不锚**：它们把这条换成一条**空的**流式回复，
高度先塌到十几像素（实测 18355 → 12），原来的阅读位置在新内容里根本不存在，
硬锚只会往上跳；而且用户按它们就是想看新回复，跟到底部才对。

**探针（现已删除）** 打的四类事实值得留着：锚点捕获 `CAP` / 第一帧 `PH1` /
每帧修正 `PH2` / 逐帧视口 + 每个可见条目的 `offset+size`。
前面七轮都在**猜机制**，这四类一上就同时暴露了两个根因（旧高度估偏移、修正只找可见条目）。
**教训：位置类 bug 不要靠推理，先把"谁写了什么、写之前之后各是多少"打出来。**

## 34. 对话内消息索引（左滑跟手）

### 34.1 目标

长会话里快速跳到之前的某条消息。几百条的会话里找三小时前那句话，此前只能一直往上滑。

### 34.2 交互

| 项 | 规则 |
|---|---|
| 触发 | 消息区**左滑跟手**（手指拖多少露多少），从**右侧**滑出索引面板 |
| 松手 | 位移 ≥ 25% 留下，否则弹回 |
| 关闭 | 点遮罩 / 右滑 / 返回键 |
| 行 | 每条一行截断，**当前所在的那条高亮**，点一条跳过去 |
| 边缘 | 面板**上下边缘加渐变**，文字在消失处渐隐 |
| 宽度 | 36% —— 瞄一眼跳过去，不是浏览 |

### 34.3 索引内容

- **只列用户消息**。用户说的话是章节标记，AI 回复是展开。
- **不分组**，纯时间倒序。
- **只放正文截断**，不带时间（时间是抽屉的语义）。
- **纯附件、无正文的用户消息**按附件占位，有正文时一律优先正文：

  | 情形 | 显示 |
  |---|---|
  | 一张图片 | `（图片）` |
  | 多个附件 | `（附件 3）` |
  | 单个文件 | `（文件·设定.md）` |

- **无用户消息的会话**显示一行「暂无消息」，不给空白面板。

### 34.4 与既有机制的关系

| 机制 | 关系 |
|---|---|
| 会话抽屉手势 | 抽屉＝**左边缘**右滑，索引＝**任意位置**左滑，一左一右不抢手势 |
| **横向块** | 落在可横滚块（代码块、宽表格）上时**横滚优先**，左滑只在别处生效 |
| 跟随滚动 | **按意图判，不按"手指动过"判**：左滑开索引是导航动作，不改跟随；只有真正跳走（视口离开底部）才停，回到 `atBottom` 自动恢复（§25.1） |
| 跳转落点 | 对齐**视口顶部**，复用 §25.3 切版本那套锚点机制（`pathRevision` + 视口偏移回摆），不另发明 |
| 返回键 | 加进 §15.7 的优先级链：面板之后、修改输入之前 |
| 消息点击 / 长按 | 都不能被吃掉（AI＝看元信息、用户＝编辑，长按＝菜单） |

### 34.5 实现要点

| 点 | 说明 |
|---|---|
| 手势 | `AnchoredDraggable` + `nestedScroll`。**不能用抢事件的 `pointerInput`**，否则会吃掉代码块的横滚；内层 `horizontalScroll` 只在能滚时消费，天然给出"横滚优先" |
| 高亮当前条 | 视口顶部那条所属的最近一条用户消息；**用 `derivedStateOf` 包住**，否则滚动时每帧重组 |
| 列表 | `LazyColumn` + 稳定 `key`（消息 id）；预览文本**别在组合里现算** |
| 索引刷新 | **打开时快照**，流式期间不实时重建；发送 / 重新生成 / 编辑重发后强制刷新一次 |
| 视觉 | 与抽屉同一套卡片与行高 |

### 34.6 验收（真机）

1. 几百条的长会话里，从底部跳到最前面的某条：**两步之内**（左滑 → 点一条）✅
2. 左滑出现索引时，**抽屉不会被误触发** ✅
3. 划在长代码块上是**滚代码**，不是开索引 ✅（不开索引）✅（长行可左右滚，行号栏不动）
4. 打开索引再关掉，**滚动位置不变** ✅
5. 长会话里左滑**不卡顿** ✅

### 34.7 实现记录

| 点 | 结论 |
|---|---|
| 面板 | 36% 宽、贴右缘、占满高度、左边两角 16dp 圆角、`AppShadow.RaisedElevation`；上下 20dp 用面板底色蒙出渐隐 |
| 面板列表 | **一露出就滚到当前那条**（`revealed > 0` 那一支里 `scrollToItem`）。原先永远从第 1 条开始排，人在长会话中段时高亮那条根本不在视野里。面板开着时消息区被遮罩挡着滚不动，`currentId` 不变，所以不必跟着实时走 |
| 遮罩 | `colors.scrim` + `graphicsLayer { alpha = progress * 0.32 }` —— 写在图层里，拖动一帧改一次不会引起重组 |
| 跟手 | `offset { IntOffset(面板宽 - 已露出, 0) }`，同样是布局期读状态 |
| 落位 | 位移 ≥ 面板宽 25% 留下；甩动速度 > 800px/s 直接按方向定 |
| 快照 | `remember(会话 id, 消息条数)` 建索引；预览文本在建索引时算完，不在组合里现算 |
| 当前条 | 视口顶那条所属的最近一条用户消息，`derivedStateOf` 包住 |
| 跳转 | `scrollToItem(index, 0)`。**刻意不走 §25.3 锚点** —— 那套是给"列表被整份重建"用的（切版本 / 删除），跳转时列表没动，`scrollToItem` 本来就是确定性的 |
| 跟随 | 跳转后 `if (!isAtBottom()) detached = true`；跳到底部那条不打断跟随 |

**踩到的坑：父层手势会抢掉子级的横滚。**

想当然的写法是"Compose 主事件遍历从子到父，内层 `horizontalScroll` 先消费"，于是直接上
`Modifier.draggable` —— **实测不成立**，父层手势节点先拿到事件并吃掉分步，代码块的横滚
一次都试不上。对照实验：把索引手势 `enabled = false`，同一根手指同样一划，代码立刻就滚了。

所以手势改成自己写（`messageIndexDrag`）+ **按落点显式让位**：能横滚的块用
`preferHorizontalScroll()` 登记自己的 `boundsInRoot()`，手指按下时落在登记过的区域里就
整段让给它。这套是确定性的，不依赖 Compose 的遍历顺序。

> **又一层**：登记完了发现代码块**还是**不滚 —— 这次跟索引无关。把索引手势整个摘掉，
> 代码块照样零位移。根因在渲染：`Text` 报给布局的是**约束宽度**而不是文字实际宽度，
> `horizontalScroll` 算出来的可滚距离恒为 0，横滚形同虚设（长行被切在右边界，划它没反应）。
> 这条是 §34 之外的既有 bug，记在 [`06-Markdown渲染.md`](06-Markdown渲染.md)。

**再两处：手势这层不参与嵌套滚动，消费了就谁也拿不回去。**

| 现象 | 根因 | 修法 |
|---|---|---|
| 点空白关不掉索引 | 遮罩的 `clickable` 收掉了面板，但手势层的 `onDragStopped` 紧接着又按"位移 0 ≥ 25% 阈值"落位回**留下**，把它拉了回来 | **只有真接管过（越过横向分步）才算松手**；点击一律不落位 |
| 会话抽屉右滑打不开 | 面板收起时手势层把**右滑**也认了。本层不是 `scrollable`、不参与嵌套滚动，`consume` 了抽屉就拿不回去 | 面板**收起时只认左滑**，右滑一个字节都不消费，整段让给抽屉 |

> 两条是同一类：**这一层的手势是"独占"的**，凡是"别的手势也能做"的方向，都得自己判清楚再让。
> `Modifier.draggable` 不会有这个问题（它走嵌套滚动，父层能接住），但它又会抢横滚 ——
> 两头不能兼得，所以干脆自己写、自己让。

**根因：带 `pointerInput` 的节点会把兄弟挡在命中路径之外。**

面板盖在消息区最上面、自身挂着 `messageIndexDrag`。实测整屏只剩它一条命中记录：
消息区、输入栏、代码块横滚一次事件都收不到 —— 上下滚不动、长按无反应、点不进输入框，
而抽屉（另一棵子树）一切正常。探针落在三层（遮罩层 / 消息区 / 输入栏）各打一条
DOWN·UP，只有最上那层有输出，下两层颗粒无收。

Compose 的命中测试按绘制顺序从上往下走，遇到第一个自带 `pointerInput` 的节点就不再
考虑它的**兄弟**；**父子之间不遮**，同一棵子树内照常下发。所以手势必须挂在浮层的
**父节点**（`Box(weight(1f))`）上，让面板、消息区、输入栏都成为它的后代，谁也不挡。

| 挂法 | 命中结果 |
|---|---|
| 挂在浮层自身（兄弟中最上） | 只有浮层收到事件，下面全瞎 |
| 挂在消息区（浮层之下） | 被浮层挡住，手势收不到 |
| **挂在浮层的父节点** | 全部收到；遮罩开着时仍由遮罩先接住点击 |

> 这条同时解释了 §34.6 第 3 条的"横滚拖不动"：不是手势打架，是**压根没进命中路径**。

## 35. 未发送草稿的持久化

### 35.1 需求

输入框里没发出去的内容**按会话分开**，进程被杀后不丢。

### 35.2 存储

Room 单开 `drafts` 表，`conversationId` 作主键（`db/Entities.kt` 的 `DraftEntity`）。

**不做成 `conversations` 上的两列**：「新对话」还没有会话行。用户打开应用就落在
「新对话」上，打一半被系统杀掉正是最常丢草稿的场景，而那一刻连会话 id 都没有、
更没有行可挂。未建会话时 key 取 `DraftEntity.NewConversation`（空串）。

**不进备份**：草稿是未发出的临时内容，随会话删掉就该消失，不值得为它改备份格式。

### 35.3 保存时机

| 时机 | 行为 |
|---|---|
| 打字 | 400ms 防抖落库（与「会话标题」那条同档） |
| 退到后台 / 离开本页 | **立刻存一次** —— 防抖最坏丢最后 400ms，而进程被杀往往就发生在这一刻 |
| 切会话 | 先把上一份写回它自己的 key，再读目标会话的 |
| 发送 | 立刻删行 |
| 草稿为空 | 删行，不留空壳 |

### 35.4 边界

- **「修改输入」期间存的是编辑前那份草稿** —— 那时输入框里是编辑文本，不是草稿；
  存进去下次打开会变成一句没头没尾的话，而且它指向的消息也没了。编辑本身不持久化。
- 超长**截尾**到 `DraftEntity.MaxChars`（100_000），只截落库那份、界面上照旧。防的是一次
  异常粘贴把 400ms 防抖变成持续写盘。
- 删除会话、导入备份 OVERWRITE 时同步清草稿 —— 不留指向已不存在的会话的死数据（§4.2）。
- 防抖落库认 `composerOwner`（换会话 effect 收尾时才更新）：换会话那一瞬间输入框里还是
  上一个会话的内容，而 key 已经是新的了，这时候写会把别人的草稿覆盖掉。

### 35.5 恢复

进会话自动读回，**光标放到末尾**。`BasicTextField` 的 `String` 重载不保证换文本后光标落在哪，
改成自己持 `TextFieldValue`：外部换文本时钉到 `TextRange(text.length)`，用户打字时不碰光标。

### 35.6 验收（真机）

1. v4 → v5 迁移：一条没丢 ✅
2. 打字后 `force-stop`，重开草稿还在 ✅
3. 按会话隔离：A 的草稿不出现在 B ✅
4. 切走落盘、切回还原 ✅
5. 发送后草稿行消失 ✅
6. 清空输入后草稿行消失 ✅
7. 删除会话后草稿行消失 ✅

单测 263 → **268**（`DraftTest` 5 项：空即删行、短文本原样、空白算内容、超长截尾、恰好到上限不截）。

## 36. 发第一条消息之前给会话起名

### 36.1 需求

「新对话」阶段就能定下会话标题，不用先发一条消息再说。

### 36.2 现状与改法

原先「对话名称」输入框在**会话还没落库时直接不显示**（`onTitleChange` 为 null），
`renameCurrentConversation` 也一进来就 `return` —— 想在发消息前起名，界面上没入口，
有入口也存不下。

改法是给「新对话」一个**待用标题**（`ChatViewModel.pendingTitle`）：那一刻会话行还
不存在，库里没有地方写，而内存里这份就是唯一的真相（§35 同一个处境，一起记在
`drafts` 表的 `DraftEntity.NewConversation` 行里，进程被杀也不丢）。[ensureConversation]
建会话时一并用上。

### 36.3 与 AI 起名的关系

标题一共有**四种**确定方式：抽屉里重命名、AI 用 flash 档起名、对话设置里的名称框、
以及这里的待用标题。**用户起过名就不让 AI 再覆盖** —— 建会话时若用上了待用标题，
直接把 `titleGeneratedFor` 置为该会话，`maybeGenerateTitle` 便整条跳过。

### 36.4 边界

- 待用标题 `trim` 后为空 / 全空白一律当**没起过名**（顶栏空一行比「新对话」更糟）。
- 会话建出来后由 `conversations.title` 接管，`drafts` 行里的 `title` 随即清空。
- 点「新建对话」不清待用标题 —— 与草稿一致，不因为点了新建就被吞掉。
- 抽屉里看不到待用标题（还没有行可挂），这是预期。

### 36.5 验收（真机）

1. 「新对话」的对话设置面板里出现「对话名称」✅
2. 起名后顶栏立刻跟着变 ✅
3. `force-stop` 重开，标题仍在 ✅
4. 发第一条消息，会话按这个名字建出来 ✅
5. `drafts` 行清空 ✅

单测 268 → **270**（`titleForStorage` 2 项：空白即没起过名、trim）。

## 37. 导入对账：不静默丢一条数据（v1.1.3）

### 37.1 问题

导入是唯一一种"用户拿一份外部文件、期望本地变成它的样子"的操作。旧实现里，单条会话
解析失败 / 超限 / 包损坏全是 `?` 掉：结果页照样说"导入完成"，用户只能凭记忆发现
少了东西（v1.1.3 之前"迁移后少了一个对话"的反馈来源）。

### 37.2 做法

统一对账模型 `ImportReport`：`expected`（归档声明几条）、`conversations` / `messages`、
`alreadyPresent`（按策略跳过）、`failures`（带原因）、`droppedImages`。
三条导入链路（本应用 JSON、Chatbox、DeepSeek）都产出同一份对账，结果页按
"声明 → 结果 → 差额 → 原因"的顺序说完整，例如：

```text
导入完成（DeepSeek 导出）：会话 4 个 · 消息 2310 条 · 归档共 5 个会话 · 1 个未能导入：会话文件损坏 ×1
```

失败原因枚举：`TOO_LARGE` / `UNREADABLE` / `EMPTY` / `BROKEN_TREE` / `MISSING_ENTRY` / `WRITE_FAILED`。
DeepSeek 归档额外按 `chat_session_index.json` 与 `chat_sessions/*.json` 双向核对：
索引里有而文件缺失的会话连**标题**一起报出来。

### 37.3 长会话：按字段切片解析

会话 JSON 的上限曾是 8 MB（整棵 `JsonObject` 树解析的内存是原文的 2~3 倍，20 MB 文本
能吃上百兆堆），超了就**整条静默跳过**。现改为 `JsonCursor`：只切原文不建树，
标量字段拼成小对象交给 kotlinx，消息数组**一次解析一条**并立刻压成 `ParsedMessage`。
峰值只与最大的单条消息有关，上限回到 24 MB，超限也会进 `failures`。

### 37.4 写库逐条隔离

一批 50 条共用一个事务（快）；整批失败时**退化为逐条重试**，坏数据只丢自己并记进
`WRITE_FAILED`，其余照常入库。回滚时同步恢复内存里的标题快照，避免同名判定串味。

### 37.5 包损坏

manifest 读不出来但目录形状像 DeepSeek → 直接报"压缩包不完整或已损坏（可能下载中断）"，
不再把 `Unexpected end of ZLIB input stream` 这类英文异常原样甩给用户（那是文件问题，
不是我们的 bug）。

## 38. 请求边界的图片校验（v1.1.3）

### 38.1 事故

v1.1.2 图片字节落盘后，Anthropic 请求路径保留了旧优化："附件条数没变就复用原对象"。
落盘附件的 `data` 是空的（要 materialize 才读回），条数当然没变 —— 于是历史里的图片
以**空 base64** 发出，服务端回 `You have uploaded an unsupported image`，而坏图在历史里，
**每一轮都会复现**，那个会话再也发不出去。

### 38.2 两层防线

1. **请求构造不再做这种复用**（`buildAnthropicRequestNow` 一律用整理后的附件）；
2. **边界层 `ApiImage`**：按文件头判真实格式（JPEG / PNG / GIF / WebP / BMP / TIFF /
   HEIC / AVIF），协议 enum 只认前四个；不收的格式本地转码为 JPEG；>1.5 MB 先缩到
   最长边 1600；解不开的图丢掉并提示（"有 N 张图片……本轮未发送"），而不是让整轮请求 400。

请求构造器再加一道兜底：`data` 为空或 `media_type` 非法的图片**不发**。
导入侧（DeepSeek / Chatbox）也按真实内容写 `mime`，减少"声明与内容不符"的历史数据。

## 39. 网络失败的可读化与断流重试（v1.1.3）

### 39.1 原始报文不是给人看的

`stream was reset: INTERNAL_ERROR` 是 OkHttp 的 IOException 文案，用户看到既不知道
发生了什么、也不知道下一步做什么。`NetworkErrors` 把异常类型 / HTTP 状态码映射成
一句话：断网 / 超时 / 证书 / 连接被中断，401 / 402 / 403 / 404 / 413 / 429 / 5xx
各有说法；服务端自己给了具体原因（如 `invalid api key`）时保留原文，原始异常进日志。

### 39.2 断流自动重试一次

只在**一个字都还没收到**时重发（`emittedAny == false`）：这种失败必然发生在内容下发之前，
重发是安全的；只要收到过任何事件就绝不重发 —— 那会出现两份回答，比让用户点一次重试更糟。

### 39.3 错误只显示一次

失败已经写在回复的 `errorMessage` 上（红字 + 重试按钮），不再同时弹一条一模一样的
banner。banner 只留给"与某条消息无关"的全局提示。
