## 48.1 结论

| # | 问题 | 结论 |
|---|---|---|
| 1 | 收藏对象 | 只做**消息级**。不做会话级收藏，也不新增会话置顶 |
| 2 | 分类 | **做收藏夹（文件夹）**：多夹、可新建 / 重命名 / 删除，一个内置「默认收藏夹」 |
| 3 | 归属 | 一条消息**只属于一个夹**。换夹 = 移动，不复制 |
| 4 | 标签 | **不做**。夹负责粗分类，「备注 + 全文搜索」负责细查找 |
| 5 | 数据模型 | 两张新表 `favorites` + `favorite_folders`；Room 版本 17 → **18** |
| 6 | 外键 | **不建**。收藏是用户资产，不随会话删除；断链由 Repository 显式做 |
| 7 | 唯一约束 | `UNIQUE(messageId)` + SQLite「多个 NULL 互不相同」= 单夹归属与「仅快照」共存 |
| 8 | 正文快照 | 保存收藏时刻的正文（≤ 10 万字）+ 独立预览列（280 字）。编辑原消息不改变收藏 |
| 9 | 分支 | **跨分支保留**。收藏挂 `messageId`，不挂路径 |
| 10 | 主入口 | 抽屉底部**与「设置」并列**的两格：`[🔖 收藏] [⚙ 设置]` |
| 11 | 消息入口 | **AI 操作栏在「删除」右边**加收藏按钮：单击进默认夹，**长按**弹底部选择面板 |
| 12 | 用户消息 | 没有操作栏（既有设计），收藏入口放在长按菜单（第 2 项） |
| 13 | 底部面板 | 自绘贴底面板（`Dialog`，与 `SourceSheet` 同一套）：选夹 / 新建夹 / 进管理页。不引 `ModalBottomSheet`（§25.5） |
| 14 | 收藏页分组 | 两种：**按会话**（默认）与**按收藏夹**。组头可折叠，偏好存 DataStore |
| 15 | 搜索 | 搜**收藏正文全文** + 备注 + 会话标题 + 夹名；命中片段围绕关键词取窗口 |
| 16 | 跳转 | **复用 `searchTarget` 通道**（只补三处，见 §48.8），不新造第二套定位机制 |
| 17 | 导出 | 复用多选分享管线；每组前加一行 `夹名 · 会话 · 日期` |
| 18 | 备份 | `backup.json` 增 `favoriteFolders` 与 `favorites`，**不升 `BackupFile.VERSION`** |

一句话：**收藏是一份「用户亲手挑出来、并且归了档的正文副本」**。
夹是归档方式，快照是它活过会话删除的凭据，两者都不能省。

## 48.2 背景与目标

### 48.2.1 背景

主用途是长文本创作（[01-PRD](01-PRD.md) §1.1）。写到几十轮之后，真正想留住的是**片段**：
一句世界观、一段满意的开头、一个突然想到的转折。

现在的四条路各有缺口：

| 现有能力 | 缺口 |
|---|---|
| 滚动翻找 | 长会话几百条，翻不动 |
| 全文搜索（§22.2） | 要先想起关键词。收藏的价值恰是「想不起关键词但记得有这句」 |
| 从这里新建对话（§21） | 把片段复制成新会话，代价太大，还会污染会话列表 |
| 复制到剪贴板 | 只有一格，跨会话、跨天就没了 |

第一版设计把「分类」判成过度设计。实测需求不成立：一旦收藏过 50 条，
「按时间倒序的一条长列表」本身就成了新的翻找负担。**夹是把「浏览」变回「查找」的最小手段。**

### 48.2.2 目标

1. 任意一条已完成的消息：**两次点击内**完成收藏（AI 回复一次）。
2. 不离开聊天页就能把这条放进**指定**夹（长按收藏按钮）。
3. 从抽屉一步打开收藏页，可在「按会话」与「按收藏夹」之间切换。
4. 搜索能命中**收藏正文里的任何位置**，并显示命中片段。
5. 点一条收藏，跨会话跳回原消息并定位；原消息不在当前分支时切回它的分支。
6. 原消息被编辑 / 删除、会话进回收站之后，收藏**仍可读、可复制、可导出**。
7. 收藏与夹随备份走：换机恢复后结构不变。

### 48.2.3 非目标

| 不做 | 理由 |
|---|---|
| 会话级收藏 / 第二种置顶 | 与 `conversations.pinned` 是同一件事的两种说法（同 §21.1 的判断） |
| 多标签 | 夹 + 备注 + 全文搜索已覆盖。标签要配筛选器、重命名、合并，收益不成比例 |
| 一条消息进多个夹 | 「归类」被拆成「拷贝」后，用户无法回答「这条到底在哪」，且去重、同步、导出都要重做 |
| 夹的嵌套 | 两级结构会让「这条在哪」变成一次树搜索；50 个扁平夹足够 |
| 收藏图片字节 | 图片在 `filesDir/attachments/`，复制一份等于把库再撑大一倍 |
| 收藏思考内容 | 与 Markdown 导出同一取舍（§22.1）：对着稿子，思维链是噪音 |
| 云同步 / 跨设备 | [01-PRD](01-PRD.md) §1.3 的 Non-Goals |
| 单条收藏的「导出」按钮 | 与 §29.5「单条消息导出明确不做」冲突；单条用「复制」 |
| 收藏计数红点 | 收藏不是任务，不需要催 |

## 48.3 用户场景

| # | 场景 | 现在 | 有了收藏夹 |
|---|---|---|---|
| S1 | 写第三章时想引用第一章那句设定 | 滑很久 | 抽屉 → 收藏 → 按会话分组 → 点那条 |
| S2 | 攒了 80 条，想只看「人物设定」 | 一条条翻 | 按收藏夹分组 → 展开「人物设定」 |
| S3 | 同一提问生成了三版，喜欢第二版 | 只能记住 `‹ 2/3 ›` | 收藏第二版；之后切到第一版也不影响 |
| S4 | 正在写，看到一句想存进「灵感」夹 | 要先收藏再去别处挪 | 长按收藏按钮 → 点「灵感」 |
| S5 | 记得某句台词但忘了在哪条会话 | 只能搜会话正文，且要翻命中 | 收藏页搜索「台词」→ 命中片段直接可读 |
| S6 | 整理会话时删了整条旧会话 | 挑出来的句子一起没了 | 收藏里还在（快照） |
| S7 | 换手机 | 靠 JSON 备份 | 备份带夹与收藏 |

S6 需要产品确认，见 §48.16 第 1 条。

## 48.4 交互流程

### 48.4.1 三处入口

```text
① 抽屉底部（与「设置」并列）
   ┌─────────────────────────────┐
   │ 🔖 收藏        │        ⚙ 设置 │
   └─────────────────────────────┘

② AI 回复下方操作栏（删除右边新增）
   ‹1/2›  📋  ▶  🔊  ✏️  🗑  🔖        …（弹性空白）…  🔄
                               ↑单击 = 收藏到默认夹 / 取消
                               ↑长按 = 底部「选择收藏夹」面板

③ 长按消息菜单（两种角色都有；用户消息只能走这里）
   复制 / 收藏·取消收藏 / 选择文本 / 分享 / … / 从这里新建对话 / ─── / 删除
```

为什么用户消息没有第二个入口：用户气泡一直**没有操作栏**（§15.3、§28.1 明确的选择），
它的长按菜单已有 7 项。再塞一个「收藏到…」会把菜单推到 8 项，而且和「收藏」重复。
用户消息的换夹走两条替代路径：收藏页行菜单「移到收藏夹」，或先收藏再到收藏页挪。

### 48.4.2 收藏动作与状态

| 触发 | 条件 | 行为 |
|---|---|---|
| 操作栏按钮 **单击** | 未收藏 | 收藏到默认夹，`Toast`「已收藏到「默认收藏夹」」 |
| 操作栏按钮 **单击** | 已收藏 | 取消收藏，`Toast`「已取消收藏」 |
| 操作栏按钮 **长按** | 任意 | 打开底部「选择收藏夹」面板；选中一个夹 = 收藏 / 移动过去 |
| 长按消息 →「收藏」 | 未收藏 | 收藏到默认夹 |
| 长按消息 →「取消收藏」 | 已收藏 | 取消收藏 |
| 收藏页行 → 长按 →「移到收藏夹」 | 任意 | 打开同一个面板 |
| 面板 →「新建收藏夹」 | 未满 50 个 | 文本对话框 → 创建 → 立即放入该夹 |
| 面板 →「管理收藏夹」 | 任意 | 关闭面板，进收藏夹管理页 |

按钮形态：

| 状态 | 图标 | 颜色 | 说明 |
|---|---|---|---|
| 未收藏 | `AppIcons.Bookmark` | `colors.processText` | 与同行图标一致 |
| 已收藏 | `AppIcons.BookmarkCheck` | `MaterialTheme.colorScheme.primary` | 形状仍是线框，靠勾与主题色区分 |

**流式中的回复没有收藏入口**：操作栏整行不出现（`actionable = !streaming`，§17.3），
长按菜单也不给。避免收藏半截内容。

不做「撤销条」：取消收藏后按钮仍在原处，再点一下就回来了。备注会随行删除 ——
这一点写进批量取消的确认框（§48.10.6）。

### 48.4.3 底部「选择收藏夹」面板

```text
                          ┌───────────────────────────────┐
   （对话页，压暗）        │  选择收藏夹              ✕   │
                          │  默认收藏夹   12        ✓     │
                          │  人物设定      7              │
                          │  灵感          3              │
                          │  世界观        0              │
                          │  ───────────────────────────  │
                          │  ＋ 新建收藏夹                 │
                          │  ⚙ 管理收藏夹                 │
                          └───────────────────────────────┘
```

| 项 | 规则 |
|---|---|
| 出现 | 长按操作栏收藏按钮；或收藏页行菜单「移到收藏夹」 |
| 高度 | 内容自适应，上限**屏高 70%**，超出时列表内部滚动（动作行固定在最下） |
| 排序 | 按 `sortOrder`，默认夹恒在第一位 |
| 每行 | 夹名 + 条数 + 当前归属的勾；点一行 = 收藏 / 移动并关闭 |
| 新建 | 弹 `AppTextInputDialog`（既有组件），成功后立即放入并关闭 |
| 管理 | 关闭面板，跳收藏夹管理页 |
| 关闭 | 点遮罩 / 点 ✕ / 返回键 |

实现方式是**自绘贴底面板**，与项目里已有的 `SourceSheet`（`ui/chat/SourceSheet.kt`）
同一套：`Dialog(usePlatformDefaultWidth = false, decorFitsSystemWindows = false)`
+ 全屏 `colors.scrim`（整层可点关闭）+ 贴底 `Column`（上两角 24dp、`colors.card`、
`navigationBarsPadding`、卡片内点击吞掉）。三点好处：

- **不用 `ModalBottomSheet`**：它自带满宽、蒙版、拖拽把手，摆进本应用像外来组件
  （§25.5 的结论、`Attachments.kt` 的注释）。
- **不存在 §34.7 那种命中遮挡**：`Dialog` 是独立窗口，不会把兄弟节点挡在命中路径外。
- **返回键天然正确**：返回触发 `onDismissRequest`，不必往 §15.7 的优先级链里再加一层。

做法上把 `SourceSheet` 里那层「scrim + 贴底卡片 + 高度上限 + 吞点击」抽成
`ui/common/BottomSheet.kt`，两处共用；不改视觉。

### 48.4.4 收藏页：两种分组 + 搜索

```text
┌ 顶栏 ────────────────────────────────────────┐
│ (←)  收藏              [分组切换]  [⋯]        │  按会话 ⇄ 按收藏夹
├ 搜索框 ──────────────────────────────────────┤
│ 🔍 搜索收藏内容…                              │
│ [全部]  [我]  [AI]                            │  角色筛选（有收藏时显示）
├ 列表 ────────────────────────────────────────┤
│ ▾ 第一章 · 第六章草稿                 8 条    │  组头（按会话）
│    我 · 11-27  那句话是这么写的…              │
│    AI · 11-26  「风从北面来……」               │
│ ▸ 人物小传                            3 条    │  折叠
│ ▾ 默认收藏夹                         12 条    │  组头（按收藏夹）
│    …                                          │
└──────────────────────────────────────────────┘
```

| 模式 | 组头 | 组序 | 组内序 | 空组 |
|---|---|---|---|---|
| 按会话（默认） | 会话标题 + 条数 | 组内最近一条收藏时间倒序 | 收藏时间倒序 | 不显示（没有收藏的会话不进列表） |
| 按收藏夹 | 夹名 + 条数 | `sortOrder`（默认夹第一） | 收藏时间倒序 | **显示**「0 条」，展开后一行「这个收藏夹还是空的」 |

按夹分组**必须显示空夹**：那一屏是这个功能的「结构视图」，隐藏空夹会让人以为夹没了。

搜索态（输入非空）：

- **平铺，不分组**。结果按收藏时间倒序；每行补 `夹名 · 会话标题` 与命中片段。
- 命中范围：收藏正文全文（`content`）、备注、会话标题、夹名。
- 片段：SQL 里围绕命中处取 160–200 字，再交给已有的 `snippetAround()` 压平与补省略号
  （与搜索结果同一套，§22.2）。
- 上限 100 条；超出显示「还有更多结果，请补充关键词」。
- 清空搜索框回到分组列表，折叠状态保持不变。

折叠状态只记在 ViewModel（离开页面即重置）；分组偏好写 DataStore
（`favorites_group_mode`），下次打开还是上次那一种。

### 48.4.5 收藏夹管理

入口：收藏页顶栏 ⋯ →「管理收藏夹」；底部面板 →「管理收藏夹」。
落点：`Route.FAVORITE_FOLDERS(depth = 2)`。

```text
(←)  收藏夹                            ＋
──────────────────────────────────────
默认收藏夹        12 条        默认     ⋯
人物设定           7 条                 ⋯
灵感               3 条                 ⋯
```

| 动作 | 规则 |
|---|---|
| 新建 | 文本对话框；≤ 20 字；去空白后非空；不与他人重名；上限 50 个 |
| 重命名 | 同上校验；默认夹**也可以改名**（它只是默认落点，不是固定文字） |
| 删除 | 确认框写明「其中 N 条收藏会移到『默认收藏夹』」；**不删任何收藏** |
| 默认夹 | 没有「删除」项；行尾一个「默认」小字 |
| 排序 | MVP 按 `sortOrder`（= 创建顺序），不提供拖动；P1 再加 |

### 48.4.6 状态图

```text
消息 ──单击收藏按钮/菜单「收藏」──▶ 已收藏（默认夹）
  ▲                                  │
  │                                  ├──长按按钮/行菜单──▶ 选择面板 ──选夹──▶ 已收藏（该夹）
  └──────单击按钮/菜单「取消收藏」────┤

```

## 48.5 数据模型与迁移

### 48.5.1 两张表

```sql
CREATE TABLE IF NOT EXISTS `favorite_folders` (
  `id`        TEXT NOT NULL,
  `name`      TEXT NOT NULL,
  `sortOrder` INTEGER NOT NULL DEFAULT 0,
  `createdAt` INTEGER NOT NULL,
  `updatedAt` INTEGER NOT NULL,
  PRIMARY KEY(`id`)
);

CREATE TABLE IF NOT EXISTS `favorites` (
  `id`                TEXT NOT NULL,
  `messageId`         TEXT,
  `conversationId`    TEXT NOT NULL,
  `conversationTitle` TEXT NOT NULL,
  `folderId`          TEXT NOT NULL DEFAULT 'default',
  `role`              TEXT NOT NULL,
  `content`           TEXT NOT NULL,
  `preview`           TEXT NOT NULL,
  `note`              TEXT,
  `hasAttachments`    INTEGER NOT NULL DEFAULT 0,
  `messageCreatedAt`  INTEGER NOT NULL,
  `createdAt`         INTEGER NOT NULL,
  PRIMARY KEY(`id`)
);

CREATE UNIQUE INDEX IF NOT EXISTS `index_favorites_messageId` ON `favorites` (`messageId`);
CREATE INDEX IF NOT EXISTS `index_favorites_createdAt` ON `favorites` (`createdAt`);
CREATE INDEX IF NOT EXISTS `index_favorites_folder_created` ON `favorites` (`folderId`, `createdAt`);
CREATE INDEX IF NOT EXISTS `index_favorites_conversationId` ON `favorites` (`conversationId`);
CREATE INDEX IF NOT EXISTS `index_favorite_folders_sortOrder` ON `favorite_folders` (`sortOrder`);
```

> 真相是 Room 生成的 `app/schemas/com.simplechat.app.db.AppDatabase/18.json`
> （`exportSchema = true`）。上面这份是给人读的版本，处理方式同 §4.2。

### 48.5.2 字段取舍

| 字段 | 理由 |
|---|---|
| `favorites.messageId` 可空 | 三件事共用：彻底删除后的「仅快照」、导入后没对上原消息、未来的会话级收藏 |
| `favorites.folderId` 带默认值 `'default'` | 老行（若有）与新写入都能落到兜底位置；不需要额外的 NULL 分支 |
| `conversationTitle` 快照 | 会话不存在时列表仍要有标题；查询优先用 `conversations.title`，取不到再回落 |
| `preview` 与 `content` 分列 | 列表只读 `preview`，**永不**把 `content` 拉进游标（§48.13） |
| `hasAttachments` | 纯图片消息正文为空，界面据此显示「（含附件）」而不是一行空白 |
| 无 `reasoning` / `active` / `parentId` | 非目标，或会变成第二份真相 |
| `favorite_folders.sortOrder` | 决定分组顺序；`updatedAt` 用于「最近改名的夹」P1 排序 |

### 48.5.3 默认收藏夹

| 项 | 值 |
|---|---|
| `id` | 常量 `FavoriteFolders.DefaultId = "default"` |
| 初始名 | 「默认收藏夹」（进字符串资源，随语言） |
| 创建 | 迁移里 `INSERT OR IGNORE` 一行；Repository 在读取 / 收藏前再调一次 `ensureDefaultFolder()`（幂等兜底） |
| 删除 | **不允许**（UI 不给入口，DAO 侧 `DELETE ... WHERE id != 'default'` 再兜一层） |
| 改名 | 允许 |

名字随语言切换的问题：首次创建时写入当前语言的名字，之后不跟随切语言。
若要跟随，就得为它保留「未改名」标记 —— 为一个夹的文案加一列不值得。这条写进已知限制。

### 48.5.4 单夹归属与唯一约束

`UNIQUE(messageId)` 一举三得：

1. 同一条消息只能收藏一次 → `INSERT OR IGNORE` 幂等；换夹走 `UPDATE folderId`。
2. SQLite 的唯一索引把多个 `NULL` 视为互不相同 → 「仅快照」行要多少有多少。
3. 「一条消息在两个夹里」这件事在库里**根本表达不出来** —— 这是有意的约束，
   不是副作用（§48.2.3）。

重复收藏不更新 `createdAt`、不覆盖备注、**不改夹**：第一次归档的决定优先。
要换夹得显式选一次（长按按钮 / 行菜单），这样「我又点了一下」永远不会偷偷搬走东西。

### 48.5.5 为什么没有外键

| 候选外键 | 加上会发生什么 | 结论 |
|---|---|---|
| `favorites.folderId → favorite_folders(id) ON DELETE CASCADE` | 删夹 = 连带删掉其中的收藏 | **不加**（删夹只搬移） |
| `favorites.folderId → favorite_folders(id) ON DELETE SET NULL` | 语义对，但要给 `NOT NULL DEFAULT` 的列配可空外键，自相矛盾 | **不加** |
| `favorites.messageId → messages(id) ON DELETE SET NULL` | 合理，但 Room 迁移要逐字对齐约束，收益不抵 | **不加** |

代价是清理与搬移必须由 Repository 显式做（§48.6.3）。换来的保证是：
**没有任何一条 SQL 能顺手删掉收藏。**

**为什么放在顶层、而不是挂在会话下面**：收藏可能指向已被删除的会话，挂在

**为什么不升 `version`**：`OwnBackupStream.open()` 对版本做严格相等校验
（`check(version == BackupFile.VERSION)`）。升到 3 的直接后果是**旧版 App 拒绝导入新备份**，
整套数据都进不去。不升版本时旧版只是忽略多出来的两个字段（`ignoreUnknownKeys = true`）。
附件、`timeline`、`compactions` 三次加字段都是这么办的（§14.4）。

| 情形 | 行为 |
|---|---|
| 旧备份（无两个字段）→ 新版导入 | 只有默认夹、没有收藏。**不报错** |
| 新备份 → 旧版导入 | 忽略两字段，会话 / 消息 / 预设 / 摘要正常。**只丢收藏与夹** |
| 新备份 → 新版导入 | 夹按 `id` upsert；收藏按 `id` upsert；`folderId` 落空的归默认夹 |
| 单会话导出 | **不带收藏、不带夹**（与「不带全局预设」同一条理由） |
| ZIP 归档 | 自动带上；`manifest.json` 增 `favoriteFolders` / `favorites` 两个计数 |

组头（按会话）：

```sql
SELECT f.conversationId AS id,
       COALESCE(c.title, f.conversationTitle) AS title,
       COUNT(*) AS count,
       MAX(f.createdAt) AS lastAt
FROM favorites f
LEFT JOIN conversations c ON c.id = f.conversationId
GROUP BY f.conversationId
ORDER BY lastAt DESC
```

组头（按夹，**含空夹**）：

```sql
SELECT d.id, d.name, d.sortOrder,
       (SELECT COUNT(*) FROM favorites f WHERE f.folderId = d.id) AS count
FROM favorite_folders d
ORDER BY d.sortOrder ASC, d.createdAt ASC
```

组内：

```sql
SELECT f.id, f.messageId, f.conversationId, f.role, f.preview, f.note,
       f.hasAttachments, f.messageCreatedAt, f.createdAt
FROM favorites f
WHERE f.folderId = :folderId        -- 或 f.conversationId = :cid
ORDER BY f.createdAt DESC
LIMIT :limit
```

搜索（命中正文任意位置，片段在 SQL 里开窗）：

```sql
SELECT f.id, f.messageId, f.conversationId, f.role, f.preview, f.note,
       f.createdAt, f.messageCreatedAt, f.folderId,
       COALESCE(c.title, f.conversationTitle) AS conversationTitle,
       (SELECT name FROM favorite_folders d WHERE d.id = f.folderId) AS folderName,
       CASE WHEN instr(lower(f.content), lower(:query)) > 0
            THEN substr(f.content,
                        max(1, instr(lower(f.content), lower(:query)) - 40),
                        max(160, length(:query) + 80))
       END AS snippet
FROM favorites f
LEFT JOIN conversations c ON c.id = f.conversationId
WHERE length(:query) > 0
  AND (:role = '' OR f.role = :role)
  AND (instr(lower(f.content), lower(:query)) > 0
       OR instr(lower(COALESCE(f.note, '')), lower(:query)) > 0
       OR instr(lower(COALESCE(c.title, f.conversationTitle)), lower(:query)) > 0
       OR instr(lower(COALESCE((SELECT name FROM favorite_folders d
                                WHERE d.id = f.folderId), '')), lower(:query)) > 0)
ORDER BY f.createdAt DESC
LIMIT :limit
```

三处刻意的写法：

- **`instr(lower(…))` 而不是 `LIKE '%…%'`**：`%` 与 `_` 在 LIKE 里是通配符，用户搜 `100%`
  会变成「100 加任意内容」。仓库里已有同类测试（搜索把 `%` 当字面量）。
- **片段在 SQL 里开窗**：整条正文可能十万字，交给 Kotlin 之前先切到 160–200 字；
  之后再用 `snippetAround()` 压平空白与补省略号（同一个纯函数，不在收藏页复制一份）。
- **状态是算出来的，不是存出来的**（`LIVE` / `TRASHED` / `GONE` / `CONVERSATION_TRASHED`）：
  存一份就要在删除、恢复、导入、删夹四条路径上同步，§4.2 的「两处真相」正是这么来的。

## 48.7 语义：编辑、删除、分支、夹

### 48.7.1 总表

| 事件 | 收藏行 | 列表显示 | 点一条 |
|---|---|---|---|
| 编辑原消息（「保存」原地改） | 不变 | 正常 | 跳到原消息看到**改后**正文；收藏里仍是改前快照 |
| 「保存并发送」/ 重新生成（新增同父版本） | 不变 | 正常 | 跳到那一版（收藏的是旧版本那条 id） |
| 原消息进回收站 | 保留，`messageId` 不动 | 徽标「原消息在回收站」 | 提示 +「去回收站」 |
| 消息在回收站被彻底删除 | 保留，`messageId` 置空 | 徽标「原消息已删除」 | 只读：复制 / 导出 / 取消 |
| 会话进回收站 | 保留 | 徽标「会话在回收站」 | 提示 +「恢复会话」 |
| 会话彻底删除 / 15 天过期清理 | 保留，`messageId` 置空 | 徽标「来源会话已删除」 | 只读 |
| 切到别的分支 | 不变 | 正常 | 跳到该消息，并**切回它所在的分支** |
| 换夹 | 只改 `folderId` | 跟随新夹 | 正常 |
| 删除收藏夹 | 行保留，`folderId` 改默认夹 | 出现在默认夹组 | 正常 |
| 「删除所有历史对话」 | 全部删除 | 空态 | — |

### 48.7.2 为什么跨分支保留

收藏挂 `messageId`，切版本只改同父兄弟的 `active`（§18.2），两件事不相交 ——
这是免费的，不需要额外机制。

### 48.7.3 为什么保存快照

1. **删除后仍可读。** 没有快照，收藏会在用户整理会话时静默失效。
2. **列表不必读 `messages.content`。** 否则一页 50 行正文，撞 `CursorWindow`（§23.8）。
3. **导出的东西与看到的一致。** 用户收藏的是当时那一版。

两个代价：

- **编辑不跟随。** 改完错别字收藏里还是旧文本；P1 给「用当前正文更新快照」，MVP 的
  替代办法是取消收藏再收藏。
- **占空间。** 单条 ≤ 100 000 字符（与 `DraftEntity.MaxChars` 同档，§35.4）。
  1000 条、平均 2 KB ≈ 2 MB，不值得为它做去重或压缩。

### 48.7.4 快照与预览生成（纯函数，有单测）

`favoritePreview(content)`：统一换行 → 连续空行压到最多一个空行 → 去首尾空白 →
取前 280 字（按字符，不按字节）→ 截断补 `…`。

`favoriteContent(content)`：统一换行 → 去首尾空白 → `take(100_000)`。
**不剥 Markdown 标记**：`**加粗**` 在列表里读起来仍是原文，剥了反而可能歧义。

## 48.8 跳转：从收藏回到原消息

### 48.8.1 结论：复用 `searchTarget`，不新造通道

第一版写的是「不能借用 `searchTarget`」，那个判断错了，两处事实也说错了。更正如下：

| 第一版的说法 | 事实 |
|---|---|
| 「4 秒后补白消失，内容会跳一下」 | **不会。** `searchSpacePx` 只在 `messages.lastOrNull()?.id` 或 `searchPlacementReset` 变化时归零；`dismissSearch()` 不重置它，真正的复位发生在 `resumeFollowing()`（用户回到列表底部的那一刻，§25.1） |
| 「`openConversation` 的同会话早退会吞掉定位」 | **反了。** 早退条件是 `id == currentConversationId && targetMessageId == null`，带目标时不早退 —— 它会走完整切换（`stop()` + 清空 + 重载） |

`searchTarget` 本身没有缺陷。它是「把会话打开到某一条」的唯一通道，而且已经解决了
最麻烦的时序：等 `switching` 结束 → 按 key 找下标 → `scrollToItem` → `markSearchReady`。
再写一套，等于把这套时序抄一遍，是 §17.4 那类「两条路维护同一件事」的老陷阱。

### 48.8.2 三处必须补的改动

| # | 现状 | 改动 |
|---|---|---|
| 1 | `openConversation(id, target)` 带目标时也走完整切换：`stop()` 会掐掉正在生成的回复，列表还会闪一下 | 同会话时走轻量路径：目标在活跃路径 → 只置 `searchTarget`，让界面滚动；目标在非活跃分支 → 先 `reveal` + `reloadPath`，**不重建观察者、不清会话** |
| 2 | `revealSearchMessage` 内部 `check(...)`，失败抛异常，被 `openConversation` 的通用 `catch` 变成「会话加载失败」 | 改成返回 `Boolean`（搜索调用点同步处理 false），收藏侧拿到 false 就「打开会话 + banner」 |
| 3 | 空 query 时 `SearchHighlightHost` 仍会 `withTimeoutOrNull(4000)` 等一个永不到来的命中 | `query.isEmpty()` 时直接 `finish()`，省掉 4 秒的「搜索态」尾巴 |

第 2 条对搜索本身也是净改进：现在搜索跳到一个坏边界会报「会话加载失败」，
那句话对用户没有指导意义（§37.2 的同一取向）。

### 48.8.3 流程

```text
点一条收藏
  ├─ 跨会话 ── openConversation(cid, messageId, query = "")
  │              └─ 加载完 → searchTarget 生效 → 定位（38% 顶部留白）
  ├─ 同会话、在活跃路径 ── 只置 searchTarget（不 stop、不重载）
  ├─ 同会话、在非活跃分支 ── 停流式（切分支的既有语义）
  │                          → revealFavoriteMessage → reloadPath → 定位
  ├─ 会话在回收站 ── 对话框：恢复并打开 / 取消
  ├─ 原消息在回收站 ── 对话框：去回收站 / 取消
  └─ 原消息已删除 ── 对话框：复制快照 / 取消
```

三处细节：

- 定位后 `detached = true`（已有 `SideEffect`），避免流式把视口拽回底部。
- **不做闪烁高亮**：搜索的高亮来自命中范围，收藏没有关键词。38% 留白 + 目标在视口内
  已经足够表明「就是这条」。
- 返回列表底部时 `resumeFollowing()` 会顺带清掉 `searchTarget` 与补白，回到正常阅读态。

## 48.9 导出与分享

| 入口 | 范围 | 产出 | 复用 |
|---|---|---|---|
| 收藏页多选 → 导出 MD | 选中 N 条 | `.md`（系统文件选择器） | `MessageShareDocument` + `writeSharedMarkdown` + `MessageShareFiles` |
| 收藏页多选 → 复制文本 | 选中 N 条 | 剪贴板 | 同上（文本分支） |

| 单条 | 1 条 | 不给导出按钮 | 行菜单「复制」；要出文件回原消息用既有「分享」 |
| 图片（P1） | 选中 N 条 | PNG | `NativeShareRender` |

**每组前加一行来源**：`> 默认收藏夹 · 第一章 · 2026-11-27`。
现在 `MessageShareDocument(title, groups, excerptFooter)` 没有位置放，加一个带默认值的字段：

```kotlin
data class MessageShareDocument(
    val title: String,
    val groups: List<MessageShareGroup>,
    val excerptFooter: List<String> = emptyList(),
    /** 与 groups 同序；空串 = 不显示。收藏导出填「夹名 · 会话 · 日期」。 */
    val groupHeaders: List<String> = emptyList(),
```

默认值保证现有分享调用点一行不改（§19 的行为不变）。图片渲染器 MVP 忽略该字段。

上限沿用 §19：图片 20 万字符 / 80 页；Markdown 超 10 万字符不进剪贴板。
全部导出时逐条 `bodyById` 边读边写。

## 48.11 边界与异常

| 情形 | 行为 |
|---|---|
| 流式回复 | 操作栏整行不出现，长按菜单也没有收藏项 |
| 正文为空、有附件 | 允许收藏，`hasAttachments = 1`，行显示「（含附件）」 |
| 正文与附件都空（失败回复） | 允许收藏；摘要显示「（空）」 |
| 重复收藏 | `INSERT OR IGNORE`：不新增行、不满 `createdAt`、不覆盖备注、**不改夹** |
| 收藏时消息刚被删（竞态） | `NOT_FOUND` → 提示「这条消息已不存在」，不写脏行 |
| 夹名空白 / 超 20 字 / 重名 | 对话框内就地提示，不提交 |
| 夹已达 50 个 | 「新建」置灰 + 说明；「管理」仍可用 |
| 删除当前正在使用的夹 | 行保留并改挂默认夹；列表即时跟随 |
| 删除夹时其中收藏被别处清空 | 事务内 `moveAll` 影响 0 行也算成功 |
| 备注超长 | 输入框限 200 字，落库前 `trim()`；全空白 = 清空 |
| 备注对话框打开时收藏被删 | 按 `id` 更新，影响 0 行即静默放弃 |
| 搜索词含 `%` / `_` | 按字面量处理（`instr` 而非 `LIKE`） |
| 搜索命中在正文深处 | SQL 开窗 + `snippetAround()`，行里能看见关键词 |
| 搜索无结果 | 一行「没有匹配的收藏」，保留搜索框与筛选 |
| 组内条目过多 | 单组一次读 ≤ 500 条，超出显示「还有更多，请用搜索」 |
| 备份里的夹缺失 | 该收藏归默认夹（导入收尾的一条 SQL） |
| 备份条目损坏 | 逐条解析，坏的跳过并计入 `ImportReport.failures`（§37.2 对账） |
| 数据库升级失败 | 不设 `fallbackToDestructiveMigration`，宁可崩（§4.2） |

## 48.13 性能

### 48.13.1 列表与分组

| 关注点 | 处理 |
|---|---|
| 组头 | 按会话：`GROUP BY conversationId`（1e3 行量级，毫秒内）；按夹：≤ 50 行 + 计数子查询 |
| 组内 | **展开时才查**，折叠组零 IO；`folderId` / `conversationId` 各有索引 |
| 组内上限 | 500 条；超出提示用搜索（不虚拟化超长组） |
| 平铺 / 搜索 | keyset 分页，50 行一页；搜索上限 100 条 |
| 每页字节量 | 只取 `preview`（≤ 280 字，约 1 KB）→ 一页约 50 KB，远低于 `CursorWindow` 的 2 MB |
| 大字段 | 列表查询**永不** select `content`；正文只在复制 / 导出时按 `id` 单条读 |
| 单条读取 | `content ≤ 100 000` 字符（约 300 KB UTF-8），单行安全 |
| 状态 | 由 `CASE` 表达式算，不做冗余列 |
| 重组 | 行 `key = row.id`；摘要与片段在建行数据时算好，不在组合里现算（§34.5） |

### 48.13.2 搜索成本

搜索要扫 `content`。收藏量级小，这个代价可以接受，但要写清上限：

- 500 条 × 平均 5 KB ≈ 2.5 MB，`instr` 一遍是毫秒级；
- 极端 5000 条 × 100 KB = 500 MB，会到百毫秒以上 —— 这时输入防抖仍然有效，
  但结果延迟可见。降级方案（不在 MVP）：只搜 `preview`，或给 `content` 建 FTS5 虚表
  （中文要配分词器，§22.2 明确拒绝过）。
- `lower(content)` 会为每行生成一份小写副本；这是既有全文搜索（§22.2）已经在付的成本。

### 48.13.3 10 万级消息下的成本

驱动表永远是 `favorites`（1e3 量级），`messages` 只按主键回查 ≤ 50 行。语料总量只影响
主键 B-tree 深度（10 万行约 3–4 层），可忽略。反面写法是拿 `messages` 当驱动表按
`conversationId` 关联收藏 —— 那会扫 10 万行。

### 48.13.4 写与导出

收藏 = 1 次单行读 + 1 次单行写，异步做，不阻塞 UI。导出逐条 `bodyById` 边读边写；
**不做** `SELECT * FROM favorites WHERE id IN (:ids)`：50 行 × 300 KB 会一次性撑爆游标窗口
（§23.8 的同款错误）。

## 48.16 开放问题

**1. 删除会话时，收藏应保留还是连带删除？**

本稿选「保留快照」：我挑出来的句子不该因为整理会话而消失（S6）。代价是用户以为删干净
的东西仍在收藏里。折中方案：删除确认框里加一个默认勾选的「同时清理其收藏」。

**2. 一条消息是否允许同时属于多个收藏夹？**

本稿选「不允许」（`UNIQUE(messageId)`，换夹 = 移动）。允许多归属的话，「这条在哪」会变成
一次多结果查询，去重、导出、删除夹都要重做。若真实需求是「同一段素材按不同视角归类」，
那更像标签而不是夹。

**3. 收藏是否包含图片附件的字节？**

本稿选「不包含」，只记 `hasAttachments`。代价是会话删除后，收藏里的图片只剩一行
「（含附件）」。要包含就得复制图片文件并在 `attachment_refs` 之外再维护一份引用计数，
工作量是本稿图片部分的 3 倍以上。
