# 37 · Agent 工具调用与循环审查报告（2026-11-25）

> 审查范围：`net/AgentHarness.kt`、`net/WebToolLoop.kt`、`net/ChatApi.kt`、`net/SseClient.kt`、
> `net/StreamingRequestBody.kt`、`net/SearchAugmentation.kt`、`net/SearchConsistency.kt`、
> `ui/chat/ChatViewModel.kt`（发送/流式/agent 接入段）、`ui/chat/AnthropicRequestBuilder.kt`、
> `data/ChatRepository.kt`（附件准备段）、`data/ApiImage.kt`、`data/SettingsStore.kt`（开关落库）。
>
> 审查目标：①有时不调用工具；②有时声称自己没有工具；③开关控制不实时；
> ④对缓存命中破坏大；⑤加载慢导致首 token 慢。
>
> 结论先行：**五个症状里有四个同源 ——「每轮都变的指令文本被放在了请求头部」**。
> 它同时解释了缓存命中差（前缀失效）、首 token 慢（全量 prefill）、
> "说自己没工具"（指令位置注意力最弱 + 收尾阶段语义被写成 unavailable）。
> 其余的根因是循环的健壮性缺口（stop reason 白名单、`require` 炸整轮、工具名增量拼接）
> 和发送链路上的串行重活（双次序列化、逐轮重读附件、记忆检索阻塞）。

---

## 1. 问题清单（按症状 → 根因）

### A. 「有时候不知道调用工具」

| # | 根因 | 位置 | 后果 |
|---|---|---|---|
| A1 | **stop reason 白名单过窄**：只有 `tool_calls` / `tool_use` 才进入工具执行分支；兼容网关常发 `function_call`、`null`、或带 tool_calls 却报 `stop`，此时已解析出的工具调用被**静默丢弃**，循环按最终回答收尾 | `WebToolLoop.kt:295` | 模型"调了工具但没执行"，用户看到普通回答 |
| A2 | **协议守卫用 `require` 直接抛异常**：单轮调用数 >4、参数 >8KB、index 越界/过多、call id 重复，任何一个都让**整轮失败**（`IllegalArgumentException` 冒泡成错误消息），而不是把越界部分降级为结构化工具结果 | `WebToolLoop.kt:231-234`、`331-333` | 偶发的"这一轮直接报错" |
| A3 | **工具名增量用 `+=` 拼接**：部分兼容网关每个 delta 重发全名，名字被拼成 `generate_imagegenerate_image…`，`knownTool()` 判 false → 调用被丢弃 | `WebToolLoop.kt:233`（`ImageToolCall.kt:22` 同款） | 特定网关下工具永远不触发 |
| A4 | **续写（`prefix != null`）时 INDEPENDENT 路由不建 session**：`WebResearchSession` 只在 `prefix == null` 时创建，续写轮客户端搜索/读链工具完全不暴露，但开关在 UI 上仍是开 | `ChatViewModel.kt:2185-2195` | 续写时说"再查一下"，模型无从调用 |
| A5 | **只有软提示，没有纠偏**：`webToolInstruction` 只有一句"相关时用工具"；模型首轮没调就没有任何二次机会（`onSearchAnswerRetry` 只在"答案声称开关关闭"时触发，见 B4） | `WebToolLoop.kt:13`、`302-313` | 时效性问题被直接凭印象回答 |

### B. 「有时候说自己没有工具」

| # | 根因 | 位置 | 说明 |
|---|---|---|---|
| B1 | **权威状态指令放在请求头部**：OpenAI 路径插在系统前缀之后、全部历史**之前**（`ChatApi.kt:114-118`）；Anthropic 路径拼进 `system`（`WebToolLoop.kt:55-67`）。长上下文里这是注意力最弱的位置，而历史里模型自己说过的"我无法联网"在上下文末尾、逐字被模仿 | 同上 | 指令写了 "overrides earlier assistant claims"，但位置削弱了它 |
| B2 | **收尾/预算阶段被翻译成 "unavailable"**：第 3 轮起 web 工具因 `maxWebRounds=2` 撤下，指令直接写 `web_search=unavailable`；`FINAL_ANSWER` 轮所有工具报 disabled，且 `textAnswerRecoveryInstruction` 让模型"解释实际限制" —— 诱导模型在最终答案里向用户谈论工具状态 | `WebToolLoop.kt:24`、`184-202`；`AgentHarness.kt:239-271` | 搜完两轮后模型说"我目前无法使用搜索" |
| B3 | **矛盾回答的处置是整段作废**：重试一次仍声称不能搜索 → `resolveSearchAnswerFailure()` 丢弃已生成的答案并把消息标成**错误**（`search_answer_unresolved`） | `ChatViewModel.kt:2300-2303`、`WebToolLoop.kt:323-326` | 用户看到"一条错误"而不是"一个答案" |
| B4 | **检测全靠正则**：`claimsSearchIsOff` / `deniesSearchCapability` 只能覆盖枚举过的中英文句式；模型换个说法（"当前环境不支持联网查询"）就漏检，以错误答案收尾 | `SearchConsistency.kt:3-21` | 间歇性、不可复现的"说没工具" |
| B5 | 生图完成后每轮 system 追加 `imageAnswerInstruction`，与 B1 同源（也是 D2 的缓存破坏源之一） | `WebToolLoop.kt:65` | 次要 |

### C. 「开关控制不实时」

先说**已经是实时的部分**，避免误改：

- 开关值本身是乐观即时生效的：`pendingSearchSwitch` 覆盖 `stored.webSearch`，不等 DataStore 回写（`ChatViewModel.kt:356-360`、`385-402`）；
- 每轮开始重读 `runtime()`（`WebToolLoop.kt:183`），执行前再用 `stillEnabled` 重查一次（`WebToolLoop.kt:344`）——**轮次边界上的开关变化是会生效的**。

真正的缺口：

| # | 缺口 | 位置 | 表现 |
|---|---|---|---|
| C1 | **结构上限：开关只在轮次边界重读**。模型直接作答（无工具调用）时循环一轮即结束，流式中途拨开关本轮完全不生效 | `WebToolLoop.kt:295-330` | "我明明开了搜索，它还说没开" |
| C2 | **中途恢复的触发完全押在正则上**：`onSearchAnswerRetry` 要求答案文本命中 `claimsSearchIsOff` 才进入 `RECOVER_SEARCH`；且恢复 = 丢弃已生成文字重问一轮（用户看着文字消失，token 双倍） | `WebToolLoop.kt:302-313`；`ChatViewModel.kt:2285-2299` | Regex 漏检时无恢复；命中时体验也差 |
| C3 | **路由与执行器在 `startStream` 时一次性算死**：`searchRoute` / `webSession` / `searchThroughFlash` / `imageToolEnabled` / `automaticSearch` 之后不再变；本轮内换模型、换 profile、改搜索 API 配置都不生效（开关本身因 C 的乐观值是活的） | `ChatViewModel.kt:1964-1985` | 配置变更要下一轮才生效 |
| C4 | **AUTOMATIC 路由（gpt-5-search-api）开关被禁用且恒为开**：UI 上开关置灰选中（`InputPanels.kt:255-269`），`runtimeState` 里 `automatic` 不看开关（`ChatViewModel.kt:2269`）——设计上自洽，但注意指令因此恒报 enabled | `ChatViewModel.kt:2264-2281` | 仅记录，非缺陷 |

### D. 「对缓存命中破坏大」

缓存背景：DeepSeek 上下文缓存与 OpenAI 自动前缀缓存都是**请求前缀逐字节命中**；
Anthropic 官方需要显式 `cache_control` 断点 —— 当前代码**完全没有设置**（全库 grep 无 `cache_control`）。

| # | 破坏源 | 位置 | 影响面 |
|---|---|---|---|
| D1 | **易变指令注在头部**：`appInstructions`（含 `agentStateInstruction` 运行时状态、`webToolInstruction`、`serverSearchInstruction` 等）插在系统前缀之后、全部历史**之前**；开关拨一下、工具暴露变一下，整段历史前缀全部失效。OpenAI 路径的日期行（`systemContext`）甚至是**第一条消息** | `ChatApi.kt:104-118`；`ChatViewModel.kt:3120`、`2140-2148` | 拨一次开关 = 全量重 prefill；跨零点同理 |
| D2 | **同一轮 agentLoop 内逐轮改写头部**：`runtimeInstruction` 每轮重算并追加 `Current-turn web outcome: …`；`webToolInstruction ↔ webAnswerInstruction` 随 `webUsed` 切换；`tools` 数组逐轮增删（`webTools()` 过滤、`imageOffered` 变化、Anthropic 侧 `serverSearchInstruction` 的删除/恢复）——第 2 轮起每轮都是从 0 开始的全量 prefill | `WebToolLoop.kt:55-79`、`197-211`；`ChatApi.kt:135-147` | 长会话 + 一次搜索 = 2~4 次全量 prefill，TTFT 与费用同步放大 |
| D3 | **Anthropic 官方端无缓存断点**：`AnthropicRequest` 没有 `cache_control` 字段，api.anthropic.com 上每一轮都是全价全量 | `AnthropicDto.kt`、`AnthropicRequestBuilder.kt` | 官方 Claude 端缓存命中恒为 0 |
| D4 | **tools 数组随开关变化**：FLASH_NATIVE 加/不加 `deepseek_web_search`、OpenAI 加/不加 `web_search_options`，工具序列化在 prompt 最前，一变全变 | `ChatApi.kt:95-103`、`AnthropicRequestBuilder.kt:175-184` | 与 D1 同源 |
| D5 | 对照组（已做对的）：跨对话记忆拼在**最后一条 user 消息前**（`ChatViewModel.kt:3162-3168`）、`latest_reminder` 插在本轮提问之前（`AnthropicRequestBuilder.kt:155-165`）——**易变内容放尾部**的正确示范就在代码里，只是没有推广到工具指令 | — | 方案的直接依据 |

> 注：落库历史本身逐字节稳定；`ApiImage` 转码是内容寻址的确定性结果，不会破坏前缀。
> 前缀破坏全部来自"头部注入的易变文本/工具数组"。

### E. 「加载慢 → 首 token 慢」

按发送链路的先后顺序，每个节点都标了量级来源：

| # | 节点 | 位置 | 量级 |
|---|---|---|---|
| E1 | **请求体被完整序列化两遍**：`StreamingRequestBody.byteCount` 先 serialize 一遍只为数字节，OkHttp `writeTo` 再 serialize 一遍。带图长会话几十 MB JSON × 2，移动端每次可达秒级；agent 多轮时**按轮数翻倍** | `StreamingRequestBody.kt:18-39`；`SseClient.kt:79-80`、`AnthropicApi.kt:60-61` | 大请求下秒级 × 2 × 轮数 |
| E2 | **每条 user 消息的附件每轮重处理**：`prepareRequestAttachments` 逐条 `withContext(Dispatchers.IO)`：读全文件 + SHA-256（命中 LRU 也要先读完整个文件算 key），未命中再解码转码。会话里有几张图，每轮发送前就要重读+重 hash 几遍 | `ChatRepository.kt:1499-1521`；`ApiImage.kt:148-167` | 每图每次 IO+hash；首轮还有转码 |
| E3 | **跨对话记忆检索串行阻塞发送**：`crossChatMemoryFor` 在请求构造前执行，上限 ~220ms 扫描 + ~750ms 加载（`CrossChatMemory.kt:39-40`），开启记忆时每次发送都付 | `ChatViewModel.kt:2304-2305`、`3046-3107` | 0~1s |
| E4 | **send() 里 3~5 次串行 Room 往返**：`ensureConversation`（含重复 `findConversation`）、`appendUserMessage`、`findConversation`（仅为同步标题 UI，`ChatViewModel.kt:881`）、`beginAssistantMessage`，全部在 `startStream` 之前 | `ChatViewModel.kt:866-910`、`929-968` | 每次 1~10ms，可并发/挪后的没挪 |
| E5 | **`estimatedInputTokens` 每轮全量扫描**（`RequestBudget.kt:15-22`），按 agent 轮数翻倍；`computeContextStats` 已有 per-message `MessageWeight` 增量缓存（`ChatViewModel.kt:1333-`），这里没复用 | `SseClient.kt:51`、`AnthropicApi.kt:57` | O(全文字符) × 轮数 |
| E6 | **无连接预热**：OkHttp 空闲 5 分钟后首次发送要重新 TCP+TLS(+HTTP/2) 握手；进入会话/开始输入时没有任何预热 | `ChatApi.kt:218-234`（仅客户端配置） | 空闲后首发 +RTT×2~3 |
| E7 | **服务端 prefill 放大**：D1/D2 造成的前缀失效，在长会话上是首 token 最大的单项 —— 这不是网络问题，是请求形状问题 | 见 D | 随历史长度线性增长 |

### F. 顺带发现（非本次主诉，建议一并处理）

- **F1** 只要带工具或标题，`temperature`/`topP` 被强制置空（`ChatApi.kt:150-159`）——用户的采样设置在工具轮静默失效，应在设置页说明或改为按端点条件化。
- **F2** 开搜索时 `retryBeforeContent` 被关掉（`ChatViewModel.kt:2334`、`2420`），断流不再自动重发一次，用户更容易看到"连接中断"；注释里没写这条取舍的理由，建议补。
- **F3** `ImageToolCall` 在 ViewModel 侧已经收不到 `ToolCallDelta`（`agentLoop` 拦截后不重发，`WebToolLoop.kt:230-235`），其 `invocation()` 实为死代码，`endedWithoutCall` 仅靠 `Stopped` 恰好还正确 —— 建议精简或注释，免得后人误用。
- **F4** 循环收尾的 `Done` 发送条件 `done || offerWeb || imageOffered`（`WebToolLoop.kt:328`）在"流被截断且本轮无工具"时不发 `Done`，与其它路径不一致。
- **F5** OpenAI 路径的非搜索路由**完全没有日期锚点**（`latest_reminder` 只在 Anthropic 通道用；`systemContext` 只在搜索路由非空时带日期）——"今天几号"在纯 OpenAI 通道上天然答错，与工具无关但同属"请求形状"问题。

## 2. 解决方案

### P0 · 请求形状稳定化（同时治 D、B1、B2，并直接改善 E7）

**原则：稳定的内容往前放，每轮/每天会变的内容一律放尾部（最后一条 user 消息附近）。**

1. **易变指令尾部化**：
   - OpenAI 路径：把 `appInstructions` 与 `systemContext`（日期行）从"系统前缀之后"移到**历史之后、本轮提问之前**（合成一条 `system`/`user` 角色消息，或并入最后一条 user 消息前缀——与跨对话记忆同一落点）。
   - Anthropic 路径：`webToolInstruction` / `webAnswerInstruction` / `runtimeInstruction` 不再拼进 `system`，改为 messages 末尾的附加块；`system` 只放系统提示 + 预设 + 压缩摘要这些**会话级稳定**内容。
   - agentLoop 的轮次间状态更新（web outcome、预算变化）作为 tool result 之后的**追加消息**下发，而不是改写头部。
2. **tools 数组稳定化**：拨开关不再从请求里撤工具，改为"工具照发 + 指令声明禁用 + 执行层拒绝"（`stillEnabled`/`DISABLED` 结果已经是现成机制）；至少要撤也在会话级（新 turn 才变），不在轮次级变。
3. **Anthropic 官方端点补 `cache_control`**：在稳定 `system` 末尾与历史倒数第二条各打一个断点，易变尾部不进断点。自定义/DeepSeek 端点不发该字段（400 风险）。
4. 完成后用服务端回报的 `prompt_cache_hit_tokens` 验收：同会话连续 3 轮命中应 ≥ 历史前缀；拨开关后的下一轮命中**不应掉到 0**；agent 第 2 轮应命中第 1 轮的全部内容。

### P1 · 循环健壮性（治 A、C 的硬错误）

5. **stop reason 放宽**：有 `hasKnownCall` 就执行，仅在 `refusal` / `length` / `max_tokens` / `content_filter` 时放弃；`null`、`function_call`、`stop` 带调用一律照执行（`WebToolLoop.kt:295`）。
6. **`require` 全部改降级**：超 `maxToolCallsPerRound` 的执行前 4 个、其余回 `BUDGET_EXCEEDED`；参数超长/id 异常回 `INVALID_ARGUMENTS` 结构化结果喂回模型，整轮不再炸（`WebToolLoop.kt:231-234`、`331-333`）。
7. **工具名增量去重**：首个非空 name chunk 直接采用，后续 chunk 仅当是当前累计值的前缀延续时才拼（`WebToolLoop.kt:233`、`ImageToolCall.kt:22`）。
8. **收尾语义与指令分离**：预算耗尽/最终回答阶段，指令写 `used_this_turn (budget exhausted); answer from the evidence above`，而不是 `unavailable`；并加一句"不要主动向用户报告工具状态，除非用户问"。
9. **矛盾检测结构化**：答案落库时记录结构化字段（本轮是否产生 `SearchResult` 证据 —— 时间线里本来就有），矛盾检测优先看结构化字段，正则只作兜底；`resolveSearchAnswerFailure` 的"整段作废报错"降级为"保留答案 + 横幅提示"（B3）。

### P1 · 首 token（治 E）

10. **请求体只序列化一次**：序列化到临时文件（或 okio `Buffer`），`contentLength()` 取文件大小、`writeTo` 流式拷贝；`canReplayOnDisconnect` 语义不变。大请求立即省一遍全量 serialize。
11. **附件可发送形态缓存**：以 `message.id + 附件内容摘要` 为 key 缓存 `prepareRequestAttachments` 的结果，每轮只处理**新消息**；`ApiImage` 的 SHA-256 可与入库时的导入摘要对齐，避免每轮重读全文件。
12. **记忆检索预取**：输入框停笔防抖时后台先跑 `crossChatMemoryFor`，发送时直接用快照（超预算就放弃注入，不阻塞）；现状的 `memorySnapshot` 只在 attempt 间复用，改成按"问题文本 + 会话"缓存。
13. **send() 关键路径瘦身**：`findConversation`（标题同步）挪到 `startStream` 之后；`ensureConversation` 里重复的 `findConversation` 合并。
14. **token 估算增量**：复用 `computeContextStats` 的 `MessageWeight` 缓存，按消息 id 增量累计，agent 轮次间 O(新增) 而不是 O(全部)。
15. **连接预热**：进入会话/输入框聚焦时，对已配置端点在后台建连（HEAD `/models` 或直接 OkHttp 预连官方域），砍掉空闲后的 TCP+TLS 握手。

### P2 · 开关实时性（治 C1/C2，体验闭环）

16. **开关作为 Flow 注入进行中的 turn**：`webSearch` 已是 `mutableStateOf`，包一层 `snapshotFlow` 挂进 `streamJob`：
    - 首个 content token **之前**翻转 → 取消当前请求、以新状态重发（此时重发免费，还没有内容可丢）；
    - 已有内容之后翻转 → 不再打断，但在本轮收尾判定里加入"开关方向翻转"作为恢复条件（不再只押正则）。
17. **RECOVER_SEARCH 触发条件放宽**：`claimsSearchIsOff(answer)` → `claimsSearchIsOff(answer) || switchFlippedOnWithoutEvidence`（`!state.webEnabled && current.webEnabled` 且本轮无搜索证据）。配合 16，用户拨开关的最坏结果从"错误的旧答案"变成"安静重问一轮"。
18. 开关落库链路保持现状（乐观值 + writeId 回执已经是对的），不用改。

### 不建议做的事

- 不要为"更实时"去打断已产出内容的流 —— 已下发内容撤回的代价比晚一轮生效大（§"已写完然后没了"的历史事故）。
- 不要把正则越堆越多当作 B4 的长期解 —— 结构化证据字段才是。
- 不要为了缓存把 `latest_reminder` 的日期挪进头部 —— 它现在的位置就是对的。

## 3. 实施顺序建议

| 步骤 | 内容 | 验证 |
|---|---|---|
