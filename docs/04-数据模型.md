## 4. 数据模型

### 4.1 核心设计：**parentId 树**（v1.8 起，取代原「槽位 + 多版本」）

> 原方案是「槽位 + 多版本」：消息的身份是**位置**（`slotIndex`），同一位置堆多个版本。
> 它在 90% 的场景下工作良好，但有一个致命伤 —— **做不出分支**。
>
> 因为 slot 2 只知道"我排第 2 位"，**不知道自己是基于 slot 1 的哪个版本生成的**。
> 上游一换版本，下游就无法判断该不该跟着变；唯一自洽的处理是**删掉下游**。
> 于是「编辑重发」变成不可逆的破坏操作 —— 那是模型里根本没有"分支"这个概念的必然结果。
>
> **现在改为树**：

```
        u1 ── a1 ── u2 ── a2
         │            │
         │            └── a2'   ← 在 u2 上「编辑并重发」
         └── a1'                  ← 在 u1 上「重新生成」
```

| 概念 | 实现 |
|---|---|
| 身份 | `parentId`（父亲消息 id；`""` 表示根） |
| 兄弟 = 多版本 | 同一个 `parentId` 下按 `variantIndex` 编号，`active` 标记选中 |
| 当前对话 | 从根沿 `active` 一直走到底的**路径** |
| 编辑重发 | 挂一个新兄弟；**旧兄弟连同它整棵子树原样留着** |
| 切换版本 | 换一个兄弟 → **整段下游跟着换** |
| 删除 | 删该节点的**整棵子树** |

收益：编辑重发不再删任何东西，旧分支随时切回。代价：读取要按会话全量读一次
（几百条，可忽略），且备份格式语义变了（v1 → v2 不兼容）。

**为什么不用递归 SQL**：会话规模就几百条，一次读回来在内存里走，
可读、可测、不受 SQLite 方言影响。行走逻辑抽成纯函数 `MessageTree`（有单测）。

### 4.1.1 （已废弃）槽位 + 多版本

这是本项目最关键的数据结构决策。**一条消息的逻辑身份是 `(conversationId, slotIndex)`，不是 `id`。**

```
slot 0     slot 1        slot 2     slot 3
 U1    →   A1 [1/2]  →    U2    →   A2 [1/3]
            ├ v0 (active=0)
            └ v1 (active=1) ← 当前
```

**为什么不用树（parentId）**：树模型下编辑 A1 会产生兄弟节点 A1'，而其下游 U2 挂在
A1 之下 —— 一旦切换版本，后面的对话就"消失"了。要修就得复制冗余下游或递归重挂，都很别扭。

**槽位模型的行为**：

| 操作 | 行为 |
|---|---|
| 编辑 AI 消息 | 该 slot 新增版本，`active` 移过去。**后续 slot 完全不受影响** |
| 重新生成 | 同上，新版本加在同一 slot |
| 编辑用户消息 + 重发 | 该 slot 新增版本，**并自动为下一 slot 生成新的 assistant 版本** |
| 仅编辑用户消息 | 只改文字，不重发（菜单项与上一条分开） |

**收益**：零冗余、零递归、零 400 风险。读取当前对话是一条无 JOIN 的 SQL。
（同时它也规避了 §11.2 的"Chat Completions 不支持在对话中间插入工具调用"限制。）

### 4.2 Schema（v8，与代码一致）

> 以 `app/schemas/3.json` 为准（Room `exportSchema = true` 自动生成）。
> 下面这份是**给人读的版本**，加了字段含义与"为什么这么设计"。

```sql
CREATE TABLE conversations (
  id            TEXT PRIMARY KEY NOT NULL,
  title         TEXT NOT NULL,
  mode          TEXT NOT NULL,          -- CREATIVE | ROLEPLAY（§9.1.1②）
  provider      TEXT NOT NULL,          -- DEEPSEEK | OPENCODE_GO | CUSTOM
  model         TEXT NOT NULL,
  systemPrompt  TEXT,                   -- 会话级补充提示词（与预设拼接）
  createdAt     INTEGER NOT NULL,
  updatedAt     INTEGER NOT NULL,
  pinned        INTEGER NOT NULL DEFAULT 0,
  pinnedAt      INTEGER
);

-- 消息是**树**（§4.1 / §18）：身份挂在 parentId 上，不是在列表里的位置。
CREATE TABLE messages (
  id             TEXT PRIMARY KEY NOT NULL,
  conversationId TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  parentId       TEXT NOT NULL,         -- 父亲消息 id；空串 = 根（哨兵，见 §4.1）
  variantIndex   INTEGER NOT NULL,      -- 同父兄弟里的版本号 0,1,2...
  active         INTEGER NOT NULL,      -- 同父兄弟里当前选中的那条
  role           TEXT NOT NULL,         -- user | assistant
  content        TEXT NOT NULL,
  attachments    TEXT,                  -- JSON 数组，见 §23（v3 新增）
  reasoning      TEXT,                  -- reasoning_content，仅本地展示，不回传（§11.1）
  status         TEXT NOT NULL,         -- DONE | STREAMING | STOPPED | ERROR
  errorMessage   TEXT,
  excluded       INTEGER NOT NULL DEFAULT 0,  -- 休眠字段，见实体注释
  thinkingMs     INTEGER,               -- 真实思考时长（首条思维链 → 首条正文）
  ttftMs         INTEGER,               -- 首字延迟
  tps            REAL,                  -- 每秒 token 数
  tokens_in      INTEGER,
  tokens_out     INTEGER,
  createdAt      INTEGER NOT NULL
);
CREATE UNIQUE INDEX idx_msg_sibling ON messages(conversationId, parentId, variantIndex);
CREATE INDEX        idx_msg_parent  ON messages(conversationId, parentId);

-- 预设：其实就是「一段可命名的系统提示词」。
-- 刻意不做 provider/model/采样参数等结构化字段，保持泛用性（§9.1.1①）。
CREATE TABLE presets (
  id         TEXT PRIMARY KEY NOT NULL,
  name       TEXT NOT NULL,
  content    TEXT NOT NULL,             -- 系统提示词正文，纯文本
  sortOrder  INTEGER NOT NULL DEFAULT 0,
  createdAt  INTEGER NOT NULL,
  updatedAt  INTEGER NOT NULL
);

-- 会话挂载的预设：多对多 + 顺序 + 启停
CREATE TABLE conversation_presets (
  conversationId TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  presetId       TEXT NOT NULL REFERENCES presets(id) ON DELETE CASCADE,
  sortOrder      INTEGER NOT NULL DEFAULT 0,   -- 拼接顺序有意义
  enabled        INTEGER NOT NULL DEFAULT 1,
  PRIMARY KEY (conversationId, presetId)
);

-- 上下文压缩摘要（§9.1.1③）。只影响发送给 API 的内容，不删本地消息。
CREATE TABLE compactions (
  id              TEXT PRIMARY KEY NOT NULL,
  conversationId  TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  throughMessageId TEXT NOT NULL,       -- 摘要**覆盖到哪一条**为止
  summary         TEXT NOT NULL,        -- 摘要正文，可编辑、可重生
  createdAt       INTEGER NOT NULL,
  updatedAt       INTEGER NOT NULL
);
CREATE INDEX idx_compaction_conv ON compactions(conversationId);
```

#### 为什么附件是 `messages` 上的一列 JSON，而不是 `attachments` 表

早先的草案里有一张独立的 `attachments` 表（`localPath` + 宽高）—— **没有实现，也
不打算实现**。实际做法是把附件序列化成 JSON 存进 `messages.attachments`：

- 附件的生命周期**完全跟随消息**。它没有独立查询需求，单独一张表只会多一次
  join、多一处级联要维护。删消息时"附件会不会变孤儿"这种问题根本不存在。
- 图片以 **base64 存在库里**，而不是文件路径。这样「一份 JSON = 一份完整备份」
  这个约定不用打破（路径方案要么在备份里丢图，要么把备份改成 zip）。
  代价是库会变大 —— 所以导入时就压到最长边 1600px（§23.2）。

| v7 | `messages` + `timeline` / `stopReason` |
| v8 | 新增 `attachment_refs`（落盘图片的引用；删会话时据此清文件） |

#### 迁移策略：**只许前向，不许清库**

`AppDatabase` 里**不再有** `fallbackToDestructiveMigration`。

那条配置在开发期很省事，但它意味着"用户升级一次 App，全部对话凭空消失"。
用户真机上已经有成篇的稿子，这个代价不能接受 —— 宁可让它崩（看得见、能修），
也不能让它静默清库。**每次改 schema 都必须配一条显式 `Migration`。**

```kotlin
private val MIGRATION_2_3 = object : Migration(2, 3) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE messages ADD COLUMN attachments TEXT")
    }
}
```

### 4.3 关键查询

```sql
-- 读取当前对话（无 JOIN、无递归）
SELECT * FROM messages
WHERE conversationId = :cid AND active = 1
ORDER BY slotIndex ASC;

-- 版本数量（渲染 ‹ n/m ›）
SELECT slotIndex, COUNT(*) AS n FROM messages
WHERE conversationId = :cid GROUP BY slotIndex;

-- 切换版本
UPDATE messages SET active = 0 WHERE conversationId = :cid AND slotIndex = :slot;
UPDATE messages SET active = 1 WHERE id = :msgId;

-- 新增版本
SELECT COALESCE(MAX(variantIndex), -1) + 1 FROM messages
WHERE conversationId = :cid AND slotIndex = :slot;
```

### 4.4 写入策略

**绝不每 token 写库。** 一次 2000 字回复会产生 2000 次磁盘事务。

- 流式进行中：每 **~1.5 秒** checkpoint 一次
- 流结束 / 用户取消 / 异常：**终写一次**
- 效果：崩溃不丢内容，写入次数下降约两个数量级

---

### 14.1 持久层（Room）

5 张表：`conversations` / `messages` / `presets` / `conversation_presets` / `compactions`。
`messages` 对 `conversations` 是 `ON DELETE CASCADE`，删会话即级联清掉消息、
预设挂载与摘要 —— 少写三处手写清理。

写入分两条通道：

- **列表页**走 Room `Flow`，天然响应式（重命名 / 置顶 / 删除立刻反映）
- **对话流**以内存 `SnapshotStateList` 为准，按 §4.4 **节流 checkpoint**：
  流中每 ~1.5s 落盘一次，结束/中断时终写一次

> 为什么不全量落库：一次 2000 字回复逐 token 回写就是 2000 次磁盘事务。
> 为什么不攒到最后一次写：进程被杀就全丢。

### 14.4 备份格式

```jsonc
{
  "format": "simplechat-backup",   // 导入时校验；改名等于让所有老备份失效
  "version": 1,
  "exportedAt": 1758...,
  "conversations": [{
    "id": "...", "title": "...", "mode": "CREATIVE",
    "provider": "DEEPSEEK", "model": "deepseek-flash",
    "systemPrompt": null, "pinned": false, "pinnedAt": null,
    "createdAt": 0, "updatedAt": 0,
    "enabledPresetIds": ["third-person"],   // 挂载的预设，**顺序有意义**
    "messages": [ /* 含全部历史版本，不只 active 那条 */ ]
  }],
  "presets": [ /* 全局提示词库 */ ]
}
```

- 刻意**扁平**：会话下面直接挂消息数组。导出文件是给人看、给别的工具读的，
  嵌套比"外键 + 表连接"直观。
- 刻意**缩进**：与网络层的紧凑 JSON 分开两套 `Json` 实例。
  一行 JSON 没法读也没法 diff。
- 导入两种模式：`MERGE` 按 id 去重（多设备汇总）、`OVERWRITE` 先清空（换机恢复）。
  **预设两种模式都不删本地已有项** —— 预设是长期积累的资产，
  不该因为恢复一份旧备份就被清掉。
- 单会话导出**不带全局预设**：导入方的库里未必有这些 id，带过去只制造孤儿项。

## 17. 数据结构一致性：完整情况表与规则

> 这一章的由来：请求顺序出过一次严重错乱。回头把「槽位 + 版本」模型的
> **全部操作组合**过了一遍，发现 6 个真缺陷。记录下来，避免再走一遍。

### 17.1 不变量

| # | 不变量 | 保障方式 |
|---|---|---|
| I1 | 每个 slot 恰有 **1** 个 active 版本 | `activate()` = 清同 slot + 点亮，且在同一事务内 |
| I2 | `variantIndex` 在 slot 内连续 0..n-1 | `nextVariantIndex` = MAX+1；**只能删整个 slot**，不支持删单个版本 |
| I3 | `(conversationId, slotIndex, variantIndex)` 唯一 | DB 唯一索引 |
| I4 | **发出去的消息 = slotIndex 升序** | `orderedOutgoingMessages()`，纯函数 + 单测 |

> I2 的隐含前提要记住：一旦以后加"删除这个版本"，连续性就破了，
> 必须同时改 `nextVariantIndex` 的策略（改成找第一个空洞）。

### 17.2 语义：这不是树，是「线性槽位 + 版本栈」

```
slot 0        slot 1        slot 2        slot 3
[user]        [assistant]   [user]        [assistant]
  v0            v0            v0            v0
                v1 ←active    v1 ←active    v1
                v2
```

**切换版本不改变下游。** 换掉 slot 1 的 active，slot 2/3 仍是当初基于 v0 写的。
这不是缺陷，是刻意的选择（§4.1）：树模型要么复制冗余下游，要么递归重挂，都很别扭。

代价是**用户会误以为"应该回到那个分支"**，所以：
- 重新生成只替换这一条，界面上不做任何"分支跳转"的暗示
- 「保存并发送」会**截断下游**，因此必须二次确认

### 17.3 六个真缺陷与修法

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | **卡死会话**：某条 assistant 既无操作栏也无长按菜单，删不掉切不走 | 进程被杀时最后一条停在 `STREAMING`；`actionable = !streaming` 把**所有**入口一起关掉了 | 打开会话时把 `STREAMING` 清扫为 `STOPPED` |
| 2 | AI 回复的「保存并发送」毫无反应 | `if (role == USER && resend)` 分支写死，assistant 落进 else | 两种角色都截断 + 继续生成 |
| 3 | 编辑重发后几轮分支永久消失 | `truncateAfter` 删掉其后**所有 slot 的全部版本** | 二次确认，写明会删几条 |
| 4 | 压缩区域内的编辑"改了没用" | 请求里用的是摘要，原文不参与 | 面板明写"压缩只改变发给模型的内容" |
| 5 | 按 id 回查静默落空 | `send()` 自编 `local-user-<时间戳>` 当 id，库里是 UUID | `appendUserMessage` 返回真实 id |
| 6 | 请求以 assistant 开头 | 压缩切割点 `size - KEEP_RECENT` 没对齐角色 | 回退到 user 边界；再加一道兜底 |

### 17.4 请求顺序（修得最重的一条）

**旧实现**：`messages.filter{...}.forEach{...}` —— 顺序 = 内存列表的物理顺序。
而列表由一串增删改维护，任何一处出错都会错乱，且**界面上不一定看得出来**，
只表现为"模型答非所问"。

**乱序的两个来源**（都在 `openConversation`）：

```
currentConversationId = id        ← 协程内
settingsStore.setLastConversation(id)   ← 挂起点 ①
messages.clear()
messages.addAll(loadActiveMessages(id)) ← 挂起点 ②
```

- 窗口 ①：id 已是新的、列表还是旧的 → 新消息被追加进旧列表
- 窗口 ②：列表已清空、addAll 还没跑 → 新消息先入列，历史被追加到它**后面**

**修法**：id 与 `clear()` 同步做，异步只留"读回来填入"，并加世代号丢弃过期结果；
`send()` 先 `join()` 切换任务。

**兜底**：`orderedOutgoingMessages(messages, compaction)` —— 纯函数，
显式 `sortedBy(slotIndex)`，并保证首条为 user。9 项单测覆盖：
乱序输入 / slot 有洞 / 流式占位 / 空内容 / 首条必为 user / 纯 assistant 列表 /
压缩切割 / 切割后仍领先 assistant。

### 17.5 压缩：增量滚动

**旧实现**：每次从 slot 0 重压一遍 → 早先情节被反复摘要，信息每轮衰减一次，
几轮下来人名地名就开始漂。

**新实现**：只总结「上次摘要之后」的新增部分，把旧摘要作为上下文一并交给模型，
`fromSlotIndex` 沿用、`toSlotIndex` 前移。

### 17.6 已撤下：「不参与上下文」

功能本身合理（留着当参考但不发给模型），但当前实现有隐患：
字段、UI、请求过滤、统计过滤四处都要同步，且与压缩区域叠加时语义会打架
（被摘要覆盖的消息标记"不参与"本来就不生效）。

撤下的处理：**DB 列与备份字段保留休眠**，不动 schema ——
否则 `fallbackToDestructiveMigration` 会清空现有数据，
且老备份里少一个字段会解析失败。

### 17.7 已撤下：模式切换

扮演模式是远期功能。现在把「创作 / 扮演」两个并列摆出来，
等于让用户在两件当前不等价的事情之间做选择。
默认创作模式、不显示模式名；`ConversationMode` 与 `SegmentedSwitch` 均保留给以后。

## 18. 消息树：完整语义

### 18.1 不变量

| # | 不变量 | 保障 |
|---|---|---|
| I1 | 同一 `parentId` 下恰有 1 条 `active = 1` | `activate()` = 清同父兄弟 + 点亮，同一事务 |
| I2 | `(conversationId, parentId, variantIndex)` 唯一 | DB 唯一索引（根用 `""` 哨兵，否则 SQLite 把多个 NULL 视作互不相同，索引形同虚设） |
| I3 | 路径从根一路到叶，无环 | `activePath` 带 visited 集合，坏数据也不会死循环 |
| I4 | 发出去的消息 = 路径上筛选后的序列 | `orderedOutgoingMessages`，纯函数 + 单测 |

### 18.2 操作表

| 操作 | 语义 | 会删东西吗 |
|---|---|---|
| 发送 | user 挂在路径末尾，assistant 挂在 user 下 | 否 |
| 重新生成 | 新 assistant 挂在**被重生成那条的父亲**下 → 成为它的兄弟 | 否 |
| 编辑（仅保存） | 新兄弟，无子树 → 路径在此结束；旧子树留着 | 否 |
| 编辑并发送 | 新兄弟 + 在它下面生成回复 | **否** |
| 切换版本 | 换兄弟 → 下游整段跟着换 | 否 |
| 从这里新建对话 | **会话之间**的动作：复制活跃路径到某条为止，另起一个新会话（§21） | 否 |
| 删除 | 删该节点的整棵子树 | **是**（唯一会删的操作，有二次确认） |

### 18.3 压缩与分支的关系

`CompactionEntity.throughMessageId` 记的是**路径上的某一条消息**，不是"第几条"。

- 摘要在路径上 → 从它之后开始发
- 摘要不在路径上（切到别的分支了）→ **整个忽略**，老老实实发全量

用位置会在切分支后错位，用 id 天然免疫。

### 18.4 一致性策略：一律重读

所有增删改**完成后都调 `reloadPath()`** 从库里重读一遍活跃路径，
不在内存列表上原地修补。

理由：切换版本会**整段替换下游**（旧分支的子树让位给新分支的），
原地修补要处理的组合太多；读一遍反而又快又不会错。
流式期间仍走原地 patch（按 id），因为每 50ms 就要更新一次。

## 19. API Key 的存储与加密

### 19.1 为什么不用 `androidx.security:security-crypto`

`EncryptedSharedPreferences` 已停止维护，而且它的粒度是"把整份
SharedPreferences 加密"。我们只需要保护**一个字符串** ——
用它等于为一行数据引入一整套存储层。直接用 Keystore 更短、更透明。

**依赖已从 `libs.versions.toml` 移除。**

### 19.2 方案（`data/SecretBox.kt`）

```
Keystore 别名 : simplechat.api_key.v1
算法          : AES-256-GCM，密钥**不可导出**（userAuthenticationRequired = false）
存储格式      : base64( IV(12B) ‖ 密文 ‖ GCM Tag(16B) )
```

- 不要求用户认证：要求的话每次发请求前都得弹指纹，对"点开就能写"的 App 是灾难
- IV 由 Keystore 每次随机生成，随密文一起存
- 解密结果做了**密文→明文**的一级缓存：`SettingsStore.flow` 每次配置变化都会重读，
  而 Keystore 调用要过 Binder，比纯内存读贵几个数量级

### 19.3 失败路径的处理

| 情形 | 行为 |
|---|---|
| 换机 / 清除数据（密钥没了） | `decrypt` 返回空串 → 界面显示"未配置"，用户重填 |
| 密文损坏 | 同上，**不抛异常** |
| 从没设过 Key | 返回空串 |

**绝不回落成明文存储**：加密失败就让它是"未设置"，而不是悄悄写一份明文进去。

### 19.4 老数据迁移

v1.7 之前的版本把 Key 明文写在 `api_key` 里。升级后 `App.onCreate` 起一个
IO 协程调 `migrateLegacyApiKey()`：**就地加密 → 写进 `api_key_enc` → 删掉明文**。

`readApiKey` 保留了对明文的读取，所以即使迁移还没跑完，App 也是可用的。

### 19.5 实测验证

```
adb shell run-as com.simplechat.app.debug \
  cat files/datastore/simplechat_settings.preferences_pb
```

结果：文件里只有 `api_key_enc` 和一段 base64 密文，
**搜不到 `sk-` 开头的任何内容**；界面仍能显示 脱敏 Key（示例：`sk-••••`）（解密往返正常）。

另外 `android:allowBackup="false"`，所以不存在"备份还原后密文解不开"的坑。
