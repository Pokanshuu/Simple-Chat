## 53.1 结论

先给结论，后文逐条给出依据、数值与验收方式。

| # | 议题 | 结论 |
|---|---|---|
| 1 | 功能形态 | **自动注入的「时间上下文」为主（MVP），可调用的「时间工具」为 P1**。普通文聊不暴露任何时间工具，只注入上下文 |
| 2 | 注入位置 | **本轮最新一条 user 消息的尾部**：OpenAI 兼容 / Responses 用紧邻最新 user 的独立 `system` 消息（复用现有 `appInstructions` 机制），Anthropic 把一段文本块追加到最新 user 内容里（放在 `cache_control` 断点之后）。**系统提示词本身不写时间** |
| 3 | 注入内容 | 绝对时间（`yyyy-MM-dd`、星期、`HH:mm` 24 小时制、IANA 时区、UTC 偏移）+ 相对时间（距上一条消息、本会话开始，分档措辞）+ 一句「以设备时钟为准」的权威声明。不含秒、不含农历、不含 GPS 地区 |
| 4 | 与既有提醒的关系 | DeepSeek 官方通道的 `latest_reminder`（日期 / 星期 / 地区 / 平台 / 语言）**保持原样不动**；新上下文只补它没有的**时刻、IANA 时区、UTC 偏移、相对间隔**，避免同一事实发两遍 |
| 5 | 刷新时机 | **每轮发送前算一次；同一轮 Agent loop 的多次模型调用复用同一份**；重试、重新生成、续写各算各的。不做 N 分钟阈值，不把时间写进系统提示词 |
| 6 | 是否落库 | **不落库、不进备份、不加数据库列**。只在请求装配时现拼；关闭开关后请求体与当前实现逐字节一致 |
| 7 | 缓存影响 | 失效点被限制在**尾部**（上一轮 user 消息处）：稳态每轮多重算约 1–3k 输入 token；跨天不会让长会话整段重算；首轮/升级后首请求本来就要预热缓存，不计入收益 |
| 8 | 时区与夏令时 | `ZoneId.systemDefault()` + `Instant` 差值；DST 切换不产生"负间隔"；跨时区旅行下一次请求自动生效；设备时钟被改则把负间隔钳成「刚刚」并记诊断日志 |
| 9 | 相对时间措辞 | 模型上下文用**数值分档**（刚刚 / 约 N 分钟 / 小时 / 天 / 月 / 年），不把「上周三」这类依赖"现在的星期"的歧义措辞喂给模型；`昨天 22:10`、`上周三` 这类人类措辞只在 P2 的界面显示里使用 |
| 10 | Agent 能力 | 时间拆两层：**时间上下文 = ContextProvider 性质（自动、不进工具列表）**；**时间工具 = Registry 里的可调用能力（P1）**。能力快照、循环预算、Transcript 全部沿用 [35](35-Agent-Harness长期设计方案.md) §3.2 / §5.1 / §8 |
| 11 | 工具清单与预算 | P1 三个本地工具：`time_now`、`time_convert`、`time_add`。预算：每轮最多 **2 次**、不占用联网轮次、每次调用增加一次模型往返；因此文聊默认不暴露 |
| 12 | 用户开关 | **一个开关，默认开启**：「设置 > 对话行为 > 时间」分组下的「时间感知」。关闭 = 只保留既有的 `latest_reminder`、不注入新内容，请求逐字节回到当前版本 |
| 13 | 为什么默认开 | 回答「今天几号 / 现在几点 / 距上次多久」属于**正确性修复**，不是口味偏好；默认关等于让所有用户继续拿到错误答案 |
| 14 | 为什么仍要开关 | 主用途是长文本创作（[01-PRD](01-PRD.md) §1.1）：现实时钟进入虚构世界会污染时间线；开关同时是缓存/兼容性问题的逃生门。**不新增一级入口或独立页面**，只在本页加分组卡 |
| 15 | 旧会话与导入 | 只读使用 `createdAt`；时间戳不可信（缺失 / 0 / 未来）时**省略相对间隔句子**，不写"时间未知"（避免模型复述）；分叉复制保留原始 `createdAt` 的语义不变 |
| 16 | 多端一致性 | 各端用本机时钟现算、不落库，因此没有"同步来的过期时间文本"；[40-多端同步](40-多端同步（WebDAV）设计.md) 的备份与分片格式不需要任何改动 |
| 17 | 数据库 | **不升级 DB 版本**（当前 v18，`db/AppDatabase.kt:34`），不加列，不新增迁移；只在内存模型 `UiMessage` 末尾加一个带默认值的 `createdAt` 字段 |
| 18 | 非目标 | 不做世界时区服务、不做提醒/日历/定时任务、不采集定位、不做用户画像、不推断用户作息、不做农历/黄历 |
| 19 | 验收 | JVM 纯函数（格式 / 分档 / 刷新判定 / DST）+ 三通道请求形状 golden + 「关闭时逐字节一致」+ 真机改时钟 / 跨天 / 换时区 + 缓存命中率前后对照（方法见 §53.17） |

一句话：**把"现在几点"变成每轮尾部的一小段机器生成上下文，而不是一次工具调用；把它当作 Harness 的 ContextProvider 来管，把可调用的时间能力留给已经开了工具的场景。**

## 53.2 题意解读与背景

### 53.2.1 「在对话行文里加一条」的两种读法

用户原话「在对话行文里加一条，加一个时间感知的功能」有两种可执行的理解，本设计按 A 展开，B 留出 P2 位置：

| 读法 | 含义 | 本设计中的位置 |
|---|---|---|
| **A（主线）** | 在发给模型的**对话上下文**里加一条时间信息 | §53.4–§53.12（MVP 全部实现） |
| B | 在**聊天界面**的消息行文里显示时间（时间分隔线 / 每条消息时间） | §53.10.2 只给规则表，MVP 不做；若评审确认要做，另立 UI 施工项 |

现状支持 A 才是痛点：模型看不到任何时刻（§53.2.5）；而聊天界面刻意不显示消息时间（`ui/chat/MessageList.kt:1436-1459` 的元信息只有"模型 · token 数"，历史抽屉按天分组 `ui/history/HistoryDrawer.kt:608-614`），加时间是另一类视觉决策。

### 53.2.2 模型没有时钟时的典型错误

| 用户说法 | 典型错误表现 | 根因（本设计的解释） |
|---|---|---|
| 「今天几号？」 | 答成训练截止前后的某个日期，或反问用户 | 上下文里没有任何日期锚点 |
| 「现在几点了？」 | 用"我没有实时信息"搪塞，或编一个时间 | 没有时刻、也没有时区 |
| 「明晚八点提醒我」 | 把"明天"锚到训练数据里的某一天 | 没有绝对日期，相对日期无法落地 |
| 「上周三说的那个方案」 | 把"上周三"理解成上一周任意一天，或干脆换话题 | 没有星期 + 日期锚点，无法反推 |
| 隔三天回到同一会话：「上次聊到哪了」 | 只按消息内容推断，完全不知道隔了多久 | 没有"距上一条消息多久 / 上次活动" |
| 隔天继续长文创作 | 故事内时间线漂移（人物"昨天"和"上周"错位） | 没有现实日期锚点，也没有会话跨度 |
| 「把下个月 15 号换算成还有几天」 | 心算错误或拒绝 | 没有可靠"今天是哪天" |

这些错误与模型能力无关：模型没有可观测的时钟，**任何"当前时间"都只能是训练先验**。

### 53.2.3 为什么优先放在提示词上下文，而不是每轮让模型调用工具

这是本设计最核心的取舍。把"现在几点"做成一个工具，让模型每轮自己决定是否调用，看起来更"Agent"，但对**普通文聊**代价过高：

| 维度 | 自动注入（推荐，MVP） | 每次让模型调工具 |
|---|---|---|
| 延迟 | 0 额外往返 | 至少 +1 次完整模型请求（工具结果必须回传后模型才能作答） |
| 成本 | 每轮约 35–50 输入 token | 每轮多一次请求的输入 + 一次工具结果 + 一次额外输出（首轮通常还要重新请求） |
| 可靠性 | 确定性：每轮都带 | 依赖模型"想得起来"调用，也依赖通道暴露工具；漏调就退回无时钟 |
| 失败面 | 无网络请求，不会失败 | 工具被关闭 / 通道不支持 / 预算耗尽 / 超时都会被模型误解为"我没有时间能力" |
| 缓存 | 失效点限制在尾部（§53.4.3） | 工具调用会改变每轮的消息序列，尾部变化更多 |
| 实现复杂度 | 一个纯函数 + 三处装配 | 注册表、执行器、预算、协议适配、Transcript 全都要动 |

现有代码已经证明了工具路径的单价：`net/WebToolLoop.kt:219-518` 的 Agent loop 每次工具调用后要补一轮模型请求；`net/AgentHarness.kt:106-111` 的 `maxRounds = 4` 正是为这类往返设计的。让"今天几号"这种**每轮都需要的事实**走工具，等于每轮都多付一次往返。

结论：**时间作为事实注入；时间工具只在模型真的需要"换算 / 日期加减 / 解析"时才值得暴露**（§53.13）。这也符合 [35](35-Agent-Harness长期设计方案.md) §2.2「运行时状态是权威来源」：时间属于运行时事实，应该每轮注入，而不是让模型猜。

> 一个刻意不做的类比：不让模型自己维护"我在第几轮对话、现在大概几点"。那是把确定性事实交给采样过程，跨日必错。

### 53.2.4 与 Agent Harness 的关系

按 [35](35-Agent-Harness长期设计方案.md) 的分层，时间能力拆成两层，归属完全不同：

```text
ChatViewModel（组装本轮输入）
    ↓
时间上下文 TimeContext        ← 每轮自动生成；等价于 ContextProvider，不是工具
    ↓
AgentRuntime / AgentModelAdapter
    ↓
时间工具 time_now / time_convert / time_add   ← P1；走 ToolRegistry + ToolPolicy + Executor
```

| Harness 概念 | 本设计的落点 | 依据 |
|---|---|---|
| 能力快照（§3.2） | `AgentRuntimeState` 增加 `timeToolsConfigured / timeToolsExposed / timeBudgetRemaining` | 时间工具是否可调必须由配置决定，不能由历史文本决定 |
| 工具注册（§3.3） | `AgentToolId` 增加 `TIME_NOW / TIME_CONVERT / TIME_ADD`，注册进 `AgentToolRegistry` | 工具不能散落在协议适配器里用 `if` 拼 |
| 循环预算（§5.1） | `AgentHarnessPolicy` 增加 `maxTimeCalls = 2`；不占 web 轮次 | 本地工具零成本但每次仍多一轮模型往返，必须限次 |
| Transcript（§8.1） | 记录 `time_tools` 的暴露状态、调用参数（只含时区/日期）与结果 | 可审计；不含用户隐私内容 |
| ContextProvider（§9.2） | 时间上下文**不改变工具权限**，只贡献事实 | 角色卡/世界书同一条原则 |
| 未来自动化（§9.1，未做） | `automation.schedule` 之类留给 P2/未来，本期明确不做 | §1.2 的非目标：不自动修改用户数据 |

要点：**时间上下文不是工具**。把它注册成工具会让模型在"要不要知道自己几点"上做无意义决策；把它放进能力快照里的 `time_context=injected` 才是正确位置（P1 与工具状态一起注入）。

### 53.2.5 现状：仓库里已经有一半的时间注入（且只在一半通道上）

这一点必须先说清楚，否则会误以为功能从零开始。现状经 `git grep` 与代码阅读确认如下：

| 通道 | 现状 | 证据 |
|---|---|---|
| OpenAI 兼容 `/chat/completions` | **完全没有日期 / 时刻**。请求 = 系统提示词 + 历史消息 | `ui/chat/ChatViewModel.kt:3753-3835` |
| OpenAI Responses | 同样没有；仅当搜索/Agent 路由可用时，`systemContext` 里带一句日期 | `ui/chat/ChatViewModel.kt:2894-2895`、`net/ChatApi.kt:134-158` |
| Anthropic 官方 + Flash | 有 `latest_reminder` 专有角色：`日期,星期,地区,App,界面语言` 五段 | `ui/chat/AnthropicRequestBuilder.kt:163-181`；`data/LatestReminder.kt:49-68` |

## 53.3 目标、非目标与术语

### 53.3.1 目标

| # | 目标 | 验收方式 |
|---|---|---|
| G1 | 模型每轮都知道"现在"：本地日期、星期、时刻、IANA 时区、UTC 偏移 | 三通道 golden 请求包含该段；真机问"今天几号/现在几点"答对 |
| G2 | 模型知道"距上一条消息多久、本会话跨度" | 同一会话隔 3 分钟 / 隔 3 天各发一条，检查注入文本与回答 |
| G3 | 对所有实际协议生效：OpenAI 兼容、Responses、Anthropic（官方与非官方） | 四个组合的 golden 请求各一份 |
| G4 | **不破坏前缀缓存**：系统提示词逐字节稳定；失效点只在尾部 | `RequestShapeCacheTest` 扩展用例 + 实测命中率（§53.17.3） |
| G5 | **可完全关闭**：关闭后请求体与当前实现逐字节一致 | 关闭态 golden 快照与 `8a1aa0f` 行为对比 |
| G6 | 作为 Agent 能力预留：上下文可被能力快照描述，工具可注册（P1） | P1 的 Harness 测试与 Transcript |

### 53.3.2 非目标（明确不做）

- **不改变模型自身知识**：不注入训练数据里没有的事实，只注入"现在"。
- **不做世界时区服务**：不提供任意城市列表、不做时区数据库更新、不做 UTC↔城市名解析（IANA id 由系统提供）。
- **不做提醒 / 日历 / 日程 / 定时任务**：`automation.schedule` 是未来扩展，本期连 UI 都不预留。
- **不采集定位**：不申请任何位置权限（`AndroidManifest.xml` 当前权限列表中没有定位），地区沿用用户在设置里手填的字符串。
- **不写用户画像 / 作息推断**：只输出时间，不输出"用户通常在几点活跃"之类结论。
- **不做农历 / 黄历 / 节气**：不是本项目主用途，且需要额外数据表。
- **不在 MVP 展示消息时间**：见 §53.2.1 读法 B。
- **不改数据库 schema、不改备份格式**：DB 仍 v18、备份仍 v2。

### 53.3.3 术语

| 术语 | 定义 |
|---|---|
| **时间上下文（TimeContext）** | 每轮请求时由客户端生成的、描述"现在 / 相对间隔"的一小段文本。不落库，不作为工具调用 |
| **时间锚点** | 上下文里可被模型用来解释"今天 / 明天 / 上周"的绝对时间（日期 + 时区 + 星期） |
| **相对间隔** | 当前时刻与"上一条已完成消息"或"本会话开始"的差值，按 §53.10 的规则分档 |
| **注入位置** | 时间上下文在请求体中的落点（系统提示词 / 首条 user / 尾部注记 / developer 指令） |
| **本轮（turn）** | 用户点一次发送到该条回复结束；同一轮内 Agent loop 可能有多轮模型请求（round） |
| **通道** | `ApiStyle` 的三条实际协议：`OPENAI`、`OPENAI_RESPONSES`、`ANTHROPIC`（`net/Provider.kt:378-381`） |
| **可信时间戳** | `createdAt` 非 0、不晚于当前时刻 + 5 分钟容差、且不是"导入时兜底 now"的场景（§53.9.3） |

## 53.4 时间上下文的注入位置设计（核心）

### 53.4.1 候选位置与缓存代价

前缀缓存（DeepSeek 自动上下文缓存 / OpenAI 自动 prompt cache / Anthropic 显式 `cache_control`）**只从第一个 token 开始匹配前缀**：一旦第 k 个 token 变化，k 之后全部要重新 prefill。时间信息本身只有几十 token，但它放在哪里决定了"每次变化让多少历史失效"。

| 候选位置 | 各协议可行性 | 变化频率 | 缓存失效范围 | 结论 |
|---|---|---|---|---|
| ① 系统提示词头部 | 全部可行 | 时刻：每轮；日期：每天 | 每次变化 → 从 system 起**整段历史**失效 | **否决**（长会话每轮全量 prefill，代价最大） |
| ② 首条 user 消息前 | 全部可行 | 每轮 | 从第一条 user 起整段失效 | **否决**（历史本身被改动，不可复现） |
| ③ 本轮尾部独立 `system` 消息（紧邻最新 user） | Chat Completions 支持在对话中间插 `system`（`docs/05-网络与API.md` §11.2 引官方原话）；Responses 项目已在这么发（`net/ChatApi.kt:126-137` → `net/ResponsesApi.kt:32`）；Anthropic 的 messages 不接受 system 角色，需换成"追加到最新 user 内容块" | 每轮 | 只从**上一轮最新 user 消息**开始失效；历史前缀完整命中 | **推荐** |
| ④ developer / instructions 专用字段 | `ChatRequestDto` 没有该字段（`net/Dto.kt:36-62`）；`ResponsesRequestDto` 没有 `instructions`（`:64-76`）；Anthropic 只有顶层 `system` | — | 引入需改 DTO，且三家支持不一致 | **否决**（收益为零，兼容面变大） |
| ⑤ 扩展现有 `latest_reminder` | 仅官方 DeepSeek；服务端按五段硬校验，多一个字段直接 400 | 每轮 | 同 ③ | **否决作为唯一载体**；保留原样，新内容另走 ③ |

**为什么③的失效范围是"上一轮最新 user 消息"而不是"整段尾部无人命中"：**

- 请求 N：`[system, u1, a1, …, u(N-1), <时间注记>, uN]`
- 请求 N+1：`[system, u1, a1, …, u(N-1), a(N-1), uN, aN, <新时间注记>, u(N+1)]`

N 里 `<时间注记>` 紧贴在 `u(N-1)` 之后；N+1 里这个位置换成了 `a(N-1)`。因此前缀在 `u(N-1)` 处断开，`u(N-1)` 及其之后的最后一段要重算。这一段的量级是"最后一条用户消息 + 最后一条回复"，通常 1–3k token；相对 100k–1M 的会话长度可以忽略。

**反面数值**（用来解释为什么①绝对不行）：

| 方案 | 单次注入量 | 缓存失效点 | 长会话（100k 上下文）的代价 |
|---|---|---|---|
| 尾部注记（推荐） | 约 40 token | 上一轮 user 消息处 | 每轮多算约 1–3k token；跨天不多算全量 |
| system 头部（含时刻） | 约 40 token | system 第一个 token | **每轮**重算 100k |
| system 头部（只含日期） | 20–30 token | system 第一个 token | **每天**重算一次 100k；跨天正好打断长创作 |
| 首条 user 前 | 约 40 token | 第一条 user | 每轮重算接近全量 |

> 依据：`net/ChatApi.kt:117-130` 的注释已经把"每轮变化的指令放尾部"作为固定策略；`net/WebToolLoop.kt:55-63` 也记录了同样教训——早先把运行状态放在 `system`，每个 Agent 轮次和每次开关切换都会让整段历史重新 prefill。

### 53.4.2 推荐方案：尾部注记（三种通道三种落点）

```text
请求体（OpenAI / Responses）：
  [system 系统提示词（逐字节稳定）]
  [user u1] [assistant a1] ... [user u(N-1)] [assistant a(N-1)]
  [system <时间上下文>]          ← 现有 appInstructions 机制的末尾
  [user uN]

请求体（Anthropic）：
  system = 系统提示词（逐字节稳定）+ 摘要 + 既有 latest_reminder 的 system 回退
  messages = [u1, a1, ..., u(N-1), a(N-1), uN + "\n\n<时间上下文>"]
                                                          ↑ 在 cache_control 断点之后追加文本块
```

三条通道的落点与注意点：

| 通道 | 落点 | 文件 / 符号 | 注意 |
|---|---|---|---|
| OpenAI 兼容 | 作为 `appInstructions` 的最后一条 `system` 消息，紧邻最新 user | `net/ChatApi.kt:107-130`（新增 `turnContextNote` 参数并入 `appInstructions`） | 空串时不插入，保证"关闭 = 逐字节不变" |
| OpenAI Responses | 同上（同一个 `requestMessages` 再映射到 `input`） | `net/ChatApi.kt:134-158`、`net/ResponsesApi.kt:13-38` | 现有代码已把中间 `system` 映射为 `input` 的 system 项，行为不变 |
| Anthropic（官方 / 非官方） | 最新 user 内容尾部追加一个 text 块 | `ui/chat/AnthropicRequestBuilder.kt:46-243`（新增 `turnContextNote` 参数）；追加实现参考 `net/WebToolLoop.kt:100-113` 的 `withTrailingTurnNote` | **必须**放在 `withCacheBreakpoint` 之后（`:201-206`），否则易变内容被写进缓存断点；`latest_reminder` 仍紧邻 user；续写时 assistant 前缀仍是最后一条消息 |

### 53.4.3 为什么不是"在 system 里加一行"（最容易被提出的方案）

- 时刻每分钟都在变，system 每轮都变 → 每轮全量 prefill，等于把缓存完全关掉。
- 只放日期（每天变一次）看似便宜，但长创作会话**恰好跨天**时，第二天第一条消息会重算整个 100k+ 上下文；用户感受是"第二天第一句特别慢、特别贵"。
- 系统提示词是用户可编辑/可预览的内容（`data/LatestReminder.kt` 之外的预设与补充提示词），往里塞机器时间会让"最终系统提示词预览"混入非用户内容，违反 §9.1.1 的可预览约定。
- 现有 Agent 代码已经为了缓存把每轮状态挪到尾部（`net/ChatApi.kt:117-130`、`net/WebToolLoop.kt:55-63`），时间没有理由走反方向。

### 53.4.4 与既有 `latest_reminder` 的顺序和回退

Anthropic 官方 Flash 的 `latest_reminder` 有一条服务端硬约束：**后面必须紧跟一条 user 消息**（`docs/14` §2 的真机 400 原文；`sanitizeTurns` 已在 `ui/chat/AnthropicRequestBuilder.kt:525-552` 兜底）。因此顺序固定为：

```text
… [assistant a(N-1)] [latest_reminder: 日期,星期,地区,App,语言] [user uN + "\n\n时间上下文"]
```

- 时间上下文**不创建新的角色**，只追加到既有 user 内容，不会踩 `latest_reminder` 的相邻约束；
- 没有 user 消息（例如压缩、标题这类特殊请求）时**不注入**；
- 续写（`prefix != null`）时 latest user 仍存在，注记追加到它；assistant 前缀保持最后一条（与 `net/WebToolLoop.kt:96-113` 的续写规则一致）。

**回退（只在评审确认需要时启用）**：若某个自建网关对"对话中间插 `system` 消息"返回 400，可把同一段文本改为追加到最新 user 内容尾部（与 Anthropic 同形）。这是**手动切换的常量**，不做自动重试——自动重试可能把真正的原因（参数/额度/内容审核）误判为形状问题，浪费一次计费请求。

## 53.5 注入内容与格式

### 53.5.1 字段表

| 字段 | 示例 | 是否总是包含 | 说明 |
|---|---|---|---|
| 本地日期 | `2026-11-29` | 总是（官方通道由 reminder 承载时省略） | ISO-8601，零填充 |
| 星期 | `星期日` / `Sunday` | 总是（同上） | 按界面语言；用 `bools.xml` 的 `ui_is_cjk` 判定（同 `data/LatestReminder.kt:49-68`） |
| 本地时刻 | `14:32` | 总是 | **固定 24 小时制、零填充**，不跟随设备 12/24 设置 |
| IANA 时区 | `Asia/Hong_Kong` | 总是 | `ZoneId.systemDefault().id`；跨时区下一轮自动变 |
| UTC 偏移 | `UTC+08:00` | 总是 | 由 `ZonedDateTime.offset` 现算，DST 自动正确 |
| 距上一条消息 | `距上一条消息约 3 分钟` | 仅时间戳可信时 | 分档见 §53.10.1 |
| 本会话开始 | `本会话开始于 2026-11-21（约 8 天前）` | 仅当开始时间可信且跨度 ≥ 2 天 | 长创作/长对话才有价值，避免每轮多一句 |
| 权威声明 | `以上时间由设备时钟生成，优先于对话中其他时间说法` | 总是 | 防止用户文本里的"现在是 2030 年"覆盖真实时间 |
| 秒 | — | **不含** | 秒级精度对"今天几号""刚才"没有增益，只会增加变化频率 |
| 农历 / 节气 | — | **不含** | 非目标（§53.3.2） |
| 地区（城市） | — | **不进**本上下文 | 地区只服务既有 `latest_reminder`；新上下文不重复、也不新增采集 |

### 53.5.2 格式样例

中文界面（普通通道，完整版）：

```text
[时间上下文] 2026-11-29 星期日 14:32（Asia/Hong_Kong，UTC+08:00）；
距上一条消息约 3 分钟；本会话开始于 2026-11-21（约 8 天前）。
以上时间由设备时钟生成，优先于对话中其他时间说法。
```

英文界面：

```text
[Time context] 2026-11-29 Sunday 14:32 (Asia/Hong_Kong, UTC+08:00);
about 3 minutes since the previous message; this conversation started on 2026-11-21 (about 8 days ago).
Generated from the device clock; it takes precedence over other times mentioned in the conversation.
```

DeepSeek 官方通道（日期与星期已由 `latest_reminder` 承载，此处只补缺的项）：

```text
[时间上下文] 现在 14:32（Asia/Hong_Kong，UTC+08:00）；距上一条消息约 3 分钟。
以上时间由设备时钟生成，优先于对话中其他时间说法。
```

> 两段文本由同一个 `TimeFacts` 生成；官方通道只是把 `includeDate / includeWeekday` 关掉，避免模型看到两个可能不一致的日期来源。

### 53.5.3 token 成本

按仓库的本地估算公式（`data/TokenEstimate.kt:19-36`：CJK 字符权 8、其他字符权 3，除以 12 取整）：

| 版本 | 字符构成 | 估算 token |
|---|---|---|
| 中文完整版 | ≈ 52 个 CJK + 63 个非 CJK | **≈ 50** |
| 中文官方补充版 | ≈ 42 个 CJK + 48 个非 CJK | **≈ 40** |
| 英文完整版 | ≈ 150 个 ASCII | **≈ 38** |
| 中文仅短句（无会话开始） | ≈ 37 个 CJK + 50 个非 CJK | **≈ 37** |

结论：**每轮 35–50 token，典型约 40**。相对 1M 上下文占比 < 0.005%，相对 100k 会话 < 0.05%。真正需要关注的是 §53.4.1 的缓存失效范围，不是这几十 token 本身。

预算口径不需要新增类别：注记会自然进入 `net/RequestBudget.kt:15-21` 的 `estimatedInputTokens(...)`（Anthropic 走 `:19-21` 的 `system + messages`），压缩/长度校验沿用同一份估算，不需要额外字段。

### 53.5.4 为什么不用"更聪明"的格式

| 备选 | 否决理由 |
|---|---|
| 只给 epoch 毫秒 / UTC 时间戳 | 模型要自己换算时区，换算错一次整段对话都错（`data/LatestReminder.kt:33-36` 已记录同样判断） |
| 用自然语言长句（"今天是 2026 年 11 月 29 日星期日，现在是下午两点三十二分……"） | token 翻倍；"下午两点"还会引入 12 小时制歧义 |
| 每次把注入文本给用户看 / 可编辑 | 每轮变化、无编辑价值；用户不需要为机器上下文负责。P2 若要做，只在"关于/诊断"里只读展示一行 |
| 把时间塞进用户输入框（可见可改） | 会污染用户消息、进入备份与导出（违反"不改写内容"的既有原则） |

## 53.6 刷新时机

### 53.6.1 什么时候算、什么时候复用

| 场景 | 是否重算 | 理由 |
|---|---|---|
| 用户发送一条新消息（新一轮） | **重算** | 时刻/间隔必然变化 |
| 同一轮内 Agent loop 的第 2、3… 次模型请求 | **复用本轮第一份** | 同一轮内重算会让尾注在轮次之间变化，破坏同轮前缀缓存；而且一轮几秒内时间没有语义差异 |
| 工具执行超过 1 分钟后再请求 | 仍复用 | 同上；"时间冻结在本轮开始"是刻意的取舍（§53.6.3） |
| 自动重试 / 断流重发（同一轮） | 复用 | 同一请求形状；`canRetryThisTurn()` 的重试在 `ui/chat/ChatViewModel.kt:3033-3071` |
| 用户手动"重新生成" / "编辑重发"（新一轮） | 重算 | 新的流式任务，应当拿最新时间 |
| 续写（`ui/chat/ChatViewModel.kt:1931` 的 `startStream(..., prefix = current)`） | 重算 | 续写是新的流式任务；尾注变化只影响尾部缓存 |
| 打开会话 / 切换会话（不发送） | 不算 | 没有请求；时间只属于请求 |
| 标题、压缩摘要、远程附件摘要等后台请求 | 不注入 | 见 §53.11 |
| 用户关闭开关 | 不注入 | §53.14/§53.16 |

### 53.6.2 为什么不设"超过 N 分钟才刷新"

被否定的方案是：只在"距上次注入超过 5 分钟 / 跨天 / 换时区"时更新，其余轮次复用上一轮的字符串。问题有二：

1. **没有收益**。既然注记在尾部，每轮重新生成只影响尾部缓存；复用旧字符串并不能让缓存多命中（上一轮的注记本来就不在历史里，见 §53.4.1 的请求序列）。
2. **有一致性代价**。跨天/换时区必须重算，但"昨天 23:59 发出去的回答"和"今天 00:01 的追问"若沿用旧字符串，模型会把新问题锚到昨天，恰好制造本设计要消灭的错误。

因此采用"**每轮现算 + 同轮冻结**"：规则少、可测试、跨日必对。

### 53.6.3 为什么同轮内允许"时间冻结"

同一轮里用户等待 30 秒还是 90 秒，对"今天几号 / 刚才"没有区别；但让尾注在同一轮的多个 round 间变化，会让 Agent loop 每一轮都改写尾部，白丢缓存。**正确性优先于秒级新鲜度，冻结是显式取舍，不是遗漏。**

### 53.6.4 实现位置（施工约束）

**禁止**在 `ui/chat/ChatViewModel.kt:3268` 的 `buildAnthropicRequestNow` 或 `:3753` 的 `buildRequestMessages` 里调用 `LocalDateTime.now()`——这两个函数在 Agent loop 每一轮都会被调用（`:2797-2801`、`:2894-2895` 分别位于两处 `agentLoop` 的请求闭包内），在里面取时间会导致同一轮多个请求拿到不同尾注。

推荐落点：

```text
startStream（ui/chat/ChatViewModel.kt:2369）
  └─ streamJob 启动、进入 agent loop 之前（约 :2433-2442 的 turnDate 附近）
       val turnTime = TimeFacts(
           now = LocalDateTime.now(),
           zone = ZoneId.systemDefault(),
           previousMessageAt = <发送前捕获的最后一条已完成消息时间>,
           conversationStartedAt = <会话 createdAt，若可信>,
       )
       val note = buildTimeContextNote(turnTime, cjk = Res.bool(R.bool.ui_is_cjk))
  └─ streamAttempt(...) 捕获 note，传给两个 builder
```

同时把既有 `latestReminder()`（`:3368-3378`，现在每轮现算）改成接收同一个 `turnTime.now`：这样 `latest_reminder` 与时间上下文**共享同一时刻**，不会在午夜边界出现"提醒是 23:59、注记是 00:00"的分裂。该改动不改变 reminder 的正常输出，只消除跨午夜的竞态。

### 53.6.5 "距上一条消息"用哪一条

定义：**本轮发送之前的最后一条已完成消息**（用户或 AI 均可），不含本轮的流式占位。

| 入口 | 捕获点 | 说明 |
|---|---|---|
| 新发送 | `send()` 里 `appendUserMessage`（`ui/chat/ChatViewModel.kt:1016`）之前，取 `messages` 中最后一条非流式消息的 `createdAt` | 第一条消息时没有"上一条" → 省略该句 |
| 重新生成 / 编辑重发 | 开始新流之前，取当前路径上最后一条非流式消息（即将被替换的那条不算） | 语义是"距上次对话多久" |
| 续写 | 同上；被续写的那条仍在路径中，但它是本轮产物，不算"上一条" | 由 `orderedOutgoingMessages(...)`（`ui/chat/RequestOrdering.kt:58-87`）的可见集合辅助判断 |
| 失败重试（同轮） | 复用 | §53.6.1 |

**不采用**"用本轮新 user 消息的 createdAt 减上一条"作为实现捷径：那会让"首轮"和"重新生成"两种入口的时间语义不一致，且依赖占位消息的时间写入时机。

## 53.7 是否记录注入过的内容

| 方案 | 做法 | 优点 | 代价 / 风险 | 结论 |
|---|---|---|---|---|
| **A（推荐）** | 只在请求装配时拼，**不落库、不进备份** | 无 schema/备份变更；重开/多端必然一致（每轮现算）；历史里不会出现"过期的现在" | 每轮尾部约 1–3k token 的重算（§53.4.1）；无法回放"当时注入的原文" | **采用** |
| B | 每条 user 消息落一个隐藏列 `time_note`，下次重建历史时原样回放，保证历史逐字节稳定 | 缓存尾部也能命中，稳态零额外重算；历史回放一致 | 需要 DB 迁移 + 备份 v3 + 导入/同步兼容；历史里的"现在 22:10"会变成误导性陈述（模型可能把旧注记当当前时间）；违背"只改请求、不改数据"的既有约定 | **否决**（除非实测缓存收益显著，见 §53.17.3 的后备方案） |
| C | 只写诊断日志（长度 / 是否注入 / 时区 id 的哈希），不留正文 | 可排查、无隐私外泄 | 不足以复现语义 | **采用**（作为 A 的补充） |

A 方案下的一致性结论：

- **重新打开会话**：不发送就没有注入；发送时按当时本机时钟现算，不会出现"昨天的日期写死到今天"。
- **多端同步**：备份里没有时间上下文，不存在合并冲突；各端用自己的时钟与 Timestamp 解释同一份会话（这本来就是"每台设备的现在"的正确语义）。
- **导出（Markdown / JSON）**：完全不受影响。
- **Agent Transcript（P1）**：`docs/35` §8.1 的 Transcript 会记录 modelRequest，届时"本轮注入的原文"自然可审计，不需要另设存储。

## 53.8 时区、夏令时、设备时间与语言

### 53.8.1 时区来源与 DST

| 项 | 决定 | 为什么 |
|---|---|---|
| 时区来源 | `ZoneId.systemDefault()`（Android 跟随系统设置） | 不维护城市表、不申请定位；用户在系统里改时区就是明确意图 |
| 相对间隔计算 | `Duration.between(Instant.ofEpochMilli(lastAt), nowInstant)` | 用绝对时刻做差，DST 前后不会出现 23/25 小时偏差 |
| 展示偏移 | `ZonedDateTime.offset.id`（如 `+08:00`） | DST 期间自动变成 `+09:00`，不需要判断"现在是不是夏令时" |
| 跨时区旅行 | 下一次请求自动用新时区；历史消息的时间戳（epoch）不回溯换算 | 历史是绝对时刻；用新时区重新解释旧消息没有意义 |
| DST 跳变（春令时 02:00→03:00） | 本地钟面可能"缺一小时"，但 epoch 差连续 | 不会产生负间隔或 24 小时以上的虚增 |
| 设备时间被手动修改 | 信任系统时钟；若 `now - lastAt < 0`，钳成「刚刚」并写诊断日志（`Diagnostics.log("TIME", ...)`）；不向用户弹提示 | 无法可靠区分"用户改时间"与"时区/系统校时"；弹提示会制造噪音 |

### 53.8.2 24/12 小时制与语言

| 项 | 决定 | 理由 |
|---|---|---|
| 模型看到的时刻 | **固定 24 小时制 `HH:mm`**，不跟随设备 12/24 设置 | 无歧义（`02:30` 不会变成 `2:30` 而丢失上午/下午）；设备设置只影响界面，不应影响模型事实 |
| 星期写法 | 跟随界面语言：中文 `星期日`，英文 `Sunday`；判定用 `bools.xml` 的 `ui_is_cjk`（与 `latest_reminder` 同一判据） | 与既有提醒一致；不要让同一条请求里出现"星期"与"Sunday"两种写法 |
| 日期格式 | `yyyy-MM-dd` 零填充，所有语言一致 | ISO 无歧义；模型不需要猜"11/29"是月/日还是日/月 |
| 时区 id | 始终 IANA（`Asia/Hong_Kong`），不用缩写（`HKT`/`CST`） | 缩写有歧义（`CST` 至少三种含义） |
| 纯函数与 Android 资源 | 新纯函数接收 `cjk: Boolean`，**不调用 `Res`** | `data/AppText.kt:21-25` 明确：纯 JVM 单测不能走 `Res`（没有 Android Resources） |

### 53.8.3 时间戳可信性规则（旧会话 / 导入 / 分叉）

`createdAt` 是写入时的 `System.currentTimeMillis()`，但导入路径可能兜底成"导入那一刻"，因此相对间隔需要先判定：

| 场景 | 判定 | 相对间隔行为 |
|---|---|---|
| 本机新写入 | 可信 | 正常计算 |
| 自家备份导入 | 备份里带原始 `createdAt`（`docs/04` §14.4），可信 | 正常计算 |
| DeepSeek 归档导入 | `inserted_at` 解析为毫秒；解析失败才用 now（`data/import/DeepSeekHistory.kt:654`、`:761`） | 解析成功则正常；失败按"不可信" |
| Chatbox / 外部备份导入 | `timestamp`/`createdAt` 解析失败时返回 `System.currentTimeMillis()`（`data/import/ExternalBackup.kt:560-565`） | **无法区分**"真·刚刚"与"兜底 now"→ 接受这一已知局限；文档与测试记录 |
| 旧会话（很久未打开） | 可信 | 间隔可能数月/数年，按 §53.10.1 分档 |
| 分叉副本 | 保留原始 `createdAt`（`data/ChatRepository.kt:529-535` 注释；`docs/07-功能设计.md` §21.2） | 语义正确：那些话确实是当时写的 |
| 时间戳为 0 或 null | 不可信 | **省略相对间隔句**（不写"未知"） |
| 时间戳晚于 now + 5 分钟 | 不可信（时钟回拨/导入异常） | 省略相对间隔句，诊断日志记一次 |

`本会话开始` 额外要求：`conversation.createdAt`（`db/Entities.kt:40-41`）非 0、不晚于 now，且与第一条消息时间无明显冲突（差 > 1 天视为不可信，因为旧备份/导入的会话头与消息时间可能来自不同来源）。

## 53.9 相对时间措辞规则

### 53.9.1 模型上下文用的数值分档（MVP）

分档由纯函数 `relativeTimeLabel(elapsedMillis, cjk)` 实现，单位取整规则统一为**四舍五入、最小 1**：

| 区间（t = 间隔） | 中文 | English |
|---|---|---|
| `t < 60s` | 刚刚 | just now |
| `60s ≤ t < 55min` | 约 N 分钟前（N = round(t/60)，≥1） | about N minutes ago |
| `55min ≤ t < 24h` | 约 N 小时前（N = round(t/60min)，≥1） | about N hours ago |
| `24h ≤ t < 48h` | 约 1 天前 | about 1 day ago |
| `48h ≤ t < 30d` | 约 N 天前（N = round(t/1d)，≥2） | about N days ago |
| `30d ≤ t < 365d` | 约 N 个月前（N = round(t/30d)，≥1） | about N months ago |
| `t ≥ 365d` | 约 N 年前（N = round(t/365d)，≥1） | about N years ago |
| 不可信 / 负数 | **整句省略** | omit |

边界设计依据：

- **60s 以内统一「刚刚」**：人对"30 秒前"和"50 秒前"没有分辨需求，写"约 1 分钟前"反而与直觉冲突。
- **55 分钟提前进位到小时**：避免出现"约 60 分钟前"这种介于两档之间的怪值；55 分钟也是"该说小时了"的自然切换点。
- **24h 固定为「约 1 天前」**：跨过一天就是"隔天了"，精确到 23 小时没有信息增益。
- **30 天 / 365 天**：与人类口语的"上个月""去年"对齐；月按 30 天折算，年按 365 天折算，误差在可接受范围。
- 会话开始时间用同一个函数，只改前缀文案（`本会话开始于 <date>（约 N 天前）`）。

### 53.9.2 用户可见措辞（P2，仅当读法 B 立项时）

如果评审确认「在界面上显示消息时间」，人类措辞表单独定义；它与模型上下文**不共用**文案（模型要无歧义，界面要自然）：

| 距当前 | 显示格式 | 示例 |
|---|---|---|
| < 1 分钟 | 刚刚 | 刚刚 |
| 同一自然日 | 今天 HH:mm | 今天 14:32 |
| 前一自然日 | 昨天 HH:mm | 昨天 22:10 |
| 前两个自然日 | 前天 HH:mm | 前天 09:05 |
| 2–6 天前 | 星期X HH:mm | 星期三 22:10 |
| 7–13 天前 | 上周X HH:mm | 上周三 22:10 |
| 14–364 天前 | M月d日 HH:mm（跨年补 `yyyy年`） | 11月3日 22:10 |
| ≥ 365 天 | yyyy年M月d日 | 2025年1月8日 |

与模型上下文的三条差异：使用设备 12/24 制设置；使用自然日（不是 24 小时整除）；允许"昨天/上周三"这类依赖当前日期的相对词。实现时必须先按自然日切分再取时间，禁止用 `elapsed / 86400000` 直接取整（会在 23:50 与 00:10 之间产生"昨天"错误）。

### 53.9.3 为什么模型上下文不用"昨天 22:10 / 上周三"

- "昨天"依赖"今天是哪天"，模型如果同时看到注入日期与相对词，容易双重换算；
- "上周三"在跨周边界（周日/周一定义差异）上本身就有歧义；
- 数值分档 + 绝对日期已经足够推断，且**可被单测钉死**。

## 53.10 与压缩 / 摘要的交互

现有压缩只替换"发给模型的内容"，不删本地消息（`docs/07` §16.3、`docs/22`）：OpenAI 通道把摘要作为一条 `system` 消息插在系统提示词之后（`ui/chat/ChatViewModel.kt:3780-3788`），Anthropic 通道因为 `system` 只有一个字符串，把摘要拼在系统提示词末尾（`ui/chat/ChatViewModel.kt:3280-3289`）。时间上下文必须与这套顺序共存：

| 问题 | 决定 | 理由 |
|---|---|---|
| 时间上下文放摘要前还是后 | **放在整个请求的尾部**（最新 user 处），永远排在摘要与 `latest_reminder` 之后 | 时间是最"当下"的事实；摘要与 reminder 描述更早的上下文 |
| 压缩摘要里要不要写"当前时间" | **不写** | 摘要会被后续多轮复用，写死的"当前"很快过期；时间属于每轮事实，不应沉淀 |
| 压缩请求本身要不要带时间上下文 | **不带** | 摘要应当"无时态"；而且压缩请求是独立请求（`ui/chat/ChatViewModel.kt:1331-1405`），带时间只会污染摘要指纹与缓存（`docs/22`：提示词参与检查点指纹） |
| 压缩后"距上一条消息"怎么算 | 仍取路径上最后一条已完成消息的 `createdAt`，与是否被压缩无关 | 被压缩的只是"发不发原文"，不是"消息是否存在" |
| 长会话中的时间跨度怎么表达 | 用"本会话开始于 X（约 N 天前）"一行，不展开逐条时间 | 逐条时间戳会让 token 与视觉都膨胀，且创作场景不需要 |
| 未来是否让摘要把"明天/下周三"归一化成绝对日期 | **P1 可选**，本期不做 | 需要改压缩提示词与指纹（`docs/22` §摘要指导），且要评估摘要质量；先解决"模型知道现在"这一层 |

一个刻意保留的缺口：被压缩掉的旧消息里的相对日期（"明天"）在摘要中可能仍是"明天"。MVP 不修，因为**修它需要重新定义摘要语义**；如果用户确实遇到，P1 的"压缩时注入日期锚点"可以作为独立小特性评估。

## 53.12 Agent 能力设计：时间上下文 + 时间工具

### 53.12.1 分层与职责

| 层 | 是否模型可见 | 生命周期 | 本设计中的实现 |
|---|---|---|---|
| 时间上下文 | 每轮可见（尾部注记） | 每次请求现算；不落库 | `data/TimeContext.kt` + 三处装配 |
| 时间工具 | P1；仅在已暴露工具的请求里可见 | 模型调用时执行；本地零网络 | `AgentToolId.TIME_*` + Registry + Executor |
| 能力快照 | 每轮可见（P1 与既有工具状态同一段） | 每轮生成；覆盖历史声明 | `AgentRuntimeState` 扩展 + `agentCapabilityInstruction` |

与 [35](35-Agent-Harness长期设计方案.md) 严格对应：时间上下文属于 §9.2 的 ContextProvider（"贡献事实，不改变工具权限"）；时间工具属于 §3.3 的 Registry；两者都不允许绕过 Policy。

### 53.12.2 能力快照扩展

P1 在 `net/AgentHarness.kt:238-284` 的 `agentCapabilityInstruction` 末尾追加一行（与 `web_search=…` 同风格）：

```text
time_context = injected / disabled_by_user
time_tools = enabled / configured_but_not_exposed / unavailable
```

规则：

- **时间上下文每轮都有**（开关开时），所以 `time_context=injected` 是常态；工具被关闭/未暴露时，模型不得因此说"我没有时间能力"——上下文里已经有当前时间。
- `time_tools=configured_but_not_exposed` 用于"配置支持工具但本轮请求没有工具位"（与生图的 `configured_but_not_exposed` 同语义，`net/AgentHarness.kt:263-268`）。
- 能力快照仍是**本轮权威**：覆盖历史 assistant 说过的"我不知道现在几点"。

| 执行器 | `AgentToolExecutor`（`:157-226`） | 增加 `TIME_*` 分支，调用 `data/TimeContext.kt` 的纯函数 |
| 循环 | `net/WebToolLoop.kt:219-518` | 记录 `timeCalls`；时间调用**不增加 `webRounds`**，但每次仍消耗一次 `maxRounds` |

预算依据：一次时间工具调用 = 多一轮模型请求（`maxRounds=4` 的每格都用得上），而它解决的问题（换算/加减）在普通文聊里很少出现；默认不暴露给文聊，P1 只在"本轮已经要开工具"的请求里顺带提供。`maxTimeCalls=2` 足以覆盖"先查现在，再算日期"的两次调用。

### 53.12.5 失败与降级

| 情形 | 返回 | 模型应当怎么做 |
|---|---|---|
| 用户关闭时间感知 | 不注册 / `disabled` | 不声称"没有时间能力"；上下文也没有时间；如实说时间信息被关闭 |
| 通道不支持工具 | 不暴露 | 用时间上下文直接答；不要调用 |
| 参数非法（时区 id / 日期） | `invalid_arguments` + 说明 | 修正参数重试，或改用上下文里的时间 |
| 预算耗尽 | `budget_exceeded` | 用已有结果作答，不能再调 |
| 本地计算异常（理论上不会） | `failed`（兜底） | 如实说明无法换算，不要编结果 |

铁律（沿用 `docs/35` §2.3 与 §7）：**工具被关闭/预算耗尽不得被模型解读为"应用没有时间能力"**；结构化结果里要写明 "Time tools are disabled by the user; the injected time context is still authoritative for this turn."

### 53.12.6 Transcript 与评测

- P1 起在 `AgentTranscript`（`net/AgentHarness.kt:228-236`）记录：`time_tools` 暴露状态、每次调用的 `toolId / 参数（时区、单位）/ 结果状态`；**不记录用户对话正文**。
- Golden Transcript 场景至少覆盖：工具开启时"现在几点"不调用工具也能答（上下文已足够）、"纽约现在几点"调用 `time_convert`、预算耗尽、用户关闭开关。
- 与 `docs/35` §10 的 FakeModel / FakeTool 思路一致：时间工具本身是纯函数，Fake 层不需要网络。

### 53.12.7 未来扩展边界

| 能力 | 归属 | 本期 | 扩展前提 |
|---|---|---|---|
| 自然语言时间解析（"下周三下午三点"） | 时间工具 | 不做 | 需要限定语法 + 单测；不能做成"猜" |
| 写日程 / 提醒 / 定时任务 | `automation.schedule` 类工具 | 不做 | `docs/35` §1.2：先有权限模型与确认流程；时间解析是前置依赖 |
| 世界时区服务 / 城市搜索 | 外部工具 | 不做 | 需要网络与隐私评估，非本项目主用途 |
| 作息画像 / 用户行为推断 | 记忆或个性化 | 不做 | 与本设计的"只给事实"原则冲突 |

## 53.13 用户可见开关与文案

### 53.13.1 决策：要开关，默认开，放在「对话行为」

| 决策 | 内容 | 理由 |
|---|---|---|
| 是否可见 | **可见** | 主用途是长文本创作：现实日期/时刻进入虚构世界会污染时间线（"你现在几点"被写进小说旁白）；同时它是缓存回归问题的逃生门 |
| 默认值 | **开** | 回答"今天几号"错误是缺陷而不是选项；默认关等于让所有人继续错 |
| 位置 | **设置 > 对话行为**页内新增「时间」分组卡，一行开关 | 约束：不新增一级入口或独立页面；沿用 `ChatBehaviorPage`（`ui/settings/SettingsScreen.kt:1725-1768`）的分组卡与行样式 |
| 为什么不是「隐私」 | 仓库没有「隐私」一级页（`SettingsPage` 枚举 `ui/settings/SettingsScreen.kt:168-201` 无此项）；时间/时区属弱隐私，不申请定位；真正需要说明的是"它会进入发给模型的请求"，一行 hint 足够 |
| 为什么不是隐藏常量 | 创作用户无法止损；出问题（某模型被时间污染/缓存异常）时用户无法自行关闭 |
| 关闭行为 | 只停新注入；既有 `latest_reminder` 保持不变（它先于本功能存在） | 保证"关闭 = 当前版本请求体逐字节一致" |

> 若评审认为"开关太多"，可退化为默认开 + 仅保留开发期常量；但那样 §53.14.3 的逐字节回归只能靠测试兜底，用户失去止损手段。本设计推荐可见开关。

- **不新增第二个地区设置**；新时间上下文不带地区；
- 若未来要"时区手动覆盖"，应作为本分组的新行（先评审），而不是复用地区。

## 53.14 隐私与安全

| 项 | 结论 | 说明 |
|---|---|---|
| 数据范围 | 设备本地时间、时区 id、UTC 偏移、相对间隔、会话开始日期 | 弱隐私；不含定位、不含 IP、不含设备标识 |
| 采集方式 | 系统时钟 + `ZoneId.systemDefault()`；**不申请定位权限** | `AndroidManifest.xml` 的权限列表只有网络、前台服务、通知、唤醒锁、录音、安装包；没有 `ACCESS_FINE/COARSE_LOCATION` |
| 存储 | **不落库、不写文件、不进备份** | §53.7 方案 A；重启/多端都不会有残留 |
| 日志 | 只记开关状态、是否注入、note 长度、时区 id 的哈希/短标识（`Diagnostics.log("TIME", ...)`），**不记注入正文** | 与 `docs/22` §进度与数据保护、仓库既有"日志只记运营元数据"的约定一致 |
| 外传 | 随本轮对话 prompt 发给**用户自己配置的模型服务商**（这是功能的必要条件）；不存在 SimpleChat 自建服务器接收 | 与现有聊天请求同一边界 |
| 用户文本冲突 | 注入文本带权威声明（§53.5.1），模型应以设备时钟为准 | 防"现在是 2030 年"这类用户输入或旧 assistant 文本覆盖真实时间 |
| 关闭开关 | 完全停止新注入；不发时间、不落库、不写日志正文 | §53.16.1 逐字节回归 |
| 注入文本不是指令 | 只是事实；不包含"请执行"之类的祈使句 | 与 `docs/35` §9.3"世界书文本是数据不是指令"同一原则 |

## 53.15 兼容性与回归

### 53.15.1 关闭时请求体逐字节一致（硬指标）

满足条件：开关关闭时

- `turnContextNote` 为空串 → `net/ChatApi.kt` 不追加 `system` 消息，`ui/chat/AnthropicRequestBuilder.kt` 不追加文本块；
- 既有 `latest_reminder` 的生成逻辑与顺序不变（`ui/chat/AnthropicRequestBuilder.kt:163-181`）；
- `UiMessage.createdAt` 只是内存字段，不进任何序列化（`Backup.kt` 的 `BackupMessage` 不引用 `UiMessage`）；
- 不新增请求字段、不改采样参数。

验证方式：在 `RequestShapeCacheTest` 风格下抓取三种通道的请求 JSON，与 `8a1aa0f` 行为生成的 golden 文件逐字节比对（测试资源里存一份固定会话的期望 JSON）。**注意**：golden 必须同时覆盖"官方 Flash / 官方 Pro / OpenAI / Responses / 非官方 Anthropic"五个组合。

### 53.15.2 升级后的第一条请求

开关默认开，升级后第一次请求的请求体会变化 → 该次缓存必然从头预热。这与"改系统提示词/改消息格式"的既有发布一样属于一次性成本；文档与 release note 写明即可。若用户关闭开关，则立即回到旧的请求形状。

### 53.15.3 旧会话、导入会话、分叉会话

- 不升 DB（仍 v18）、不加列、不加迁移；`createdAt` 只是被读取，从未被重写。
- 旧会话（本机历史）时间戳可信 → 相对间隔正常。
- DeepSeek 归档：`inserted_at` 解析成功则可信；失败兜底 now → 可能显示"刚刚"，属已知局限（§53.8.3）。
- Chatbox / 外部备份：同上；**不做启发式修正**（例如"如果会话标题里有旧年份就当作旧会话"），避免猜错。
- 分叉副本：保留原 `createdAt`（有意为之，见 `data/ChatRepository.kt:529-535` 注释），相对间隔反映"这些话是什么时候写的"。
- 恢复备份后：时间上下文不参与导入/导出，天然一致。

### 53.15.4 多端与 WebDAV

- 每台设备用自己的时钟算"现在"，这是正确语义；不存在"同步来的时间文本"。
- 备份/同步格式不变（`docs/40` 的分片、marker、墓碑均不涉及时间上下文）。
- 跨时区两台设备看同一会话：各自看到的"现在/时区"不同，但历史消息的 `createdAt` 相同 → 相对间隔以同一 epoch 基准计算，不会出现负值。

### 53.15.5 与现有行为的关系

| 现有行为 | 本设计的影响 |
|---|---|
| 系统提示词预览（`ConversationSettings.composedSystemPrompt`，`ui/chat/ChatModels.kt:130-137`） | **不变**：时间不进入系统提示词 |
| 压缩摘要与生效判定（`docs/22`） | 不变；压缩请求不注入 |
| 标题生成请求（`ui/chat/ChatViewModel.kt:3457`） | 不变，不注入 |
| 远程附件摘要请求（`:1254-1329`） | 不变，不注入 |
| 搜索桥接请求（`:2709-2716`，`latestReminder = null`） | 不变，不注入 |
| 工具循环的尾部注记（`net/WebToolLoop.kt:100-113`） | 时间注记与 Agent 注记**并列**追加到最新 user；顺序为"用户正文 → 时间注记 → 本轮 Agent 注记"（后者由 `history.anthropic` 追加） |
| 续写（`:1931`） | 时间注记追加到最新 user；assistant 前缀仍是最后一条消息，不破坏续写形状 |

### 53.15.6 prompt 缓存回归（为什么必须测）

- DeepSeek 自动缓存与 Anthropic 显式 `cache_control` 的命中统计已有字段：`RequestUsage.cacheHitTokens / cacheHitRatio`（`ui/chat/ChatModels.kt:152-165`），解析见 `ui/chat/ChatViewModel.kt:1696-1703`，界面显示见 `docs/15` §4。
- 时间注记的预期成本是"每轮多算最后一段"，不是"每轮全量"。若实测命中率大幅下降，说明注记落点错了（例如误放进 system），必须先修落点，再谈优化。

### 53.16.3 缓存命中率实测方法

目的：证明"失效点只在尾部"，而不是靠体感。

1. **固定脚本**：同一会话、同一模型、同一组 6 条问题（首条为"你好"，后续每条间隔 30 秒以上），开启与关闭各跑一遍；记录每轮的 `lastUsage`（面板"缓存命中（最近一次）"，`docs/15` §4）。
2. **取数口径**：DeepSeek 用 `usage.prompt_cache_hit_tokens`，Anthropic 用 `message_start.usage.cache_read_input_tokens`（`docs/15` §4 表格）；命中率 = `cacheHitTokens / promptTokens`。
3. **排除项**：每组第 1 条（缓存写入必然 miss）、升级后的第一条、切换模型/端点后的第一条。
4. **验收门槛（建议）**：开关打开的稳态命中率相对关闭态下降 **≤ 2 个百分点**，或每轮 miss 增量 **≤ 2k token**。超过则说明注记位置/内容有问题，回到 §53.4.1 排查；仍不达标才考虑 §53.7 的方案 B（隐藏记录），并作为独立设计评审。
5. **记录**：把两组数字（轮次、命中/输入、百分比）写进验收记录；不要写"体感正常"。
