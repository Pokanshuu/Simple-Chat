# 49 · 分享截图个性化样式设计

> 目标：让「生成图片」导出的截图保留用户自己的壁纸、字体、主题色与深浅色，同时守住正文可读性。

## 49.1 结论

先给结论，后文逐条展开并说明依据。

| # | 议题 | 结论 |
|---|---|---|
| 1 | 默认外观 | 默认跟随应用的主题色、字体、字号与**深浅色**；**壁纸默认关**，首次开启时给隐私提示，选择持久化 |
| 2 | 一键开关 | 不新增「跟随应用外观」主开关。用 3 个互不重叠的细项加「恢复默认」表达，避免主开关与细项语义打架 |
| 3 | 渲染入口 | 导出容器接收一个不可变的 `ShareImageStyle`；壁纸画在**页画布**上，不画在 Compose 内容列里 |
| 4 | 壁纸取景 | 固定 1080 × 2400 参考画幅；分页每页取景一次，长图每 2400 px 重复一段 |
| 5 | 可读性 | 保护层下限浅色 0.55、深色 0.65；导出时把用户更高的壁纸透明度钳回，滑块调不破 |
| 6 | 旧输出 | `exportSharedImages` 的新样式参数默认 `null`（浅色、无壁纸），现有调用与设备测试不改；浅色下只有标题与页脚的灰阶微调（ΔE < 2） |
| 7 | 不做 | 头像与角色名、页面圆角、卡片投影、玻璃与实时模糊、背景透明度滑块、代码与公式字体跟随 |
| 8 | 容量 | 20 万字符、80 页、12000 px 上限不变；新增 120 MB 体积预算（只影响磁盘与提示） |
| 9 | 测试 | JVM 只测纯逻辑；设备侧用坐标探针与对比度断言，不做整图逐像素比较 |
| 10 | 品牌行 | 改成「猫标 + 字标」组合；颜色跟随主题色（有壁纸时回退正文色）；文件名与分享标题不变 |

## 49.2 背景与目标

当前「多选分享 → 生成图片」在 `ShareComposeRenderer` 的独立 Composition 里渲染，
固定使用浅色配色（`SimpleChatTheme(themeMode = ThemeMode.LIGHT, …)`）、主题色气泡与默认字体，
不包含壁纸。`MessageShareImages` 收到的样式相关参数只有 `accent`、`typography`、
`typographyFonts`、`fontScale` 与 `systemFontScale`。

结果有两个可见的断裂：

1. **深色用户拿到白底图**。聊天页是近黑底，导出的图是一整张白，转发出去像另一个应用。
2. **壁纸完全丢失**。壁纸是用户主动挑的那张图，也是"这是我的聊天"最直接的视觉标识。

目标：

- 让导出图与聊天页的外观一致：主题色、三层字体、字号、深浅色、壁纸。
- 不牺牲可读性。截图是成品，接收方无法调滑块，所以可读性必须在导出时确定。
- 不破坏现有导出：隐藏思考、隐藏名称、长图与分页、表格与公式分页、附件、缓存与 FileProvider 全部保持。
- 不给隐私添新口子。壁纸是用户自己的照片，默认外发需要显式同意。

非目标之外的一条底线：**导出只是把已有外观"搬过去"，不新增一套可编辑的外观**。

## 49.3 非目标

| 不做 | 原因 |
|---|---|
| 导出主题编辑器 / 样式模板市场 | 外观的唯一编辑入口是设置里的主题与壁纸页，导出只读不写 |
| 导出 PDF、HTML、可交互长图 | 超出「分享截图」的范围，且与 docs/19 的容量模型不兼容 |
| 水印、署名、二维码 | 产品未提出；品牌行已存在且可关闭 |
| 导出图上的"回到应用"引导 | 截图会离开应用，任何跳转都无法保证 |
| 为导出单独维护一套颜色常量 | 违反 docs/33 §33.2「视觉取值只从 Token 读」，主题文件会失效 |

## 49.4 用户场景

| 场景 | 期望 | 本轮是否满足 |
|---|---|---|
| 深色模式用户把一段回答发到群里 | 截图是深色的，和他在应用里看到的一样 | 满足（默认跟随深浅色） |
| 用了手写体作为「模型回复」字体的用户 | 导出的正文仍是那款手写体 | 满足（现状已透传，本轮补齐界面字体） |
| 设了风景壁纸、气泡是紫色主题的用户 | 截图带壁纸与紫色气泡，正文仍清楚 | 满足（壁纸需手动开启一次，之后记住） |
| 只想发干净截图的用户 | 和以前一样的白底图 | 满足（「更多样式 → 深浅色 → 始终浅色」，壁纸默认关） |
| 壁纸里是自己或家人的照片 | 不希望默认被带出去 | 满足（默认关 + 提示） |
| 表格、公式、长表格混排 | 分页规则不变，每页都有同样的背景 | 满足（壁纸在页画布，不参与测量） |

## 49.5 交互流程

### 49.5.1 面板结构

沿用现有 `MessageShareImageOptions` 的 `Dialog` 与 `ContainerShape` 卡片，只增加两处：
一个可见的壁纸开关，一个折叠的「更多样式」。

```text
选择图片形式
  长截图                       (●)
  分页图片                     ( )
────────────────────────────
使用聊天壁纸                  [ ]     ← 仅在已设置壁纸时出现
  开启后这张壁纸会一起导出。壁纸可能包含个人信息。
隐藏 SimpleChat 名称          [ ]
隐藏思考内容                  [●]     ← 每次打开重置为勾选
更多样式                      ⌄       ← 默认折叠
  ├ 深浅色   跟随应用 / 浅色 / 深色
  ├ 字体     应用字体 / 系统字体
  └ 恢复默认
────────────────────────────
( 生成 )
( 取消 )
```

要点：

- **壁纸开关放在一级**。它和「隐藏思考内容」一样有外部性，用户必须一眼看到；
  其余样式只是观感，折进「更多样式」，符合 docs/32 §32.2 的逐层展开。
- **没有主开关**。加一个「跟随应用外观」再允许改细项，会出现"主开关开着但字体是系统字体"
  这种自相矛盾的状态；真需要一键的场景用「恢复默认」表达，语义单一。
- 「恢复默认」只重置样式三项，不动长截图/分页、隐藏名称、隐藏思考。
- 壁纸开关在无壁纸时直接隐藏，不显示灰行，避免"有个开关但点不动"。

### 49.5.2 默认值与记忆策略

| 项 | 默认 | 记忆 | 理由 |
|---|---|---|---|
| 长截图 / 分页 | 长截图 | `rememberSaveable`，仅本次分享 | 已有行为，不引入新的持久偏好 |
| 使用聊天壁纸 | **关** | DataStore，长期记住 | 隐私外部性最强的项，必须显式同意 |
| 隐藏 SimpleChat 名称 | 关 | `rememberSaveable` | 已有行为 |
| 隐藏思考内容 | **勾选** | **每次重置** | 思考是内容，不是偏好；沿用 docs/19 的既有决定 |
| 深浅色 | 跟随应用 | DataStore | 与壁纸同属"这个用户喜欢的成品形态" |
| 字体 | 应用字体 | DataStore | 同上 |

样式三项集中存一个 JSON 值（见 49.6.2），一次写入、一次解码，不散成三个键。

### 49.5.3 预览与回跳

生成后进入现有预览页（`preview` Dialog，按 1600 px 分块解码）。
新增两条：

1. 预览页标题在包含壁纸时补一个标记：「分享图片 · 3 张 · 含壁纸」。
2. 预览页底栏增加「样式」按钮，点开即回到选项面板，且开关状态就是刚才的样子。

回跳的价值：样式不满意时不必退出重进多选。代价是多一次渲染和一个临时目录；
目录由现有 24 小时清理兜底，回跳时也可以先删掉本次生成的目录再重新生成。

**本轮不做面板内联缩略预览**。原因：预览要真实渲染才有意义，等于把整条导出管线在面板里跑一遍，
耗时与失败路径都会翻倍；而"生成 → 看 → 调"的循环成本已经被「样式」回跳压到两次点击。

### 49.5.4 壁纸不可用时的提示

| 情况 | 面板 | 导出 |
|---|---|---|
| 从未设置壁纸 | 不显示壁纸开关 | 纯色 |
| 已设置但文件缺失 / 解码失败 | 开关置灰，副标题「壁纸文件已丢失，将使用纯色背景」 | 纯色，不阻塞 |
| 会话自定义壁纸缺失、全局壁纸存在 | 与聊天页一致：不回落全局，按纯色处理 | 纯色 |
| 导出过程中壁纸文件被删除 | 无提示 | 位图已在内存，本次导出继续 |

## 49.6 样式与渲染架构

### 49.6.1 样式范围

| 项 | 阶段 | 规格 | 理由 |
|---|---|---|---|
| 深浅色 | MVP | 跟随应用（默认）/ 始终浅 / 始终深 | 所见即所得；深色用户不再拿到白底图 |
| 主题色 | MVP | 跟随应用 | 已由 `accent` 参数实现，气泡底色由主色派生 |
| 用户 / 助手字体 | MVP | 跟随应用，可切系统字体 | `TypographyCategory(FontSlot.USER/ASSISTANT)` 已按类别套用 |
| 界面字体 | MVP | 跟随应用 | 否则标题用系统字体、正文用自定义字体，同一张图两套字 |
| 字号（含类别覆盖） | MVP | 跟随应用，含单类覆盖 | `fontScale` 与 `LocalTypographySettings` 已透传 |
| 壁纸 | MVP | 默认关，可开；参数跟随应用 | 隐私见 49.9 |
| 壁纸模糊 / 亮度 / 对比度 / 位置 / 适配 | MVP | 跟随应用当前值 | 直接复用 `WallpaperState`，不多一套参数 |
| 气泡形状 | MVP | 固定 `BubbleShapeOut` | docs/02 §15.2 只有四档圆角，不为导出新增档位 |
| 气泡底色 | MVP | 实色不透明 | 静态图里半透明气泡只是"变淡"，不产生透视信息；也避免在壁纸上糊成一片 |
| 页面圆角 / 卡片 / 投影 | 不做 | — | 现状是通栏排版，没有卡片；`ShadowTokens` 是 Compose `Modifier`，`ShareImageWriter` 的原生 `Canvas` 用不上 |
| 玻璃 / 实时模糊 | 不做 | — | 导出没有 `LocalBackdropSource` 的实时背景源，模糊在静态图里也无从采样 |
| 背景透明度滑块 | 不做 | 固定下限 | 成品图的接收方无法调整，可读性不能交给发送方去试 |
| 头像 / 角色名 | 不做 | 保持隐藏 | 应用内没有头像；角色名已由 docs/19 决定在图片中隐藏 |
| 代码块 / 公式字体 | MVP | 只随字号，不跟随自定义字体 | docs/36「回复中的代码和 LaTeX 沿用等宽字体和数学字体」 |
| 品牌行 / 页码 | MVP | 品牌行改为「猫标 + 字标」，颜色跟随主题色；页脚保留 `SimpleChat · N`；整体可隐藏 | 见 49.6.8 |

### 49.6.2 样式数据与解析

分两层，避免"面板状态"与"渲染输入"混在一起。

**持久层**（新文件 `data/ShareImageSettings.kt`）：

```kotlin
@Serializable
data class ShareImageSettings(
    val useWallpaper: Boolean = false,
    /** null = 跟随应用；"LIGHT" / "DARK"。 */
    val darkMode: String? = null,
    val useAppFonts: Boolean = true,
)
```

存储沿用 `TypographySettings` 的做法：一个 `stringPreferencesKey` 存 JSON，
在 `StoredSettings` 上暴露 `shareImage: ShareImageSettings = ShareImageSettings()`；
解码失败或字段缺失一律落回默认值，旧安装首次升级即"默认跟随、壁纸关"。

**渲染层**（新文件 `ui/chat/MessageShareStyle.kt`）：

```kotlin
internal data class ShareImageStyle(
    val dark: Boolean,
    val accent: AccentColor,
    val fonts: TypographyFonts,
    val typography: TypographySettings?,
    val globalFontScale: Float,
    val systemFontScale: Float,
    /** 已钳制并确认可读；null = 纯色背景。 */
    val wallpaper: WallpaperState?,
    val tokens: ThemeTokens,
    val useAppFonts: Boolean,
    /** 品牌行是否画猫标（来自「使用 Simple Cat 图标」，见 49.6.8）。 */
    val showCatMark: Boolean,
    /** 品牌行的图标与字标颜色：主题色，或启用壁纸时的正文色。 */
    val brandColor: Color,
)
```

解析函数是纯 Kotlin，不碰 Android API，因此可以在 JVM 单测里完整覆盖：

```kotlin
internal fun resolveShareImageStyle(
    settings: ShareImageSettings,
    appDark: Boolean,
    accent: AccentColor,
    fonts: TypographyFonts,
    typography: TypographySettings?,
    globalScale: Float,
    systemScale: Float,
    wallpaper: WallpaperState?,      // 会话壁纸优先，其次全局
    wallpaperAvailable: Boolean,     // 文件存在且解码成功
    showCatMark: Boolean,            // useSimpleCatIcon
    themeSpec: ThemeSpec? = null,
): ShareImageStyle
```

解析规则：

| 输入 | 输出 |
|---|---|
| `darkMode == null` | `dark = appDark` |
| `darkMode == "LIGHT" / "DARK"` | 对应值 |
| `darkMode` 是别的字符串 | 回落 `appDark` |
| `useAppFonts = true` | `fonts` 原样、`typography` 原样 |
| `useAppFonts = false` | `fonts = TypographyFonts()`、`typography = null` |
| `wallpaperAvailable = false` 或 `wallpaper == null` | `style.wallpaper = null` |
| 壁纸可用 | `opacity` 钳到 `≤ 1 - floor`，其余参数原样 |
| `showCatMark = false` | 品牌行只画字标，字标回到 x = 64 |
| 壁纸可用 | `brandColor = scheme.onBackground`（正文色） |
| 壁纸不可用 | `brandColor = scheme.primary`（主题色） |
| 任意 | `tokens = resolveThemeTokens(dark, accent, themeSpec)` |

`wallpaper` 来自 `ChatScreen` 第 1127 行那个已经算好的有效值
（`conversationWallpaper?.toWallpaperState(context) ?: LocalWallpaper.current`），
以参数形式传给 `MessageShareTools`。导出与聊天页共用同一份壁纸解析结果，
不另写一套"会话优先"的判断。

`ThemeTokens` 必须与应用同一份解析结果，否则主题文件（docs/33）在导出里失效。
做法是把 `SimpleChatTheme` 里那段 `remember(dark, accent, themeSpec) { … ThemeResolver.resolve(…) }`
抽成 `internal fun resolveThemeTokens(dark, accent, themeSpec): ThemeTokens`，
主题与导出各自调用一次。`ThemeResolver.resolve(base, spec)` 返回 `ResolvedTheme.tokens`，
是无 Android 依赖的纯对象，可直接在导出线程使用。

### 49.6.3 渲染容器注入

`ShareComposeRenderer` 是挂在 `decorView` 下的独立 Composition，**不继承**主 Composition 的
CompositionLocal。因此 `LocalWallpaper`、字体、深浅色都必须在它内部重新提供。

```kotlin
// ui/chat/ShareComposeRenderer.kt
compose.setContent {
    CompositionLocalProvider(
        LocalDensity provides Density(2f, style.systemFontScale),
        LocalWallpaper provides (style.wallpaper ?: WallpaperState()),
        LocalFloatingBaseOpacity provides DefaultPanelOpacity, // 1f，实色
        LocalAcrylicEnabled provides false,
        LocalFloatingGlass provides 0f,
        LocalPanelAccentOpacity provides 0f,
    ) {
        SimpleChatTheme(
            themeMode = if (style.dark) ThemeMode.DARK else ThemeMode.LIGHT,
            accent = style.accent,
            fontScale = style.globalFontScale / style.systemFontScale,
            uiFontFamily = if (style.useAppFonts) style.fonts.ui else null,
            typographySettings = style.typography,
            typographyFonts = if (style.useAppFonts) style.fonts else TypographyFonts(),
        ) { /* 现有 measure / capture 宿主，不变 */ }
    }
}
```

注入契约：

| Local / 参数 | 取值 | 说明 |
|---|---|---|
| `SimpleChatTheme.themeMode` | `DARK` / `LIGHT` | 传解析结果，不传 `SYSTEM`：导出进程里的系统值不可信 |
| `accent` | `style.accent` | 用户与助手气泡、链接、品牌色都从这里派生 |
| `uiFontFamily` + `typographyFonts` | `style.fonts` | 三层字体；关闭「应用字体」时传空 `TypographyFonts()` |
| `fontScale` + `LocalDensity` | `globalScale / systemScale`、`Density(2f, systemScale)` | 与现状一致，保证字号行为不变 |
| `LocalWallpaper` | 已钳制的壁纸状态 | 语义一致性；MVP 不靠它绘制（见 49.6.4） |
| `LocalFloatingBaseOpacity` | `DefaultPanelOpacity`（1f） | 导出表面必须实色，否则在壁纸上会透 |
| `LocalAcrylicEnabled` / `LocalFloatingGlass` / `LocalPanelAccentOpacity` | `false` / `0f` / `0f` | 不录制背景源，不掺主题色 |
| `LocalChatColors`、`MaterialTheme.colorScheme`、`LocalIsDarkTheme` | 由 `SimpleChatTheme` 提供 | 不在导出侧手工构造；`LocalIsDarkTheme` 决定自定义文字色取浅色还是深色档 |
| 有壁纸时的 `processText` | `onBackground × 0.72 / × 0.76` | 在块内覆盖 `LocalChatColors`，对应 docs/32 §32.4.5「有壁纸时次级文字 +0.10」 |

`LocalWallpaper` 注入的是"语义"，不是"绘制"：壁纸必须画在页画布上。
原因很直接——Compose 内容列的宽度是 952 px（1080 − 2×64），而且按块逐次测量；
在内容里画壁纸只能盖住这一列，还会随块重排被重画。

`LocalChatColors` 不手工构造，唯一例外是上面那条 `processText` 覆盖：
`TypographyCategory` 会用自己的 `effectiveChatColors` 覆盖 `LocalChatColors`，
所以这层覆盖要放在 `TypographyCategory(...)` 之内、`Text` 之外。

### 49.6.4 壁纸绘制与分页

绘制顺序在 `ShareImageWriter.page()` 里固定：

```text
1. canvas.drawColor(style.tokens.colors.pageBackground)
2. 壁纸（按 2400 px 分段，drawWallpaper 复用）
3. 品牌行、标题
4. 内容块 append（现有逐块捕获与切片）
5. flush()：页脚 / 页码
```

顺序不能反：壁纸必须垫在内容之下，品牌与页脚必须压在最上。

**参考画幅固定 1080 × 2400**，与 `ShareImageMode.PAGES` 的页高一致：

```kotlin
private const val WallpaperBandHeight = 2400

style.wallpaper?.let { wallpaper ->
    var bandTop = 0
    while (bandTop < height) {
        canvas.save()
        canvas.translate(0f, bandTop.toFloat())
        CanvasDrawScope().draw(
            density = Density(2f),
            layoutDirection = LayoutDirection.Ltr,
            canvas = canvas.asComposeCanvas(),
            size = Size(width.toFloat(), WallpaperBandHeight.toFloat()),
        ) {
            drawWallpaper(
                image, wallpaper, style.tokens.colors.pageBackground,
                area = Size(width.toFloat(), WallpaperBandHeight.toFloat()),
            )
        }
        canvas.restore()
        bandTop += WallpaperBandHeight
    }
}
```

为什么不是"对整张长图取景一次"：

1. 长图高度在绘制过程中才能确定（`ShareImageWriter` 边画边累积 `y`），一次性取景要两遍渲染。
2. `drawWallpaper` 的 COVER 是按画布比例算的。画布变成 1080 × 12000 时，一张 1440 × 1080 的图
   会被放大约 11 倍，只剩中间一条模糊带，等于把壁纸废掉。
3. 长图溢出会自动回退分页。两套取景不一致时，回退前后观感会跳；统一按 2400 分段就没有这个跳变。

**分页时壁纸每页重复**（同一参考画幅重新 cover），不做跨页连续。
分享出去的图会逐张显示，"跨页拼成一张壁纸"的连续性没有意义；
代价是高对比度壁纸在大页数下每 2400 px 出现一次重复图案。
后续增强可加 120 px 交叉淡入（见 49.12 阶段 2）。

长图分段处的接缝同理：默认被保护层（≥ 0.55）与用户已设的模糊压到不明显。
若用户把模糊设为 0 且壁纸是高对比度图案，接缝可见——这是可接受的已知限制，写进发布说明。

**切片判定不受影响**。`safeShareTileEnd` 只看捕获层的 alpha 与 RGB，
壁纸并不在捕获层里（`append` 用默认混合把透明底的块画到已铺壁纸的页画布上）。
因此"在行间空白处分页"的逻辑不需要改动。

**图片附件**直接叠在壁纸上。带透明通道的 PNG 会透出壁纸，与聊天页一致，不额外加卡片底。

**隐藏名称**只改变 `bottom`、标题起点与页脚绘制，壁纸始终铺满整页。

### 49.6.5 可读性保护层

`drawWallpaper` 已经在壁纸之上叠了一层
`baseColor.copy(alpha = 1 - wallpaper.opacity)`——这就是 docs/32 §32.4 的保护层，
只是当时的取值由用户滑块决定。导出时把它变成硬下限：

```text
导出有效保护层 = max(1 - 用户 opacity, floor)
floor(浅色) = 0.55    floor(深色) = 0.65
```

两个数字由最坏情况反推（WCAG 2.x 相对亮度，正文 4.5:1）：

| 最坏输入 | 正文 | 需要的保护层 | 取整 |
|---|---|---|---|
| 纯黑壁纸 + 浅色主题（白底黑字 `#1A1A1A`） | 黑字压在 55% 白上，对比度约 5.2:1 | ≥ 0.51 | 0.55 |
| 纯白壁纸 + 深色主题（近黑底白字 `#E8E8EA`） | 白字压在 65% 近黑上，对比度约 4.6:1 | ≥ 0.63 | 0.65 |

所以导出把壁纸上限压到浅色 45%、深色 35%（应用里的滑块仍可调得更高，只影响用户自己看）。
这不是重复设置，而是**成品图的另一条底线**：设置页调高不透明度只影响自己看，
导出会发给别人看。

导出**不额外叠加暗化**（`dim`）。浅色主题下压暗会同时压低黑字的对比度，
深色主题下 0.65 的保护层已经把底压得足够暗；用户的 `dim` 原样保留，
再加一层只会让壁纸彻底看不见。上面的对比度按 8 位 sRGB 直接混合估算，
与 Skia 的默认混合方式一致，留了约 10% 余量。

其余层级的验收阈值：

| 层级 | 颜色 | 阈值 |
|---|---|---|
| 正文 | `scheme.onBackground` 或类别自定义色 | ≥ 4.5:1 |
| 思考内容（有壁纸） | `onBackground × 0.72`（浅）/ `× 0.76`（深） | ≥ 3:1 |
| 页脚与页码 | `onBackground × 0.62` | ≥ 3:1 |
| 品牌行（猫标与字标） | `style.brandColor`：主题色，或启用壁纸时的正文色 | ≥ 3:1（7 色实测 3.37–6.86 / 5.36–8.12；壁纸时随正文 ≥ 4.5:1） |
| 用户气泡文字 | `colors.onUserBubble` on `colors.userBubble` | 由 Token 保证，不改 |

代码块与行内代码的底色是 `onSurface × 低 alpha`（docs/32 §32.4.5），压在保护层之上仍然成立，
文字用 `onBackground`，对比度随保护层一起被兜住。

### 49.6.6 字体与字号

| 位置 | 字体来源 | 回退 |
|---|---|---|
| 用户气泡正文 | `TypographyCategory(FontSlot.USER)` + `LocalTypographyFonts.user` | `fontFamilyOf` 返回 `null` → 系统字体（现状） |
| 助手正文 / Markdown / 表格 | `TypographyCategory(FontSlot.ASSISTANT)` | 同上 |
| 代码块、行内代码 | `CodeTextStyle` / `MarkdownInlineCodeStyle`（`FontFamily.Monospace`） | 不跟随自定义字体 |
| LaTeX | `loadExportFonts` 的 KaTeX 字体 | 不跟随自定义字体；语法不支持时回退源码（现状） |
| 标题、页脚 | UI 字体（`style.fonts.ui`） | 解析失败 → `sans-serif-medium` / `sans-serif` |
| 品牌字标 | UI 字体（组合由 Compose 渲染，与标题同一套） | 不需要额外的 `Typeface` 桥接 |

标题与页脚由 `StaticLayout` 与 `Paint` 在原生画布上绘制，当前写死
`Typeface.create("sans-serif-medium", NORMAL)`（标题）与 `Typeface.DEFAULT`（页脚）。
品牌字标走 Compose 渲染，不受这两个常量影响；标题与页脚要跟随 UI 字体，需要把 Compose 的
`FontFamily` 解析成 `android.graphics.Typeface`：用 `createFontFamilyResolver(context).resolve(family, …)`
拿到的 `State<Any>` 在 Android 上就是 `Typeface`；取不到或抛异常时回退系统字重。
**这是阶段 1 的验证点**。

若该桥接在目标 API 上不稳定，退化为"标题与页脚用系统字体、但保持字重层级"，
并接受这一处不一致（正文仍是用户字体）。这条退化路径不影响其他任何结论。

字号完全沿用应用（含单类覆盖）。不额外钳制：用户选了更大的字号，导出就更大，
页数变多由 80 页上限与既有提示兜住。

### 49.6.7 与现有导出的兼容

| 现有行为 | 影响 | 处理 |
|---|---|---|
| 隐藏思考默认勾选 | 无 | 不变，仍每次重置 |
| 隐藏名称（会话内记住） | 无 | 不变 |
| 长图 → 分页自动回退 | 观感可能跳 | 回退时沿用同一 `style`，壁纸参考画幅相同，观感连续 |
| 表格按行分组、跨页重复表头 | 无 | 壁纸在页画布，不参与测量 |
| 公式整体缩放、超高时整体缩小 | 无 | 同上 |
| 图片附件 | 透明 PNG 透出壁纸 | 接受，与聊天页一致 |
| `safeShareTileEnd` 切片 | 无 | 只看捕获层，壁纸不在层内 |
| `shareDirectory` + FileProvider 只读授权 | 单页体积变大 | 新增 120 MB 体积预算，24 小时清理不变 |
| 20 万字符 / 80 页 / 12000 px | 无 | 不调整 |
| 预览按 1600 px 分块解码 | 无 | 不变 |

**旧输出是否保持默认：默认跟随应用，但函数级默认仍为浅色。**

- 面板层：默认「跟随应用」，所以深色用户第一次生成就拿到深色图。这是本轮唯一的默认行为变化，
  也是这个功能的核心价值。
- 函数层：`exportSharedImages(..., style: ShareImageStyle? = null)` 追加在参数表末尾。
  `null` 时按旧参数（`accent` / `typography` / `typographyFonts` / `fontScale`）拼一个浅色样式，
  `androidTest` 里 12 处调用无需改动，逐字节对比的用例（`MessageShareRegression` 用
  `readBytes().contentEquals`）继续通过。
- 若把 `style` 插到参数表中间，会破坏 `MessageShareRegression` 与
  `NativeShareRenderRegression` 的位置参数调用，并让"像素不变"这条回归失效，故不做。

浅色模式下的可见改动有三处（后两处 ΔE < 2）：

| 元素 | 旧 | 新 |
|---|---|---|
| 品牌行 | 只有 `SimpleChat` 一行字，固定蓝色 | 「猫标 + 字标」组合，颜色跟随主题色 |
| 标题 | 字面量 `Color.rgb(32, 34, 40)` | `scheme.onBackground`（`#1A1A1A`） |
| 页脚 | `Color.GRAY` | `onBackground × 0.62` |

默认蓝色主题下品牌行颜色与旧值相同（`#4D6BFE`），只有加了猫标；
其余六个主题色会让品牌行跟着变色，这是"跟随主题色"的预期结果，不是回归。

`ShareImageWriter` 里的 `canvas.drawColor(Color.WHITE)` 一并改为 `colors.pageBackground`，
深色模式才有正确的底。

### 49.6.8 SimpleChat 标识：猫标、字标与文件名

品牌行从"一行文字"升级成"图标 + 字标"的组合：左侧 40 px 猫标，右侧 `SimpleChat` 字标。
**颜色跟随主题色**，与用户气泡、链接、按钮用同一个 `scheme.primary`。

```text
x=64        x=114
┌────────┐
│ 猫标 40 │  SimpleChat（26 px，基线 60）
└────────┘
 y 30..70
```

规格：

| 项 | 值 | 说明 |
|---|---|---|
| 图标 | `AppIcons.SimpleCat`（24 × 24 描边矢量） | 与界面里同一个字形，任意尺寸都清晰 |
| 绘制尺寸 | 40 × 40 px，左上角 (64, 30) | 与标题同左缘；垂直中心对齐字标的光学中心 |
| 字标 | `SimpleChat`，13 sp（2× 密度下 26 px），字重 Medium，基线 60 px，起点 x = 114 | 与图标间距 10 px；字体族取界面字体 |
| 着色 | 图标与字标同色，取 `brandColor` | 不再有独立的品牌蓝常量 |
| 跟随设置 | `useSimpleCatIcon` 为 true 时画图标 | 关闭后只剩字标，字标回到 x = 64 |
| 隐藏名称 | 图标、字标、页脚页码一起移除 | 「隐藏 SimpleChat 名称」的作用域包含图标 |
| 页脚 | 保持纯文字 `SimpleChat · N` | 不重复图标，避免每页两个记号；页脚仍用 `onBackground × 0.62` |

**颜色规则**：`brandColor` 在解析阶段就定好，写进 `ShareImageStyle`：

| 条件 | `brandColor` | 原因 |
|---|---|---|
| 无壁纸 | `scheme.primary` | 主题色在纯底上的对比度全部达标（见下表） |
| 有壁纸 | `scheme.onBackground` | 保护层保证正文 ≥ 4.5:1；品牌行不另算一遍底 |

七个主题色的实测对比度（品牌行 ≥ 3:1 即达标，字标按大号文字算）：

| 主题色 | 浅色档 / 白底 | 深色档 / `PageBgDark` |
|---|---|---|
| 蓝 | 4.33:1 | 5.81:1 |
| 绿 | 3.37:1 | 8.12:1 |
| 红 | 6.86:1 | 5.36:1 |
| 粉 | 3.64:1 | 7.72:1 |
| 紫 | 4.81:1 | 6.14:1 |
| 棕 | 4.58:1 | 6.30:1 |
| 灰 | 4.83:1 | 7.36:1 |

因此"跟随主题色"本身是安全的，不需要为某个色单独调深。
真正需要兜底的是壁纸：浅色主题下，绿色压在中灰保护层上只有约 1:1，
所以启用壁纸时品牌行统一改用正文色。被否掉的替代方案是给组合加一层
`pageBackground × 0.6` 的胶囊底——能保住主题色，但每页多一个色块，
与"通栏排版"的其余部分不搭。

三个取舍：

1. **用矢量而不是 PNG**。`@drawable/simple_chat_logo` 是 1080 × 1080 的白底位图，
   要跟主题色就必须重着色；而 `SRC_IN` 会把白色底块一起染成实心方块，色相旋转又对不准。
   矢量图标用 `tint` 一行就能换色，也没有 40 px 缩放的锯齿。
2. **不复用 adaptive icon**。经典图标是 `mipmap/ic_launcher.xml`（adaptive-icon XML），
   `BitmapFactory.decodeResource` 解不出位图；矢量猫标同时覆盖了"启用猫图标"的绝大多数用户。
3. **不新增开关**。图标跟随设置里已有的「使用 Simple Cat 图标」（`LocalUseSimpleCatIcon`），
   颜色跟随主题色，面板里不多控件。

渲染方式：组合由导出 Composition 渲染，**一次捕获**成小位图，再由 `ShareImageWriter` 每页贴一次。
原因有两个：`ImageVector` 没有 `Bitmap` 转换入口，只有 Compose 能画；顺带字标直接吃
`MaterialTheme.typography`，不必为它单独把 `FontFamily` 桥接成 `Typeface`。

落地顺序是在正文渲染之前、用同一个 `ShareComposeRenderer` 做一次 `measure` 与 `capture(0, 60)`，
拿到 952 × 60 的位图（约 228 KB），把它作为参数传给 `ShareImageWriter`；隐藏名称时跳过这一步。
每页 `drawBitmap` 一次，导出结束时回收。逐页渲染会在几十页里反复测量与重组，没有必要。

**文件名与分享标题不随标识变化**：

| 产物 | 规则 |
|---|---|
| 图片文件名 | `SimpleChat-001.png`；保存到目录时 `SimpleChat-<时间戳>-<序号>.png`，与是否隐藏名称无关 |
| 分享标题（`EXTRA_SUBJECT`） | 会话标题，不加品牌后缀 |
| Markdown 文件名 | `shareFileName(标题).md`，不带品牌前缀 |

理由：文件名是本地产物，用户在相册里靠 `SimpleChat-` 前缀找到自己导出的图；
「隐藏名称」的语义限定在图内（docs/19）。同一个开关有两种作用域，反而说不清。
这条要写进发布说明，避免"隐藏了名称、文件名却还留着"被当成 bug。

## 49.8 边界与异常

| 情况 | 行为 |
|---|---|
| 壁纸文件缺失 / 解码失败 | `WallpaperImageCache.load` 返回 `null` → 纯色；导出继续，预览页提示一次 |
| 壁纸缓存被 LRU 回收 | 导出前重新解码一次（≤ 1440 px，约几十毫秒）；失败按缺失处理 |
| 壁纸参数越界（旧数据） | 按 `WallpaperState` 现有范围钳制（`MaxWallpaperBlur = 160`、`brightness 0.2–2` 等） |
| 字体文件缺失 / 解析失败 | `fontFamilyOf` 返回 `null` → 系统字体，不阻塞 |
| 品牌组合捕获失败 | 退回纯文字品牌行（原生 `StaticLayout`，用 `brandColor` 着色），不阻塞 |
| 「使用 Simple Cat 图标」关闭 | 不画猫标，只画字标 |
| 主题色枚举损坏 | 回落 `AccentColor.BLUE`，与 `MainActivity` 同规则 |
| `darkMode` 字符串损坏 | 回落「跟随应用」 |
| 主题文件声明了壁纸（未来） | 用户壁纸优先（docs/33 §33.3）；导出侧无需额外判断 |
| 字符数 > 20 万 | 现有提示「内容过长…请使用 Markdown」（`share_image_too_long`） |
| 页数 > 80 | 同上 |
| 长图溢出 | 自动回退分页，保留两项选项（现状） |
| 导出体积 > 120 MB | 提示「图片过大，请关闭壁纸或改用 Markdown」，删除本次目录 |
| 导出被取消 | `renderer.close()` + 目录 `deleteRecursively()`（现状） |
| 字号极大导致页数暴涨 | 由 80 页上限兜住，不改逻辑 |

体积预算的判定点放在 `ShareImageWriter.flush()` 写盘之后：累加 `files.sumOf { it.length() }`，
超过 `MaxExportBytes = 120L * 1024 * 1024` 时抛专用异常。
注意它**不能**被 `ShareLongImageOverflow` 的 `catch` 吞掉，否则会被误判成"长图溢出、改分页"。

## 49.9 隐私与安全

壁纸是用户自己选的一张图，可能包含人像、住址、工牌、聊天对象的名字。
把它放进导出图，等于把这张图发给截图接收方。因此：

1. **默认关**。第一次开启时在开关下方给一行说明（面板内文案，不弹窗）：
   「开启后这张壁纸会一起导出。壁纸可能包含个人信息。」
2. **预览页标注**。标题补「含壁纸」，让用户在分享前再确认一次。
3. **不新增权限**。壁纸读取走应用私有目录 `filesDir/wallpaper`，
   不申请媒体读取权限（与 docs/19「不新增媒体读取/存储权限」一致）。
4. **缓存与授权不变**。文件仍写 `cacheDir/shares`，24 小时后清理，
   通过 `${packageName}.fileprovider` 授予临时只读权限。
5. **不写媒体库**。导出只进缓存目录和用户显式选择的目录（`OpenDocumentTree`）。
6. **不携带元数据**。`Bitmap.compress(PNG)` 不写 EXIF，壁纸原始文件不外发。
7. **对外说明**。发布说明中写明"开启壁纸后导出图包含该壁纸"，避免用户事后才发现。
8. **品牌记号与壁纸相互独立**。猫标与字标只表示来源，不携带用户内容；
   隐藏名称时图标一并移除（49.6.8），不会出现"去掉了字、还剩一个图标"的半隐藏状态。
   反过来说，保留品牌行就等于公开"这张图来自 SimpleChat"，这一点由用户通过隐藏开关决定。
   颜色只是样式：有壁纸时品牌行回退正文色，是为了在照片上仍然看清，不是为了隐藏来源。

补充一条容易被忽略的：分页模式下每一页都带壁纸，用户转发 15 张图等于外发 15 份背景。
「含壁纸」标记在分页时同样显示。

## 49.10 性能

| 环节 | 成本 | 措施 |
|---|---|---|
| 壁纸解码 | ≤ 1440 px，一次 | 复用 `WallpaperImageCache`（16 MB LRU），导出不重复解码 |
| 模糊档位 | 9 张 ≤ 480 px 位图 | 缓存内已有；导出不重算，`BlurWorkingSize = 480` 的降采样对 1080 宽足够 |
| 每页壁纸绘制 | 1 次缩放 blit + 2 次矩形 + 可能的 1 次 `saveLayer` | 每页一次；`blurLevel` 为整数时没有 `saveLayer` |
| 页位图 | 1080 × 2400 × 4 ≈ 9.9 MiB；长图 ≤ 1080 × 12000 × 4 ≈ 49 MiB | 与现状相同，壁纸不增加页像素 |
| 捕获层 | 952 × 2048 × 4 ≈ 7.4 MiB（`CaptureTileHeight`） | 不变 |
| 品牌组合 | 一次测量 + 一次捕获（952 × 60，约 228 KB）+ 每页一次 blit | 导出开始时捕获一次，与页数无关 |
| 磁盘 | PNG 体积随背景熵上升，照片壁纸单页可达数 MB | 120 MB 预算（49.8） |
| 页数 / 字符数 | 不变 | 80 页 / 20 万字符 |

**不把壁纸内存计入 `shareImagePageHeight` 的预算**：壁纸位图来自共享缓存，
导出本身不为壁纸新分配像素缓冲，长图的预算公式仍然成立。
唯一的新增峰值是"缓存未命中时的首次解码 + 模糊档位构建"，
上限约 11 MB、一次性、在 `Dispatchers.Default` 上完成，失败即回退纯色。

导出线程模型不变：`exportSharedImages` 在 `Dispatchers.Default`，
测量与捕获切到 `Dispatchers.Main.immediate`，写盘在调用方的 IO 路径。

### 49.11.3 如何避免像素测试脆弱

1. **只对受控区域的单色做颜色断言**，容差 ΔE ≤ 3；不对抗锯齿文字的边缘逐像素比较。
2. **用坐标探针代替整图比较**：页脚区、标题区、气泡右下角、页面四角，
   这些都是已知位置的稳定采样点。
3. **对比度断言看分位数**：在指定矩形内取最暗 1% 与最亮 1% 的亮度算 WCAG 比，
   而不是断言某个像素等于某个值。
4. **固定输入**：固定设备/API、固定 `Density(2f)`、固定字号、固定壁纸素材（纯色或双色渐变）。
   照片类素材只做人工目视，不进自动断言。
5. **不归档截图**：真机截图不入库（docs/README 维护约定），验收记录只写结论与命令。
6. **保留逐字节回归**：`MessageShareRegression` 里比较两次导出 PNG 的用例继续保留，
   它能抓住"同一输入两次输出不一致"这类真问题（例如把时间戳写进图里）。

## 49.13 开放问题

以下四条需要产品决策，本文给出推荐但未替产品拍板。

1. **壁纸默认关，是否接受？**
   推荐关。开的收益是"第一次导出就是满配"，代价是用户可能没意识到自己的照片被带出去。
   若要改默认为开，建议至少在预览页把「含壁纸」做成醒目的胶囊而非副标题。

2. **分页时壁纸每页重复，是否接受？**
   推荐接受。替代方案是只在第一页画壁纸、其余页纯色，体积更小但页与页之间像两套图。
   若选替代方案，需要同步修改 49.6.4 与验收矩阵第 3、4 行。

3. **深色用户默认拿到深色导出图，是否接受这次默认行为变化？**
   推荐接受，这正是本功能的主要价值。若产品要求"升级后第一张图与旧版一致"，
   把默认改为「始终浅色」即可，代价是所有深色用户都要手动点一次。

4. **体积上限取 120 MB 是否合适？**
   推荐 120 MB：照片壁纸 + 80 页时约 100–160 MB，120 MB 能在炸盘前拦住，
   又不会误伤正常使用。若要更保守（例如 64 MB），需接受更多"请关闭壁纸"的提示。
