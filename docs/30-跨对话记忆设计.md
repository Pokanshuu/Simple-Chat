# 30 · 跨对话记忆设计

更新于 2026-11-20。跨对话记忆已可使用，混合检索与端侧向量模型仍处于设计阶段。

## 用户会看到什么

用户开启跨对话记忆后，可以在新会话里接着讨论旧话题。应用根据本轮问题在手机上查找历史原文，选取相关片段，随问题发给当前配置的模型。举例来说，创作对话里往往有两类问法。

| 历史原文 | 新会话中的问题 | 希望找到它的依据 |
|---|---|---|
| “林遥出生在榆川，十岁才搬到海边。” | “林遥的故乡是哪座城？” | 姓名精确命中，即使这段设定来自很早的会话。 |
| “她每次走到地下室门口都会发抖，宁愿绕路。” | “林遥害怕去什么地方？” | 结合上一轮已明确的人物，按语义找到描写恐惧的段落。 |

发送时引用的是用户或助手当时写下的原文。两份设定相互矛盾且都相关时，保留来源会话和时间，方便模型说明差异。问候、转入无关话题或检索置信度不足时，直接发送本轮问题。

## 当前实现

PR #7 默认开启跨对话记忆，默认最多参考 4 个会话。发送前读取按更新时间排列的其他会话，最多扫描 50 个活跃分支。代码按中文单字、相邻双字和英文词建立临时索引，按词元重合、标题和近期程度排序，每个入选会话最多取两轮。明确提及“上次”等回忆意图时，还会用近期会话补足候选。[检索实现](../app/src/main/java/com/simplechat/app/ui/chat/CrossChatMemory.kt) · [配置](../app/src/main/java/com/simplechat/app/data/SettingsStore.kt)

两个协议各自在组装请求时检索，并把片段放在最后一条用户消息前。消息数据库保留原文。当前实现的限制是，第 51 个候选即使含有唯一的人名也进不了排序，入围会话则会在每次发送前重新分词。设置里的“参考会话数”控制最终引用数。[请求组装](../app/src/main/java/com/simplechat/app/ui/chat/ChatViewModel.kt)

## 设置与性能提示

「设置 > 记忆」位于「预设」下方，入口右侧显示「关闭」或「跨对话记忆」。开启主开关后，可调整参考会话数并阅读增强记忆的性能说明。增强记忆尚未开放。

拟议的增强记忆使用一个开关准备全文索引和本地向量模型。

| 用户选择 | 发送时的行为 | 设备上的工作 |
|---|---|---|
| 关闭跨对话记忆 | 跳过跨会话检索 | 停止记忆相关的下载、建库和增量更新。 |
| 开启跨对话记忆 | 在近期会话中按关键词找片段 | 后台按需读取有上限的历史正文并临时分词，跳过模型下载和持久化记忆索引。 |
| 同时开启增强记忆 | 在已建索引的历史中按关键词和语义找片段 | 首次下载模型并分批建立全文和向量索引，之后增量处理新增或修改的正文。 |

用户首次点开「增强记忆」时，先显示模型下载量和可用存储，再提供「开启增强记忆」和「暂不开启」。模型大小取自实际下载清单，索引占用随历史量变化。建议提示文案如下。

> 增强记忆能从更早的对话中找回意思相近的片段。开启后会下载模型，并在手机上为历史对话建立索引。首次建立索引可能增加耗电、发热和存储占用，建议充电时进行。建立期间可以继续使用基础记忆。

准备过程中显示「正在下载模型」或「正在建立索引（已处理会话数 / 总数）」。用户取消启用或下载失败时继续使用基础记忆。两项索引就绪后再显示「增强记忆已就绪」。日后关闭增强即回到基础记忆，停止后台任务。设置中显示模型和索引的实际占用，允许单独清理记忆资源，保留聊天原文。

## 增强记忆的检索流程（拟议）

1. **提取问题。** 以最后一条用户消息为主。遇到“她”“那个方案”等指代时，从当前会话最近的完整轮次补充少量主题词。明确的人名、文件名和代码标识符保留原样。当前会话已在上下文中，候选片段只取自其他会话。
2. **分别查关键词和向量。** 用 Room 全文索引查人名、地名和标识符。用端侧文本嵌入模型把问题编码成向量，在同版本的历史向量中按余弦相似度查找近义表述。两路独立取候选，所以即便原文与问题没有共同关键词，也有机会入选。
3. **合并并挑选原文。** 按片段 ID 去重。首版按两路名次融合，例如把每一路的 `1 / (k + 名次)` 相加，`k` 用评测集确定。两路原始分数尺度不同，分别设置最低相关性条件。对专名精确命中优先保留，对“上次”类问题再考虑时间。合并相邻片段并限制同一会话的占比。
4. **按预算注入。** 从模型上下文窗口扣除系统提示、当前历史、附件估算及预留输出，再给记忆分配 token。预算紧张时依次舍弃低排位片段，预算耗尽时正常发送。给入选原文标注会话、时间和说话人，作为参考资料放在本轮用户问题前。
5. **一次发送只检索一次。** 在协议组装前生成只读快照，包含来源 ID、正文版本和入选片段。OpenAI 与 Anthropic 共用同一套组装输入。同次自动重试复用快照，遇到上下文超限则从快照尾部裁减。用户编辑问题后重新发送时重新检索。

## 索引内容和更新时机

聊天数据库保存原文。关键词和向量索引都是可重建的派生数据。以一轮问答为索引单位，长回复按自然段切成多个片段，保留提问和段落位置，确保回复末尾的细节也能命中。第一版索引用户和助手可见的正文，数据范围限于活跃分支。

| 数据 | 用途 |
|---|---|
| 会话 ID、消息 ID、分段序号及原文范围 | 合并关键词和向量命中，按需读取原文，定位来源。 |
| 正文指纹、分段规则版本 | 判断编辑、重新生成或规则变更后，旧片段是否仍然有效。 |
| 分词结果、关键词索引 | 支持中文相邻双字及英文标识符的本地查询。 |
| 片段向量、模型版本、维度 | 查询只使用与当前编码模型兼容的向量。 |

启用增强记忆后，回复结束时由后台任务按片段更新索引。首次启用或导入历史后分批回填并记录进度，退出后可续建。编辑、删除、切换分支时先让旧片段失效，再异步更新。候选进入请求前按消息 ID、版本和活跃分支复核，避免后台任务落后时引用旧稿。恢复备份后，在增强记忆启用时从聊天原文重建。关闭记忆即跳过查询和注入，暂停后台索引任务。

## Android 端的取舍

首版建议让嵌入模型按需下载，在设备上编码问题和历史片段。首次准备期间使用基础记忆。增强记忆就绪后，若本轮推理超时，可直接采用全文索引的关键词结果。模型和索引都已就绪时，设备可离线完成混合检索。只有入选的原文片段随聊天请求发给当前端点。诊断信息记录耗时、命中数和降级原因即可。

模型选型用同一组中文创作、技术标识符和中英混合样本比较，同时记录模型包大小、首次加载耗时、峰值内存和索引体积。以 384 维 `float32` 为例，1 万个片段仅向量数据约占 14.6 MiB，实际占用还需计入模型、索引和文本。先以归一化向量的精确检索建立质量与耗时基线，若实机查询耗时超过预算，再评估量化或近似最近邻索引。

## 实施与验收

先接入片段 ID、增量关键词索引和两种协议共用的发送快照，再加入端侧向量通道。比较现有实现、仅关键词和混合检索时，使用同一份合成或已获授权的存档，固定每个问题的正确来源片段、候选范围及注入预算。以下是待执行的验收场景。

| 场景 | 检查项 |
|---|---|
| 开关与资源 | 从旧版分别以记忆开启和关闭状态升级，核对增强默认关闭。覆盖取消下载、建库中发送、退出续建、关闭增强和清理资源后再次发送。检查聊天原文、后台任务和实际检索档位。 |
| 早期设定与语义改写 | 把“林遥出生在榆川”放在最近 50 个会话之外。分别测试专名查询与低词面重合的改写，记录正确片段进入前三名的比例。 |
| 指代与无关问题 | 测试“她害怕什么”、普通问候和主题切换。分别记录指代命中率及本应跳过却注入片段的比例。 |
| 编辑、删除、分支和恢复 | 在回填期间修改原文、删除会话或切换分支，检查下一次请求的片段 ID 与原文。重启回填和恢复备份后检查重复项。 |
| 协议、重试和预算 | 核对两种协议的来源列表。相同预算的重试应引用相同片段，发生裁减时保留高排名片段。关闭记忆后请求只包含原对话上下文。 |
| 移动端开销 | 在同一台手机以 1 万个片段和含长回复的存档测量。分别记录冷启动、热查询 P50/P95、后台回填耗时、峰值内存和磁盘占用。 |

增强记忆的发布验收依据语义改写题的收益、专名命中率、无关片段注入率和发送前延迟共同决定。具体嵌入模型、相似度门槛和延迟预算在取得目标手机的基线后定稿。
