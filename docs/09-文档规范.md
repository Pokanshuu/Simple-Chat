# 09 · 文档规范（README · commit · tag · release）

> **状态：已定。**

---

## 1. README

### 基本规范

- 文件名 `README.md`，置于项目根目录。
- 格式 Markdown；语言随项目，本仓库用中文。
- 仅一个一级标题，其余用二级、三级。
- 内容简洁；详细文档放 `docs/`。
- 命令、代码、路径可复制、可运行。
- 随代码同步更新。

### 结构

1. 项目名 + 一句话简介
2. 徽章：构建、覆盖率、版本、许可证（无对应数据时省略）
3. 简介：用途、能力、适用场景
4. 目录
5. 快速开始：环境要求、安装、最小运行示例
6. 使用示例
7. 配置说明：环境变量、配置文件、参数表
8. 开发指南：克隆、依赖、测试、构建、代码风格
9. 贡献指南：链接 `CONTRIBUTING.md`（无该文件时写明提交方式）
10. 许可证：链接 `LICENSE`
11. 其他：致谢、FAQ、路线图、联系方式、变更日志

### 文风

- 正式、凝练，不用主语。
- 只写结果与做法，不写过程与缘由。
- 不写废话。

### 排版

- 中文与英文、数字之间加空格；中文用全角标点，英文与代码用半角。
- 行内代码加反引号；代码块标注语言。
- 图片加 alt；链接用相对路径。
- 命令统一不带 `$`。
- 行长 80–120 字符。
- 禁止提交敏感信息、密钥、内部地址。

### 检查清单

- [ ] 根目录存在 `README.md`
- [ ] 含一句话简介和适用场景
- [ ] 安装、运行命令可直接复制执行
- [ ] 含最小可运行示例
- [ ] 配置项含说明和默认值
- [ ] 测试、构建、贡献方式清晰
- [ ] 许可证明确
- [ ] 链接和图片有效
- [ ] 无敏感信息
- [ ] 与代码版本一致

## 2. commit

### 格式

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

### 类型

| 类型 | 用途 |
|---|---|
| feat | 新功能 |
| fix | 修复缺陷 |
| docs | 文档 |
| style | 格式，不影响逻辑 |
| refactor | 重构 |
| perf | 性能优化 |
| test | 测试 |
| build | 构建系统或依赖 |
| ci | CI 配置 |
| chore | 杂项 |
| revert | 回滚 |

### 范围

- 可选。模块名，小写。
- 格式：`feat(auth): ...`

### 描述

- 祈使句，现在时。
- 首字母小写，不加句号。
- 不超过 50 字符。
- 只写变更结果与最终功能，不写实现方式，不讨论细节。

### 正文

- 可选。
- 每行不超过 72 字符。
- 只写做了什么，不写怎么做。
- 与描述空一行。

### 脚注

- 格式：`BREAKING CHANGE: 说明` 或 `Closes #123`。
- 破坏性变更：类型后加 `!`，或用脚注 `BREAKING CHANGE:`。

### 规则

- 一次提交只做一件事，不混合无关变更。
- 使用英文。
- 禁止无意义描述：`update`、`fix bug`、`修改`。
- 描述与正文、正文与脚注之间各空一行。

### 示例

```
feat(auth): add OAuth2 login

支持 Google 和 GitHub 登录。
Closes #42
```

```
fix(api): handle empty response

BREAKING CHANGE: 移除 v1 接口
```

```
docs: update README
```

### 检查清单

- [ ] 格式符合 `<type>(<scope>): <description>`
- [ ] 类型正确
- [ ] 描述为祈使句、小写、无句号、≤50 字符
- [ ] 描述只写结果，不写实现
- [ ] 正文每行 ≤72 字符
- [ ] 破坏性变更已标注
- [ ] 关联 Issue 已写入脚注
- [ ] 一次提交只含一个逻辑变更

> 既有提交不追溯。

## 3. tag

### 格式

```
v<MAJOR>.<MINOR>.<PATCH>[-<prerelease>]
```

- 前缀 `v` 固定；小写，无空格。

### 版本语义

| 段 | 含义 |
|---|---|
| MAJOR | 不兼容变更 |
| MINOR | 向后兼容的新功能 |
| PATCH | 向后兼容的修复 |
| prerelease | `beta.N`，逐次递增 |

- 当前正式版本为 `1.1.4`；历史 `0.9.0-beta.N` 中的 `N` 曾与 `versionCode` 对齐。
- `versionCode` 随每次发布递增，当前为 20。
- `0.x` 阶段的不兼容变更提升 MINOR。

### 规则

- tag 与 `versionName` 完全一致。
- 每次发版一个 tag，指向该版的 release 提交。
- tag 一经推送不回改；作废则递增 prerelease。

### 示例

```
v0.9.0-beta.6
v1.0.0
```

## 4. release

### 标题

```
SimpleChat v<版本号>
```

### 内容结构

1. 一句话概述
2. 变更
3. 修复
4. 已知问题（可选）
5. 产物与校验

- 内容取自 [`10-CHANGELOG.md`](10-CHANGELOG.md) 对应版本。
- 只写最终功能与结果，不写实现与过程。

### 产物

- 命名：`SimpleChat-<版本号>-release.apk`。
- 附 SHA-256。
- 签名由 `keystore.properties` 提供。

### 规则

- 一个 release 对应一个 tag。
- `versionName` / `versionCode` 与 tag 同步。
- 破坏性变更在正文首行标注 `BREAKING CHANGE:`。
- 预发布版本勾选 pre-release。
- 不附带密钥、`keystore.properties`、内部地址。

### 发布前检查清单

- [ ] `./gradlew testDebugUnitTest` 全绿
- [ ] `versionName` / `versionCode` 已更新
- [ ] `10-CHANGELOG.md` 已更新
- [ ] `./gradlew assembleRelease` 产出签名包
- [ ] 真机验证 Markdown 渲染、代码高亮、Keystore 加解密
- [ ] tag 已推送
- [ ] APK 与 SHA-256 已附
- [ ] pre-release 标记正确

### 示例

```
SimpleChat v0.9.0-beta.6

变更
- 系统栏跟随 App 主题
- 新增七色主题色

修复
- 折叠块展开时标题被顶走
- 流式跟底不平滑

产物
SimpleChat-0.9.0-beta.6-release.apk
SHA-256: <hash>
```
